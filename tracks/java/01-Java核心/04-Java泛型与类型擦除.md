# Java 泛型与类型擦除

> **一句话定位**：Java 泛型在编译期提供类型检查和复用，运行期大部分类型参数会被擦除为上界，并通过强制转换和桥接方法保持多态。

---

## 1. 先给结论

Java 泛型在编译期提供类型检查和复用，运行期大部分类型参数会被擦除为上界，并通过强制转换和桥接方法保持多态。理解 PECS、通配符捕获、泛型不变性和堆污染，才能正确设计集合 API、反射代码和序列化边界。

## 2. 核心原理

### 类型擦除

编译器把类型参数擦除为 Object 或声明的上界，并在读取位置插入转换。不同参数化类型通常共享同一个运行时 Class，因此不能直接 new T、创建 T[] 或用 instanceof 判断具体类型参数。

### 泛型不变性与 PECS

List<Integer> 不是 List<Number> 的子类型。只生产 T 的参数用 ? extends T，只消费 T 的参数用 ? super T；读写兼有时通常直接使用明确的类型参数。

### 桥接方法与堆污染

编译器可能生成 bridge method 保持擦除后的重写关系。原生类型、错误的可变参数和不安全强转会让非目标类型进入泛型容器，最终在远离根因的位置触发 ClassCastException。

## 3. 工作流程与关键路径

```text
[源码声明类型参数]
    │
    ▼
[编译器执行类型检查与推断]
    │
    ▼
[字节码擦除为上界并插入强转]
    │
    ▼
[必要时生成桥接方法]
    │
    ▼
[运行期通过反射保留有限签名信息]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`源码声明类型参数` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`编译器执行类型检查与推断` 与 `字节码擦除为上界并插入强转` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`运行期通过反射保留有限签名信息` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```java
// PECS：生产者 extends，消费者 super。
static <T> void copy(
        List<? extends T> source,
        List<? super T> target) {
    for (T value : source) {
        target.add(value);
    }
}

List<Integer> source = List.of(1, 2, 3);
List<Number> target = new ArrayList<>();
copy(source, target);
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `源码声明类型参数` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `字节码擦除为上界并插入强转` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `运行期通过反射保留有限签名信息` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 6. 工程实践

- 公共 API 优先表达最小必要能力，避免通配符层级过深导致调用方难以推断类型。
- 需要保留运行期泛型信息时使用显式 Class、TypeToken 或框架提供的类型引用，而不是假设反射能恢复全部信息。
- 对 @SafeVarargs 的使用必须能证明方法不会写入或泄漏不安全的泛型数组。

### 6.1 落地检查表

- 写清 API 的空值、异常、顺序与线程安全契约。
- 给复杂度时补充数据规模、最坏路径和内存代价。
- 用单元测试覆盖 equals/hashCode、资源关闭和边界输入。
- 热点代码再用 JFR / profiler 验证，不凭直觉微优化。

## 7. 常见故障

1. 混用原生类型绕过编译检查，线上出现延迟 ClassCastException。
2. 错误使用 ? extends 后尝试写入，或错误使用 ? super 后假设能读取具体子类型。
3. JSON 反序列化只传 List.class，元素退化为 Map 而不是目标类型。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `源码声明类型参数` 逐步检查到 `运行期通过反射保留有限签名信息`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**混用原生类型绕过编译检查，线上出现延迟 ClassCastException。**
