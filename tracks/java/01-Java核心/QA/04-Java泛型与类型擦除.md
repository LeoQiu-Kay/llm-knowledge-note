# Java 泛型与类型擦除 · 面试题

## Q1: 请用一分钟说明Java 泛型与类型擦除的核心目标与工作机制。
> 难度 ⭐⭐ ｜ 高频 🔥🔥🔥

Java 泛型在编译期提供类型检查和复用，运行期大部分类型参数会被擦除为上界，并通过强制转换和桥接方法保持多态。理解 PECS、通配符捕获、泛型不变性和堆污染，才能正确设计集合 API、反射代码和序列化边界。

---

## Q2: 类型擦除的核心机制是什么？
> 难度 ⭐⭐ ｜ 高频 🔥🔥🔥

编译器把类型参数擦除为 Object 或声明的上界，并在读取位置插入转换。不同参数化类型通常共享同一个运行时 Class，因此不能直接 new T、创建 T[] 或用 instanceof 判断具体类型参数。

---

## Q3: 泛型不变性与 PECS为什么重要，实际如何落地？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

List<Integer> 不是 List<Number> 的子类型。只生产 T 的参数用 ? extends T，只消费 T 的参数用 ? super T；读写兼有时通常直接使用明确的类型参数。

---

## Q4: Java 泛型与类型擦除在工程落地时如何做取舍？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

公共 API 优先表达最小必要能力，避免通配符层级过深导致调用方难以推断类型；需要保留运行期泛型信息时使用显式 Class、TypeToken 或框架提供的类型引用，而不是假设反射能恢复全部信息；对 @SafeVarargs 的使用必须能证明方法不会写入或泄漏不安全的泛型数组。

---

## Q5: Java 泛型与类型擦除最常见的故障与排查重点是什么？
> 难度 ⭐⭐⭐⭐ ｜ 高频 🔥🔥

混用原生类型绕过编译检查，线上出现延迟 ClassCastException；错误使用 ? extends 后尝试写入，或错误使用 ? super 后假设能读取具体子类型；JSON 反序列化只传 List.class，元素退化为 Map 而不是目标类型。排查时应先用指标和日志确认现象，再缩小到线程、资源、依赖或数据边界。
