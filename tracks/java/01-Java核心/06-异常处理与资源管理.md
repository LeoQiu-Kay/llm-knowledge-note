# 异常处理与资源管理

> **一句话定位**：异常用于表达无法在当前层正常完成的控制流。

---

## 1. 先给结论

异常用于表达无法在当前层正常完成的控制流。工程上要区分可恢复业务错误、参数错误和系统故障，保持异常因果链，在正确边界转换协议错误；文件、连接和锁等资源必须用 try-with-resources 或 finally 确保释放。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### 受检与非受检异常

受检异常强制调用方处理，适合确实可恢复且需要显式决策的场景；非受检异常适合编程错误和无法局部恢复的失败。关键不是类别本身，而是调用方是否有合理恢复动作。

### 异常链与边界转换

捕获异常时应保留 cause，并在领域、应用、接口边界转换为稳定错误码。日志只在能够增加上下文或最终处理的层记录，避免同一异常被重复打印。

### try-with-resources

实现 AutoCloseable 的资源可自动按逆序关闭；主异常与 close 异常通过 suppressed exceptions 同时保留。数据库连接、流、锁封装和临时文件都应有明确生命周期。

## 3. 工作流程与关键路径

```text
[业务代码抛出异常]
    │
    ▼
[调用栈逐层寻找处理器]
    │
    ▼
[捕获后分类、转换或恢复]
    │
    ▼
[finally / close 释放资源]
    │
    ▼
[日志保留根因与业务上下文]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`业务代码抛出异常` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`调用栈逐层寻找处理器` 与 `捕获后分类、转换或恢复` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`日志保留根因与业务上下文` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```java
try (Connection connection = dataSource.getConnection();
     PreparedStatement statement = connection.prepareStatement(SQL)) {
    statement.setString(1, userId);
    try (ResultSet rs = statement.executeQuery()) {
        return rs.next() ? map(rs) : Optional.empty();
    }
} catch (SQLException e) {
    // 保留 cause，并转换为调用方能理解的领域异常。
    throw new RepositoryException("load user failed: " + userId, e);
}
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `业务代码抛出异常` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `捕获后分类、转换或恢复` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `日志保留根因与业务上下文` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **语义** | 先确定顺序、唯一性、键值、对象身份或异常边界 | 用接口表达约束，不让调用方依赖偶然实现 |
| **复杂度** | 同时说平均、最坏和触发退化的条件 | 用真实数据规模和访问分布压测 |
| **内存** | 关注对象头、引用、扩容、装箱和临时对象 | 观察分配率、存活集与 GC 压力 |
| **并发** | 区分可见性、原子性、不可变与容器线程安全 | 优先缩小共享状态，再选同步原语 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 批处理可选择逐项记录失败继续执行，交易链路则通常应快速失败并回滚。
- 错误响应要对用户稳定、对日志可诊断，同时避免泄露堆栈和内部路径。
- 重试只针对可判定的瞬时故障，并与超时、退避和幂等一起设计。

### 6.1 落地检查表

- 写清 API 的空值、异常、顺序与线程安全契约。
- 给复杂度时补充数据规模、最坏路径和内存代价。
- 用单元测试覆盖 equals/hashCode、资源关闭和边界输入。
- 热点代码再用 JFR / profiler 验证，不凭直觉微优化。

## 7. 常见故障

1. catch Exception 后吞掉异常，调用方误以为成功。
2. 只记录 message 不保留 cause，丢失真正堆栈。
3. 手工 close 在中途异常时未执行，连接池逐渐耗尽。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `业务代码抛出异常` 逐步检查到 `日志保留根因与业务上下文`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**catch Exception 后吞掉异常，调用方误以为成功。**
