# JVM 内存模型与垃圾回收

> **先记住**：JVM 运行时内存主要包括线程私有的程序计数器、虚拟机栈、本地方法栈，以及线程共享的堆和方法区。

---

## 1. 它在解决什么问题？

JVM 运行时内存主要包括线程私有的程序计数器、虚拟机栈、本地方法栈，以及线程共享的堆和方法区。对象通常分配在堆中，GC 以可达性分析判断存活，并根据分代假设选择复制、标记整理或区域化回收。排查问题时先区分堆溢出、元空间溢出、栈溢出和直接内存问题，再结合 GC 日志、堆转储和运行时指标定位，而不是先改大 `-Xmx`。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 运行时数据区

栈帧保存局部变量表、操作数栈、动态链接和返回地址。递归过深或栈帧过大会触发 `StackOverflowError`。堆保存绝大多数对象实例，是 GC 的主要区域。方法区在 HotSpot 中由元空间实现，存放类元数据等内容，使用本地内存。NIO `DirectByteBuffer` 使用堆外内存，堆里只保存其引用和清理信息。

### 可达性与引用

GC 从 GC Roots 出发做可达性分析。常见 Roots 包括线程栈中的引用、静态字段、JNI 引用和正在运行的线程。强引用存在时对象不会回收；软引用可用于内存敏感对象但不适合作为可靠缓存策略；弱引用在下一次 GC 时通常会清除；虚引用主要用于跟踪回收和资源清理。

### 收集器

G1 把堆划分为多个 Region，优先回收垃圾收益高的区域，并以停顿目标做选择，适合较大堆和可预测停顿。ZGC 通过染色指针、读屏障和并发搬迁把大部分工作与应用并发执行，目标是超低停顿，但会付出额外 CPU、内存和屏障成本。选择收集器要根据吞吐、尾延迟、堆规模和 JDK 版本实测。

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **语义** | 先确定顺序、唯一性、键值、对象身份或异常边界 | 用接口表达约束，不让调用方依赖偶然实现 |
| **复杂度** | 同时说平均、最坏和触发退化的条件 | 用真实数据规模和访问分布压测 |
| **内存** | 关注对象头、引用、扩容、装箱和临时对象 | 观察分配率、存活集与 GC 压力 |
| **并发** | 区分可见性、原子性、不可变与容器线程安全 | 优先缩小共享状态，再选同步原语 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

## 6. 放进真实系统，还要考虑什么

- 服务端应固定并记录关键 JVM 参数，启用统一 GC 日志与 OOM 自动堆转储。
- 低延迟不是“停顿越低越好”；更高并发 GC 开销可能降低吞吐，需要结合 SLO 权衡。
- 堆设置过小会频繁 GC，过大会增加扫描、提交内存及故障恢复成本。
- 容器环境要核对 JVM 是否正确识别 cgroup 限额，并为堆外内存、线程栈和原生库预留空间。

### 上线前检查

- 写清 API 的空值、异常、顺序与线程安全契约。
- 给复杂度时补充数据规模、最坏路径和内存代价。
- 用单元测试覆盖 equals/hashCode、资源关闭和边界输入。
- 热点代码再用 JFR / profiler 验证，不凭直觉微优化。

## 7. 常见误区与排查

### 容易踩的坑

1. 无界缓存或监听器未注销造成对象被长期引用，老年代持续增长。
2. 大量动态生成类或类加载器泄漏导致 Metaspace OOM。
3. 线程数失控，单线程栈叠加后耗尽进程地址空间。
4. 只看平均 GC 时间，忽略 Full GC、分配速率和 P99 停顿。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“对象与类被加载”一路检查到“通过停顿、分配率和晋升率调优”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。

## 9. 高频追问

### Q1. JVM 运行时内存区域如何划分？

线程私有区域包括程序计数器、虚拟机栈和本地方法栈；线程共享区域主要是堆和方法区。栈由一个个栈帧组成，保存方法执行状态；堆保存绝大多数对象；HotSpot 用元空间实现方法区并使用本地内存。直接内存不属于 JVM 规范的数据区，但也是服务内存预算的重要部分。

### Q2. JVM 如何判断一个对象可以被回收？

通过从 GC Roots 出发的可达性分析。若对象从任何 Roots 都不可达，才成为回收候选。Roots 常包括线程栈引用、类静态字段、JNI 引用和活动线程等。这比引用计数能处理循环引用，但可达并不等于业务上仍有用，错误的长生命周期引用仍会造成内存泄漏。

### Q3. G1 和 ZGC 的核心取舍是什么？

G1 以 Region 为单位并按收益选择回收区域，通过并发标记和 Mixed GC 控制停顿，兼顾吞吐与可预测延迟。ZGC 把标记和对象搬迁大部分并发化，以屏障、额外内存与 CPU 开销换取极低停顿，更适合大堆、严格尾延迟场景。最终选择应基于目标 JDK、负载和 SLO 压测。

### Q4. 如何区分内存泄漏和堆容量不足？

观察多轮 Full GC 后的存活集基线：若基线随时间持续上升，通常有泄漏或无界增长；若基线稳定但业务峰值超过容量，更像容量不足。再通过堆转储查看 dominator tree、对象数量、GC Roots 引用链，并结合分配速率和业务指标验证，不能只凭一次 OOM 下结论。

### Q5. ThreadLocal 为什么可能导致内存泄漏？

`ThreadLocalMap` 的 key 是弱引用，但 value 是强引用。在线程池中线程长期存活时，key 被回收后 value 仍可能挂在线程的 Map 上，直到后续操作清理槽位。因此应在 `finally` 中调用 `remove`，尤其不能把大对象或请求上下文无限期留在线程池线程中。
