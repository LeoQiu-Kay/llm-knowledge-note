# JVM 内存模型与垃圾回收

## 30 秒回答

JVM 运行时内存主要包括线程私有的程序计数器、虚拟机栈、本地方法栈，以及线程共享的堆和方法区。对象通常分配在堆中，GC 以可达性分析判断存活，并根据分代假设选择复制、标记整理或区域化回收。排查问题时先区分堆溢出、元空间溢出、栈溢出和直接内存问题，再结合 GC 日志、堆转储和运行时指标定位，而不是先改大 `-Xmx`。

## 核心原理

### 运行时数据区

栈帧保存局部变量表、操作数栈、动态链接和返回地址。递归过深或栈帧过大会触发 `StackOverflowError`。堆保存绝大多数对象实例，是 GC 的主要区域。方法区在 HotSpot 中由元空间实现，存放类元数据等内容，使用本地内存。NIO `DirectByteBuffer` 使用堆外内存，堆里只保存其引用和清理信息。

### 可达性与引用

GC 从 GC Roots 出发做可达性分析。常见 Roots 包括线程栈中的引用、静态字段、JNI 引用和正在运行的线程。强引用存在时对象不会回收；软引用可用于内存敏感对象但不适合作为可靠缓存策略；弱引用在下一次 GC 时通常会清除；虚引用主要用于跟踪回收和资源清理。

### 收集器

G1 把堆划分为多个 Region，优先回收垃圾收益高的区域，并以停顿目标做选择，适合较大堆和可预测停顿。ZGC 通过染色指针、读屏障和并发搬迁把大部分工作与应用并发执行，目标是超低停顿，但会付出额外 CPU、内存和屏障成本。选择收集器要根据吞吐、尾延迟、堆规模和 JDK 版本实测。

## 工程权衡

- 服务端应固定并记录关键 JVM 参数，启用统一 GC 日志与 OOM 自动堆转储。
- 低延迟不是“停顿越低越好”；更高并发 GC 开销可能降低吞吐，需要结合 SLO 权衡。
- 堆设置过小会频繁 GC，过大会增加扫描、提交内存及故障恢复成本。
- 容器环境要核对 JVM 是否正确识别 cgroup 限额，并为堆外内存、线程栈和原生库预留空间。

## 常见故障

1. 无界缓存或监听器未注销造成对象被长期引用，老年代持续增长。
2. 大量动态生成类或类加载器泄漏导致 Metaspace OOM。
3. 线程数失控，单线程栈叠加后耗尽进程地址空间。
4. 只看平均 GC 时间，忽略 Full GC、分配速率和 P99 停顿。
