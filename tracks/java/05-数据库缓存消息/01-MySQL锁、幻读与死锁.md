# MySQL 锁、幻读与死锁

> **先记住**：InnoDB 通过记录锁、间隙锁和 next-key lock 协调当前读与写入；锁定范围取决于索引和查询条件。

---

## 1. 它在解决什么问题？

InnoDB 通过记录锁、间隙锁和 next-key lock 协调当前读与写入；锁定范围取决于索引和查询条件。死锁是并发事务形成等待环，数据库会回滚受害者，应用仍需缩短事务、统一加锁顺序并安全重试。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 锁定读与索引

UPDATE、DELETE 和 FOR UPDATE 属于当前读，会在访问的索引记录或范围上加锁；缺少合适索引可能扫描并锁住远超预期的数据。

### 间隙与幻读

可重复读下 next-key lock 把记录和前方间隙结合，限制范围内插入；快照读主要由 MVCC 提供一致视图。

### 死锁处理

InnoDB 检测等待图并选择事务回滚。死锁日志中的 SQL、索引和持锁顺序比单看报错更重要。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```sql
START TRANSACTION;
SELECT id, balance
  FROM account
 WHERE id IN (101, 202)
 ORDER BY id
 FOR UPDATE;

UPDATE account SET balance = balance - 100 WHERE id = 101;
UPDATE account SET balance = balance + 100 WHERE id = 202;
COMMIT;
-- 所有事务按同一顺序加锁，可显著降低死锁概率。
```

### 对照着看

- **从哪里开始**：事务读取或修改索引记录
- **关键状态变化**：并发事务形成等待
- **怎样才算完成**：回滚代价较小事务并重试

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **一致性** | 明确允许的陈旧窗口、重复和丢失语义 | 设计幂等、对账与补偿而非口头承诺 exactly-once |
| **访问路径** | 从索引、分区、key 和队列说明数据怎么被定位 | 验证热点、倾斜、扫描量和回表 |
| **持久性** | 区分内存确认、日志落盘、复制完成与消费完成 | 故障注入验证崩溃和切主语义 |
| **容量** | 按峰值流量、保留期和积压估算 | 监控 lag、命中率、淘汰、磁盘和复制延迟 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

## 6. 放进真实系统，还要考虑什么

- 统一业务资源排序后加锁，降低环路概率。
- 失败重试必须有次数、退避和幂等，不能无限重放整个请求。
- 热点行可通过分片计数、队列化或乐观并发降低竞争。

### 上线前检查

- 所有重试路径都带业务幂等键，消费者能识别重复。
- 容量模型包含峰值、保留期、积压、复制和故障切换余量。
- 用 kill、断网、磁盘满和主从切换验证持久性语义。
- 建立慢查询、命中率、lag、死信和对账差异告警。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 无索引更新扩大锁范围。
2. 事务内用户交互或 RPC 导致长时间持锁。
3. 捕获死锁后立即无退避重试，引发重试风暴。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“事务读取或修改索引记录”一路检查到“回滚代价较小事务并重试”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
