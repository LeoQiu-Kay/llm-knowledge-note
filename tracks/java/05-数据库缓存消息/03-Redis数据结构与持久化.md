# Redis 数据结构与持久化

> **先记住**：Redis 以单线程命令执行语义和高效内存数据结构提供低延迟访问，字符串、哈希、集合、有序集合、Stream 等适合不同模型。

---

## 1. 它在解决什么问题？

Redis 以单线程命令执行语义和高效内存数据结构提供低延迟访问，字符串、哈希、集合、有序集合、Stream 等适合不同模型。RDB、AOF 和复制解决不同恢复目标，不能把缓存默认当作永久可靠数据库。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 结构选择

Hash 适合对象字段，Set 适合去重和集合运算，Sorted Set 适合排名和时间序列索引，Stream 提供消费组和待确认消息。结构要匹配访问模式。

### 过期与淘汰

过期由惰性删除和定期采样共同完成；达到 maxmemory 后按策略淘汰。大量同一时刻过期会造成负载尖峰。

### RDB 与 AOF

RDB 快照紧凑、恢复快但可能丢失快照后的数据；AOF 记录写命令并可重写，数据更完整但文件和恢复成本更高。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```text
MULTI
HINCRBY account:42 balance -100
XADD account-events * account 42 delta -100
EXEC

# 原子命令只保证 Redis 内部状态；跨数据库、消息系统时
# 仍需幂等键、事务消息或对账补偿。
```

### 对照着看

- **从哪里开始**：命令进入单线程执行路径
- **关键状态变化**：数据结构执行操作
- **怎样才算完成**：复制与故障转移传播状态

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **一致性** | 明确允许的陈旧窗口、重复和丢失语义 | 设计幂等、对账与补偿而非口头承诺 exactly-once |
| **访问路径** | 从索引、分区、key 和队列说明数据怎么被定位 | 验证热点、倾斜、扫描量和回表 |
| **持久性** | 区分内存确认、日志落盘、复制完成与消费完成 | 故障注入验证崩溃和切主语义 |
| **容量** | 按峰值流量、保留期和积压估算 | 监控 lag、命中率、淘汰、磁盘和复制延迟 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 缓存实例与持久状态实例最好隔离容量和淘汰策略。
- 大 key、热 key 和高基数结构要提前分片或归档。
- Lua/事务适合短小原子逻辑，长脚本会阻塞其他命令。

### 上线前检查

- 所有重试路径都带业务幂等键，消费者能识别重复。
- 容量模型包含峰值、保留期、积压、复制和故障切换余量。
- 用 kill、断网、磁盘满和主从切换验证持久性语义。
- 建立慢查询、命中率、lag、死信和对账差异告警。

---

## 7. 常见误区与排查

### 容易踩的坑

1. KEYS 或大范围 Lua 阻塞实例。
2. 超大 Hash 删除引发延迟抖动。
3. 以为写入返回成功就等同跨机房永久持久化。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“命令进入单线程执行路径”一路检查到“复制与故障转移传播状态”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
