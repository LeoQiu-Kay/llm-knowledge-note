# Redis 数据结构与持久化

> **一句话定位**：Redis 以单线程命令执行语义和高效内存数据结构提供低延迟访问，字符串、哈希、集合、有序集合、Stream 等适合不同模型。

---

## 1. 先给结论

Redis 以单线程命令执行语义和高效内存数据结构提供低延迟访问，字符串、哈希、集合、有序集合、Stream 等适合不同模型。RDB、AOF 和复制解决不同恢复目标，不能把缓存默认当作永久可靠数据库。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 结构选择

Hash 适合对象字段，Set 适合去重和集合运算，Sorted Set 适合排名和时间序列索引，Stream 提供消费组和待确认消息。结构要匹配访问模式。

### 过期与淘汰

过期由惰性删除和定期采样共同完成；达到 maxmemory 后按策略淘汰。大量同一时刻过期会造成负载尖峰。

### RDB 与 AOF

RDB 快照紧凑、恢复快但可能丢失快照后的数据；AOF 记录写命令并可重写，数据更完整但文件和恢复成本更高。

## 3. 工作流程与关键路径

```text
[命令进入单线程执行路径]
    │
    ▼
[按 key 定位对象]
    │
    ▼
[数据结构执行操作]
    │
    ▼
[AOF 记录或 RDB 快照]
    │
    ▼
[复制与故障转移传播状态]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`命令进入单线程执行路径` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`按 key 定位对象` 与 `数据结构执行操作` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`复制与故障转移传播状态` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```text
MULTI
HINCRBY account:42 balance -100
XADD account-events * account 42 delta -100
EXEC

# 原子命令只保证 Redis 内部状态；跨数据库、消息系统时
# 仍需幂等键、事务消息或对账补偿。
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `命令进入单线程执行路径` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `数据结构执行操作` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `复制与故障转移传播状态` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **一致性** | 明确允许的陈旧窗口、重复和丢失语义 | 设计幂等、对账与补偿而非口头承诺 exactly-once |
| **访问路径** | 从索引、分区、key 和队列说明数据怎么被定位 | 验证热点、倾斜、扫描量和回表 |
| **持久性** | 区分内存确认、日志落盘、复制完成与消费完成 | 故障注入验证崩溃和切主语义 |
| **容量** | 按峰值流量、保留期和积压估算 | 监控 lag、命中率、淘汰、磁盘和复制延迟 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 缓存实例与持久状态实例最好隔离容量和淘汰策略。
- 大 key、热 key 和高基数结构要提前分片或归档。
- Lua/事务适合短小原子逻辑，长脚本会阻塞其他命令。

### 6.1 落地检查表

- 所有重试路径都带业务幂等键，消费者能识别重复。
- 容量模型包含峰值、保留期、积压、复制和故障切换余量。
- 用 kill、断网、磁盘满和主从切换验证持久性语义。
- 建立慢查询、命中率、lag、死信和对账差异告警。

## 7. 常见故障

1. KEYS 或大范围 Lua 阻塞实例。
2. 超大 Hash 删除引发延迟抖动。
3. 以为写入返回成功就等同跨机房永久持久化。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `命令进入单线程执行路径` 逐步检查到 `复制与故障转移传播状态`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**KEYS 或大范围 Lua 阻塞实例。**
