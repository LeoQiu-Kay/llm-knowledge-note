# Java 性能分析与基准测试

> **先记住**：性能优化必须以可重复测量为基础。

---

## 1. 它在解决什么问题？

性能优化必须以可重复测量为基础。宏观压测验证端到端容量和尾延迟，JMH 处理 JVM 微基准中的预热、死代码消除和常量折叠；profile 用采样数据寻找真正热点。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 基准陷阱

JIT 会消除无副作用结果、折叠常量并根据调用形态优化。JMH 通过 fork、warmup、measurement 和 Blackhole 降低这些干扰。

### 延迟分布

平均值会掩盖排队和暂停，需报告吞吐、并发、P50/P95/P99、错误率和资源使用，并保持测试负载模型接近生产。

### 采样与归因

CPU、alloc、lock、wall-clock 等 profile 回答不同问题；火焰图展示聚合调用栈，但仍需结合业务请求和依赖指标判断因果。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```java
@State(Scope.Thread)
public class LookupBenchmark {
    private Map<Integer, String> map;

    @Setup public void setup() {
        map = IntStream.range(0, 10_000).boxed()
            .collect(Collectors.toMap(i -> i, Object::toString));
    }

    @Benchmark public String lookup() {
        return map.get(ThreadLocalRandom.current().nextInt(10_000));
    }
}
```

### 对照着看

- **从哪里开始**：定义可度量性能问题
- **关键状态变化**：预热并隔离环境噪声
- **怎样才算完成**：优化后以业务压测回归

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **证据** | 先抓低开销证据，再做堆转储等重操作 | 所有结论都对应时间窗、指标和 Trace |
| **目标** | 明确优化吞吐、尾延迟、内存还是启动时间 | 一次只改一个变量并保留基线 |
| **环境** | 区分 JVM、容器限制、操作系统和下游问题 | 同时核对 cgroup、磁盘、网络与连接池 |
| **回归** | 微基准不能替代业务压测 | 用生产形态流量验证收益和副作用 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 微基准适合比较局部实现，不能替代真实网络、数据库和 GC 环境。
- 优化目标应来自 SLO 和成本，而不是单个方法纳秒数。
- 每次变更保留基线、环境、JDK 和参数，避免不可复现实验。

### 上线前检查

- 事故现场先保留时间戳、版本、流量和容器资源基线。
- 采集线程转储、GC、JFR 等证据时评估额外开销。
- 调优一次只改一个变量，并保留可立即回退的配置。
- 微基准、组件压测与端到端压测分别回答不同问题。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 在 Debug、低功耗或共享机器上跑基准。
2. 只测成功快路径，忽略错误和超时路径。
3. 吞吐提高但 P99 和 CPU 成本恶化。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“定义可度量性能问题”一路检查到“优化后以业务压测回归”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
