# 类加载与双亲委派

> **一句话定位**：JVM 类生命周期包括加载、验证、准备、解析、初始化和卸载。

---

## 1. 先给结论

JVM 类生命周期包括加载、验证、准备、解析、初始化和卸载。类由“全限定名 + 定义它的 ClassLoader”共同确定身份；双亲委派优先让父加载器处理，减少核心类被重复或恶意替换。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 加载与初始化

加载创建 Class 对象，链接完成验证、静态字段默认值和符号解析；初始化执行类初始化方法。访问编译期常量等操作不一定触发初始化。

### ClassLoader 身份

相同字节码若由不同加载器定义，在 JVM 中也是不同类型，强转会失败。插件、容器和热部署都依赖独立加载器形成命名空间。

### 委派与破坏

父优先保护基础类并促进共享；SPI、模块容器可能使用线程上下文加载器或子优先策略，但必须限定包范围避免依赖冲突。

## 3. 工作流程与关键路径

```text
[按类名发起加载]
    │
    ▼
[父加载器优先查找]
    │
    ▼
[读取字节码并校验]
    │
    ▼
[准备静态字段并解析符号引用]
    │
    ▼
[初始化静态代码并返回 Class]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`按类名发起加载` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`父加载器优先查找` 与 `读取字节码并校验` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`初始化静态代码并返回 Class` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```java
final class PluginClassLoader extends URLClassLoader {
    PluginClassLoader(URL[] urls, ClassLoader parent) {
        super(urls, parent);
    }
}

try (var loader = new PluginClassLoader(urls, Api.class.getClassLoader())) {
    Class<?> type = Class.forName(pluginClassName, true, loader);
    Plugin plugin = type.asSubclass(Plugin.class)
                        .getDeclaredConstructor()
                        .newInstance();
    plugin.start();
}
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `按类名发起加载` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `读取字节码并校验` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `初始化静态代码并返回 Class` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **证据** | 先抓低开销证据，再做堆转储等重操作 | 所有结论都对应时间窗、指标和 Trace |
| **目标** | 明确优化吞吐、尾延迟、内存还是启动时间 | 一次只改一个变量并保留基线 |
| **环境** | 区分 JVM、容器限制、操作系统和下游问题 | 同时核对 cgroup、磁盘、网络与连接池 |
| **回归** | 微基准不能替代业务压测 | 用生产形态流量验证收益和副作用 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 插件隔离要明确 API 由父加载器共享、实现由子加载器加载。
- 热部署需确保旧 ClassLoader 及其线程、ThreadLocal、静态缓存可回收。
- 排查依赖冲突同时打印类名、加载器和代码来源。

### 6.1 落地检查表

- 事故现场先保留时间戳、版本、流量和容器资源基线。
- 采集线程转储、GC、JFR 等证据时评估额外开销。
- 调优一次只改一个变量，并保留可立即回退的配置。
- 微基准、组件压测与端到端压测分别回答不同问题。

## 7. 常见故障

1. 第三方包多版本冲突导致 NoSuchMethodError。
2. 线程上下文加载器长期引用旧应用造成 Metaspace 泄漏。
3. 自定义加载器错误覆盖 java.* 或共享 API。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `按类名发起加载` 逐步检查到 `初始化静态代码并返回 Class`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**第三方包多版本冲突导致 NoSuchMethodError。**
