# GC 调优与停顿治理

> **先记住**：GC 调优不是先改参数，而是从分配速率、存活集、晋升、停顿分布和 CPU 成本判断问题。

---

## 1. 它在解决什么问题？

GC 调优不是先改参数，而是从分配速率、存活集、晋升、停顿分布和 CPU 成本判断问题。先满足内存预算与 SLO，再选择收集器和堆布局；泄漏、超大对象和突发分配必须从应用侧解决。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### GC 指标模型

关注分配速率、回收后占用、年轻代晋升、并发周期是否及时、P95/P99 停顿和应用吞吐，平均停顿不足以描述尾延迟。

### 收集器选择

G1 兼顾吞吐与可预测停顿，ZGC 面向超低停顿和大堆；实际效果取决于 JDK、堆规模、对象图和 CPU 余量。

### 堆外与容器预算

进程内存还包括 Metaspace、线程栈、Code Cache、Direct Memory 和 native 库。容器限额必须为这些区域及安全余量留空间。

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```bash
# 统一记录 GC 日志，保留时间、级别和文件轮转。

```

### 对照着看

- **从哪里开始**：采集分配率、存活集与停顿
- **关键状态变化**：选择堆大小与收集器
- **怎样才算完成**：逐项调整并回归业务延迟

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **证据** | 先抓低开销证据，再做堆转储等重操作 | 所有结论都对应时间窗、指标和 Trace |
| **目标** | 明确优化吞吐、尾延迟、内存还是启动时间 | 一次只改一个变量并保留基线 |
| **环境** | 区分 JVM、容器限制、操作系统和下游问题 | 同时核对 cgroup、磁盘、网络与连接池 |
| **回归** | 微基准不能替代业务压测 | 用生产形态流量验证收益和副作用 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 先修复无界缓存和分配热点，再调堆与收集器。
- 更大堆减少回收频率，却可能增加提交内存、扫描和故障恢复时间。
- 参数变更通过压测和线上灰度验证，不复制其他服务的“万能参数”。

### 上线前检查

- 事故现场先保留时间戳、版本、流量和容器资源基线。
- 采集线程转储、GC、JFR 等证据时评估额外开销。
- 调优一次只改一个变量，并保留可立即回退的配置。
- 微基准、组件压测与端到端压测分别回答不同问题。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 只增大 Xmx 掩盖泄漏。
2. 容器内把 Xmx 设到内存上限，进程被 OOM Killer 杀死。
3. 只看 Young GC，忽略并发周期失败和 Full GC。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“采集分配率、存活集与停顿”一路检查到“逐项调整并回归业务延迟”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
