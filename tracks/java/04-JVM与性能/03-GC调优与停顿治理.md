# GC 调优与停顿治理

> **一句话定位**：GC 调优不是先改参数，而是从分配速率、存活集、晋升、停顿分布和 CPU 成本判断问题。

---

## 1. 先给结论

GC 调优不是先改参数，而是从分配速率、存活集、晋升、停顿分布和 CPU 成本判断问题。先满足内存预算与 SLO，再选择收集器和堆布局；泄漏、超大对象和突发分配必须从应用侧解决。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### GC 指标模型

关注分配速率、回收后占用、年轻代晋升、并发周期是否及时、P95/P99 停顿和应用吞吐，平均停顿不足以描述尾延迟。

### 收集器选择

G1 兼顾吞吐与可预测停顿，ZGC 面向超低停顿和大堆；实际效果取决于 JDK、堆规模、对象图和 CPU 余量。

### 堆外与容器预算

进程内存还包括 Metaspace、线程栈、Code Cache、Direct Memory 和 native 库。容器限额必须为这些区域及安全余量留空间。

## 3. 工作流程与关键路径

```text
[采集分配率、存活集与停顿]
    │
    ▼
[确认吞吐或延迟目标]
    │
    ▼
[选择堆大小与收集器]
    │
    ▼
[压测观察晋升、并发周期和 Full GC]
    │
    ▼
[逐项调整并回归业务延迟]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`采集分配率、存活集与停顿` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`确认吞吐或延迟目标` 与 `选择堆大小与收集器` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`逐项调整并回归业务延迟` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```bash
# 统一记录 GC 日志，保留时间、级别和文件轮转。
java -Xms4g -Xmx4g              -Xlog:gc*,safepoint:file=gc.log:time,uptime,level,tags:filecount=10,filesize=50m              -jar app.jar

jcmd <pid> GC.heap_info
jcmd <pid> JFR.start name=gc-check duration=120s filename=gc-check.jfr
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `采集分配率、存活集与停顿` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `选择堆大小与收集器` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `逐项调整并回归业务延迟` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **证据** | 先抓低开销证据，再做堆转储等重操作 | 所有结论都对应时间窗、指标和 Trace |
| **目标** | 明确优化吞吐、尾延迟、内存还是启动时间 | 一次只改一个变量并保留基线 |
| **环境** | 区分 JVM、容器限制、操作系统和下游问题 | 同时核对 cgroup、磁盘、网络与连接池 |
| **回归** | 微基准不能替代业务压测 | 用生产形态流量验证收益和副作用 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 先修复无界缓存和分配热点，再调堆与收集器。
- 更大堆减少回收频率，却可能增加提交内存、扫描和故障恢复时间。
- 参数变更通过压测和线上灰度验证，不复制其他服务的“万能参数”。

### 6.1 落地检查表

- 事故现场先保留时间戳、版本、流量和容器资源基线。
- 采集线程转储、GC、JFR 等证据时评估额外开销。
- 调优一次只改一个变量，并保留可立即回退的配置。
- 微基准、组件压测与端到端压测分别回答不同问题。

## 7. 常见故障

1. 只增大 Xmx 掩盖泄漏。
2. 容器内把 Xmx 设到内存上限，进程被 OOM Killer 杀死。
3. 只看 Young GC，忽略并发周期失败和 Full GC。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `采集分配率、存活集与停顿` 逐步检查到 `逐项调整并回归业务延迟`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**只增大 Xmx 掩盖泄漏。**
