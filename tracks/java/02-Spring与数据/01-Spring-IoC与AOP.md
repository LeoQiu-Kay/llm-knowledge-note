# Spring IoC 与 AOP

> **一句话定位**：IoC 把对象创建、依赖装配和生命周期交给容器，依赖注入是它的主要实现方式；AOP 则把事务、鉴权、监控等横切逻辑织入业务调用。

---

## 1. 先给结论

IoC 把对象创建、依赖装配和生命周期交给容器，依赖注入是它的主要实现方式；AOP 则把事务、鉴权、监控等横切逻辑织入业务调用。Spring 启动时解析 BeanDefinition、实例化并填充依赖，再经过 BeanPostProcessor 完成增强。AOP 通常基于 JDK 动态代理或 CGLIB，因此自调用、非代理对象和方法可见性都会影响增强是否生效。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### Bean 生命周期

容器先读取配置形成 `BeanDefinition`，随后实例化 Bean、填充属性、调用 Aware 回调、执行各类 `BeanPostProcessor`，再运行初始化方法。销毁时执行销毁回调。AOP 代理通常由后置处理器在初始化阶段创建，因此从容器拿到的对象可能是代理而非原始实例。

推荐构造器注入：依赖显式、便于测试，并能让必要依赖保持不可变。字段注入隐藏依赖且不利于无容器测试。循环依赖往往暴露设计问题；Spring 对部分单例 setter 循环依赖可通过提前暴露引用处理，但构造器循环依赖无法这样解决。

### AOP 与事务

JDK 动态代理面向接口，CGLIB 通过生成子类代理。调用先进入代理，再由拦截器链执行事务、日志等增强，最终调用目标方法。`@Transactional` 的本质是事务拦截器：进入时开启或加入事务，正常返回时提交，满足回滚规则的异常时回滚。

## 3. 工作流程与关键路径

```text
[扫描配置与 BeanDefinition]
    │
    ▼
[实例化并注入依赖]
    │
    ▼
[BeanPostProcessor 增强 Bean]
    │
    ▼
[代理拦截方法调用]
    │
    ▼
[事务、监控等通知围绕目标执行]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`扫描配置与 BeanDefinition` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`实例化并注入依赖` 与 `BeanPostProcessor 增强 Bean` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`事务、监控等通知围绕目标执行` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```java
@Configuration
class PaymentConfig {
    @Bean
    PaymentService paymentService(PaymentRepository repository) {
        return new DefaultPaymentService(repository);
    }
}

@Aspect
@Component
class TimingAspect {
    @Around("@annotation(Monitored)")
    Object time(ProceedingJoinPoint pjp) throws Throwable {
        return metrics.time(pjp.getSignature().toShortString(), pjp::proceed);
    }
}
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `扫描配置与 BeanDefinition` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `BeanPostProcessor 增强 Bean` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `事务、监控等通知围绕目标执行` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **边界** | 明确容器、代理、Web、事务和数据访问各自负责什么 | 避免把业务规则藏进框架回调 |
| **代理** | 说明哪些调用会穿过代理，哪些会绕过 | 用集成测试覆盖 self-invocation、final 与异常路径 |
| **数据** | 从索引访问路径、事务边界和连接占用解释性能 | 核对执行计划、锁等待与连接池指标 |
| **可替换性** | 抽象应允许测试替身和实现替换 | 避免全局静态访问与过度自动配置 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 事务边界应围绕完整业务用例，而不是随意标在每个 DAO 方法上。
- 长事务会占用连接、锁和版本，外部 HTTP/RPC 调用一般不要放进数据库事务。
- AOP 适合与业务正交且规则统一的能力；核心业务流程隐藏在切面中会降低可读性。
- 多数据源、异步线程或事件消费场景要明确事务管理器和上下文传播边界。

### 6.1 落地检查表

- 用集成测试验证代理、事务、MVC 与数据库真实边界。
- 配置提供默认值、校验、版本和回滚，不把环境差异写死。
- 监控连接池、慢 SQL、事务时长、错误分类和请求 Trace。
- 对自动装配和动态 SQL 保留可解释的启动报告与执行计划。

## 7. 常见故障

1. 同一个类中 `this.method()` 自调用绕过代理，事务或切面不生效。
2. 捕获异常后不再抛出，事务拦截器看到“正常返回”而提交。
3. 默认只对运行时异常回滚，却期望受检异常自动回滚。
4. Bean 初始化阶段过早调用尚未完成增强的对象，得到原始引用。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `扫描配置与 BeanDefinition` 逐步检查到 `事务、监控等通知围绕目标执行`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**同一个类中 `this.method()` 自调用绕过代理，事务或切面不生效。**

## 🎯 高频追问

1. **什么是 IoC，为什么推荐构造器注入？**

   IoC 是把对象创建、依赖装配和生命周期控制从业务代码移交给容器，依赖注入是主要实现方式。构造器注入能显式表达必需依赖、便于无容器单测、允许字段不可变，并能在创建时保证对象处于完整状态；字段注入隐藏依赖且不利于测试。

2. **Spring Bean 的主要生命周期阶段有哪些？**

   读取配置生成 BeanDefinition，实例化 Bean，填充依赖，执行 Aware 回调，依次经过初始化前后的 BeanPostProcessor，再执行初始化回调并投入使用；容器关闭时执行销毁回调。AOP 代理通常由后置处理器创建，所以最终暴露的对象可能是代理。

3. **为什么同类中的事务方法自调用可能不生效？**

   声明式事务依赖代理拦截。从外部通过代理调用方法时，事务拦截器才会执行；同类中的 `this.method()` 直接调用目标对象自身，绕过代理，因此不会开启新的事务增强。可以重构事务边界到另一个 Bean，或通过合适的代理调用，但不应把获取自身代理作为默认设计。

4. **JDK 动态代理和 CGLIB 有什么区别？**

   JDK 动态代理基于接口生成代理对象；CGLIB 通过生成目标类子类并重写可代理方法。没有接口时 Spring 通常使用 CGLIB。`final` 类或方法无法被子类代理覆盖，private 方法也不是正常代理入口。业务上应面向代理语义设计，而不是依赖两者细小性能差异。

5. **@Transactional 捕获异常后为什么可能提交？**

   事务拦截器根据方法是否以符合回滚规则的异常退出决定回滚。业务代码捕获异常并正常返回时，拦截器认为调用成功，便会提交。应在需要回滚时继续抛出异常、显式标记 rollback-only，或重新设计错误处理；还要注意默认通常只对运行时异常和 Error 回滚。
