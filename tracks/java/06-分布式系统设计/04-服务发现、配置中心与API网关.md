# 服务发现、配置中心与 API 网关

> **先记住**：服务发现维护实例与健康状态，配置中心分发运行参数，API 网关承担统一入口的路由、认证、限流和协议转换。

---

## 1. 它在解决什么问题？

服务发现维护实例与健康状态，配置中心分发运行参数，API 网关承担统一入口的路由、认证、限流和协议转换。它们是控制面能力，故障时应尽量让数据面继续使用最近可用状态。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 发现与健康检查

客户端或代理从注册中心获取实例列表并负载均衡；健康检查需区分进程存活、可接流量和关键依赖状态。

### 配置发布

配置需要版本、校验、灰度、审计和回滚。监听更新时先构建新快照并原子替换，避免读取半更新状态。

### 网关职责

网关适合通用横切能力，不应承载大量领域编排；请求身份和追踪上下文需安全传递到下游。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```yaml
routes:
  - id: order-api-v2
    match:
      path: /api/orders/**
      header: { X-Canary: "v2" }
    filters:
      - authenticate
      - rateLimit: { key: userId, permitsPerSecond: 50 }
    upstream:
      service: order-service
      timeoutMs: 800
```

### 对照着看

- **从哪里开始**：实例注册并定期续约
- **关键状态变化**：配置中心下发版本化配置
- **怎样才算完成**：指标反馈驱动摘除和回滚

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **一致性边界** | 先说明哪些状态必须原子，哪些可最终一致 | 把补偿、对账和人工兜底写进方案 |
| **故障模型** | 考虑超时、重复、乱序、分区和部分成功 | 通过故障注入而非正常路径证明可靠性 |
| **容量保护** | 入口、服务和依赖分别限流与隔离 | 阈值来自压测和 SLO，不靠拍脑袋 |
| **可观测性** | 每个跨服务操作携带业务键与 trace_id | 告警能直接跳到证据和回滚动作 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 控制面短暂不可用时使用本地缓存继续服务。
- 配置动态化越多，测试状态空间越大，应限制高风险开关。
- 网关集中治理带来统一性，也形成容量和故障关键点。

### 上线前检查

- 先写 SLO、故障模型和降级结果，再选中间件。
- 跨服务操作记录业务键、版本、trace_id 和补偿状态。
- 恢复策略使用退避、抖动、限次和渐进放量。
- 定期演练单实例、单机房、依赖和数据不一致故障。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 健康检查只看端口，故障实例持续接流量。
2. 配置全量同时推送导致所有实例一起重连。
3. 网关重试写请求造成重复副作用。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“实例注册并定期续约”一路检查到“指标反馈驱动摘除和回滚”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
