# 幂等、重试与去重

> **一句话定位**：幂等保证相同业务请求重复执行不会产生额外副作用，是网络重试和至少一次投递的基础。

---

## 1. 先给结论

幂等保证相同业务请求重复执行不会产生额外副作用，是网络重试和至少一次投递的基础。实现依赖稳定幂等键、原子状态检查与写入、结果复用，以及明确的键作用域和过期策略。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### 幂等键设计

键应代表同一业务意图而不是随机请求，通常包含调用方、操作类型和业务唯一号；重试必须复用同一键。

### 原子去重

数据库唯一约束、条件更新、状态机或原子缓存脚本用于把“检查并执行”合并，单独先查再写仍有竞态。

### 重试策略

只重试瞬时错误，采用指数退避、随机抖动、截止时间和最大次数；超时后先查询上一请求结果再决定重试。

## 3. 工作流程与关键路径

```text
[请求携带业务幂等键]
    │
    ▼
[服务原子占位或查询历史结果]
    │
    ▼
[首次请求执行副作用]
    │
    ▼
[结果与状态持久化]
    │
    ▼
[重复请求返回同一结果或安全拒绝]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`请求携带业务幂等键` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`服务原子占位或查询历史结果` 与 `首次请求执行副作用` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`重复请求返回同一结果或安全拒绝` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```sql
CREATE TABLE idempotency_record (
  tenant_id     BIGINT NOT NULL,
  idem_key      VARCHAR(128) NOT NULL,
  request_hash  CHAR(64) NOT NULL,
  status        VARCHAR(16) NOT NULL,
  response_json JSON,
  PRIMARY KEY (tenant_id, idem_key)
);

-- 原子插入成功者执行；冲突者校验 request_hash 后返回历史结果。
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `请求携带业务幂等键` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `首次请求执行副作用` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `重复请求返回同一结果或安全拒绝` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **一致性边界** | 先说明哪些状态必须原子，哪些可最终一致 | 把补偿、对账和人工兜底写进方案 |
| **故障模型** | 考虑超时、重复、乱序、分区和部分成功 | 通过故障注入而非正常路径证明可靠性 |
| **容量保护** | 入口、服务和依赖分别限流与隔离 | 阈值来自压测和 SLO，不靠拍脑袋 |
| **可观测性** | 每个跨服务操作携带业务键与 trace_id | 告警能直接跳到证据和回滚动作 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 结果缓存提高重复请求体验，但要控制容量和保留期。
- 客户端、网关、服务和消息框架多层重试会相乘，应统一预算。
- 非幂等外部系统通过业务唯一号或对账补偿降低风险。

### 6.1 落地检查表

- 先写 SLO、故障模型和降级结果，再选中间件。
- 跨服务操作记录业务键、版本、trace_id 和补偿状态。
- 恢复策略使用退避、抖动、限次和渐进放量。
- 定期演练单实例、单机房、依赖和数据不一致故障。

## 7. 常见故障

1. 每次重试生成新幂等键。
2. 仅用 Redis SETNX，键过期早于业务完成。
3. 对参数错误和永久失败持续重试。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `请求携带业务幂等键` 逐步检查到 `重复请求返回同一结果或安全拒绝`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**每次重试生成新幂等键。**
