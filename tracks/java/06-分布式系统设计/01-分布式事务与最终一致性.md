# 分布式事务与最终一致性

> **一句话定位**：跨服务一致性无法仅依赖单库事务。

---

## 1. 先给结论

跨服务一致性无法仅依赖单库事务。强一致可用 XA 等协调协议但成本高，互联网业务更常用 Saga、TCC、事务消息或 Outbox，把全局流程拆成可提交、可重试、可补偿的本地事务。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### 一致性边界

先定义必须原子、允许延迟和可人工修复的业务不变量，再选择方案；不是所有字段都需要同一时刻一致。

### Outbox 与消息

业务数据和待发送事件在同一数据库事务写入，后台可靠发布并标记状态，避免“数据库成功但消息丢失”。消费端用 inbox 或业务唯一键去重。

### Saga 与补偿

Saga 把长事务拆成本地事务序列，失败后执行语义补偿。补偿不是物理回滚，必须考虑已被外部观察和补偿失败。

## 3. 工作流程与关键路径

```text
[本地事务写业务数据与事件]
    │
    ▼
[可靠投递消息]
    │
    ▼
[下游幂等消费]
    │
    ▼
[失败步骤重试或补偿]
    │
    ▼
[对账任务发现并修复最终不一致]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`本地事务写业务数据与事件` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`可靠投递消息` 与 `下游幂等消费` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`对账任务发现并修复最终不一致` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```sql
START TRANSACTION;
INSERT INTO orders(id, user_id, status) VALUES (?, ?, 'CREATED');
INSERT INTO outbox(id, aggregate_id, event_type, payload, status)
VALUES (?, ?, 'ORDER_CREATED', ?, 'NEW');
COMMIT;

-- Relay 扫描 NEW 事件并发布；消费者以 event id 幂等处理。
-- 发布成功后更新状态，另有对账任务修复长期未完成记录。
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `本地事务写业务数据与事件` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `下游幂等消费` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `对账任务发现并修复最终不一致` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **一致性边界** | 先说明哪些状态必须原子，哪些可最终一致 | 把补偿、对账和人工兜底写进方案 |
| **故障模型** | 考虑超时、重复、乱序、分区和部分成功 | 通过故障注入而非正常路径证明可靠性 |
| **容量保护** | 入口、服务和依赖分别限流与隔离 | 阈值来自压测和 SLO，不靠拍脑袋 |
| **可观测性** | 每个跨服务操作携带业务键与 trace_id | 告警能直接跳到证据和回滚动作 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 资金、库存等核心不变量可局部强一致，外围通知最终一致。
- TCC 控制力强但业务侵入和资源悬挂处理复杂。
- 所有方案都需要状态查询、对账和人工兜底。

### 6.1 落地检查表

- 先写 SLO、故障模型和降级结果，再选中间件。
- 跨服务操作记录业务键、版本、trace_id 和补偿状态。
- 恢复策略使用退避、抖动、限次和渐进放量。
- 定期演练单实例、单机房、依赖和数据不一致故障。

## 7. 常见故障

1. 消息发送与数据库提交分离造成丢事件。
2. 补偿接口不幂等，重复回滚产生二次损失。
3. 流程状态只在日志里，没有可查询状态机。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `本地事务写业务数据与事件` 逐步检查到 `对账任务发现并修复最终不一致`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**消息发送与数据库提交分离造成丢事件。**
