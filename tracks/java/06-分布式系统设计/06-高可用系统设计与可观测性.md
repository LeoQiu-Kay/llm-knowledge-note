# 高可用系统设计与可观测性

> **一句话定位**：高可用从消除单点、限制故障域、自动恢复和可验证演练入手。

---

## 1. 先给结论

高可用从消除单点、限制故障域、自动恢复和可验证演练入手。可观测性用指标发现趋势、日志解释事件、Trace 还原调用链，并以 SLI/SLO 和错误预算决定发布速度与治理优先级。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 冗余与故障域

实例、机架、可用区和区域是不同故障域；冗余只有在依赖、数据和流量路径真正隔离时才有效。

### SLI 与错误预算

可用性、正确率、延迟和新鲜度等 SLI 应从用户体验定义。错误预算把可靠性目标转换为发布与治理决策。

### 三类遥测

Metrics 适合聚合和告警，Logs 适合离散上下文，Traces 适合跨服务因果链。统一 correlation ID、时间和版本信息才能关联。

## 3. 工作流程与关键路径

```text
[定义 SLI / SLO 与故障域]
    │
    ▼
[多副本部署并健康检查]
    │
    ▼
[请求携带 Trace 上下文]
    │
    ▼
[日志、指标、Trace 汇聚]
    │
    ▼
[告警触发降级、切换与复盘]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`定义 SLI / SLO 与故障域` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`多副本部署并健康检查` 与 `请求携带 Trace 上下文` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`告警触发降级、切换与复盘` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```java
Span span = tracer.spanBuilder("order.create")
    .setAttribute("order.id", order.id())
    .setAttribute("tenant.id", tenantId)
    .startSpan();
try (Scope ignored = span.makeCurrent()) {
    return service.create(order);
} catch (Throwable error) {
    span.recordException(error);
    span.setStatus(StatusCode.ERROR);
    throw error;
} finally {
    span.end();
}
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `定义 SLI / SLO 与故障域` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `请求携带 Trace 上下文` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `告警触发降级、切换与复盘` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **一致性边界** | 先说明哪些状态必须原子，哪些可最终一致 | 把补偿、对账和人工兜底写进方案 |
| **故障模型** | 考虑超时、重复、乱序、分区和部分成功 | 通过故障注入而非正常路径证明可靠性 |
| **容量保护** | 入口、服务和依赖分别限流与隔离 | 阈值来自压测和 SLO，不靠拍脑袋 |
| **可观测性** | 每个跨服务操作携带业务键与 trace_id | 告警能直接跳到证据和回滚动作 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 多活提升容灾能力，也显著增加数据一致性和运维复杂度。
- 告警基于用户影响和燃烧率，减少无行动价值的噪声。
- 混沌演练从可控依赖、限流和回滚开始，逐步扩大故障范围。

### 6.1 落地检查表

- 先写 SLO、故障模型和降级结果，再选中间件。
- 跨服务操作记录业务键、版本、trace_id 和补偿状态。
- 恢复策略使用退避、抖动、限次和渐进放量。
- 定期演练单实例、单机房、依赖和数据不一致故障。

---

## 7. 常见故障

1. 只有实例健康监控，没有业务成功率。
2. 备用链路长期不演练，真正故障时不可用。
3. 日志、指标和 Trace 使用不同请求标识，无法关联。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `定义 SLI / SLO 与故障域` 逐步检查到 `告警触发降级、切换与复盘`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**只有实例健康监控，没有业务成功率。**
