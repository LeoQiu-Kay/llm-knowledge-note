# Java 内存模型与 volatile

> **先记住**：Java 内存模型定义线程之间读写共享变量的可见性和有序性。

---

## 1. 它在解决什么问题？

Java 内存模型定义线程之间读写共享变量的可见性和有序性。happens-before 是判断读能否看到写的核心规则；volatile 提供可见性和特定顺序约束，但复合读改写仍不具备原子性。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### happens-before

程序次序、监视器解锁到加锁、volatile 写到读、线程 start/join 等规则建立跨线程可见性；没有 happens-before 的数据竞争结果不可依赖。

### volatile 语义

volatile 写具有释放语义，读具有获取语义，可用于状态发布和停止标记；它不能把 count++ 变成原子操作。

### 安全发布

对象应通过 final 字段、锁、volatile 引用、静态初始化或并发容器安全发布，避免其他线程观察到构造中的中间状态。

---

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```java
final class Service {
    private volatile boolean stopped;

    void runLoop() {
        while (!stopped) {
            doOneUnit();
        }
    }

    void stop() {
        stopped = true; // volatile 写发布此前动作，并让读线程可见
    }
}
```

### 对照着看

- **从哪里开始**：线程执行普通读写
- **关键状态变化**：同步动作建立 happens-before
- **怎样才算完成**：读线程刷新并观察可见状态

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **正确性** | 先定义共享状态、不变量和 happens-before | 用压力测试、竞态测试和线程转储验证 |
| **吞吐** | 线程数不能突破 CPU、连接池和下游容量 | 观察排队时间而非只看完成量 |
| **延迟** | 区分锁等待、队列等待、I/O 等待和调度 | 记录 p95/p99 与超时、取消传播 |
| **故障隔离** | 任务必须有界、可取消、可拒绝 | 按依赖拆池，禁止无限队列与无限重试 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 单写多读状态可用 volatile，涉及多个变量一致性或复合操作时使用锁或原子类。
- 无锁并不天然更快，高竞争 CAS 自旋可能浪费 CPU。
- 并发正确性先用状态不变量描述，再选择同步原语。

### 上线前检查

- 队列、等待、重试和并发度全部有界。
- 中断、取消、超时沿调用链传播，finally 释放锁与资源。
- 按依赖隔离执行器，避免一个慢下游占满全部线程。
- 压测同时观察吞吐、排队、上下文切换、锁竞争和尾延迟。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 双重检查锁定缺少 volatile，可能发布未完成对象。
2. 用 volatile 修饰集合引用，却并发修改普通集合内部状态。
3. 忙等循环没有退避或阻塞机制，CPU 被打满。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“线程执行普通读写”一路检查到“读线程刷新并观察可见状态”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
