# 并发容器与原子类

> **先记住**：并发容器通过分段、CAS、写时复制或无锁队列等机制提供明确的线程安全语义；原子类适合单变量或可表达为 CAS 循环的状态更新。

---

## 1. 它在解决什么问题？

并发容器通过分段、CAS、写时复制或无锁队列等机制提供明确的线程安全语义；原子类适合单变量或可表达为 CAS 循环的状态更新。容器方法安全不代表多个方法组合后的业务操作原子。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### ConcurrentHashMap

读取通常不加全局锁，更新通过 CAS 与桶级同步完成；compute、merge 等方法可把单 key 的复合逻辑放进原子操作。

### CopyOnWrite 与队列

CopyOnWriteArrayList 用写时复制换取无锁快照遍历，适合读多写极少；BlockingQueue 同时承担缓冲和生产消费协调。

### CAS 与 ABA

CAS 比较旧值并条件更新，竞争失败重试；版本戳或不可复用节点可处理 ABA。LongAdder 通过分散热点提高高竞争计数吞吐，但读取不是瞬时原子快照。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```java
ConcurrentHashMap<String, LongAdder> counts = new ConcurrentHashMap<>();

void record(String key) {
    counts.computeIfAbsent(key, ignored -> new LongAdder()).increment();
}

long snapshot(String key) {
    LongAdder value = counts.get(key);
    return value == null ? 0 : value.sum();
}
```

### 对照着看

- **从哪里开始**：读取当前桶或槽位
- **关键状态变化**：冲突时锁定局部结构
- **怎样才算完成**：原子复合 API 返回一致结果

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **正确性** | 先定义共享状态、不变量和 happens-before | 用压力测试、竞态测试和线程转储验证 |
| **吞吐** | 线程数不能突破 CPU、连接池和下游容量 | 观察排队时间而非只看完成量 |
| **延迟** | 区分锁等待、队列等待、I/O 等待和调度 | 记录 p95/p99 与超时、取消传播 |
| **故障隔离** | 任务必须有界、可取消、可拒绝 | 按依赖拆池，禁止无限队列与无限重试 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 按访问模式选择容器，不能只看“线程安全”标签。
- compute 回调应短小且无外部阻塞，避免放大桶竞争。
- 跨多个 key 或多个容器的一致性仍需锁、事务或状态机。

### 上线前检查

- 队列、等待、重试和并发度全部有界。
- 中断、取消、超时沿调用链传播，finally 释放锁与资源。
- 按依赖隔离执行器，避免一个慢下游占满全部线程。
- 压测同时观察吞吐、排队、上下文切换、锁竞争和尾延迟。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 在 ConcurrentHashMap 上先 get 再 put，初始化被并发执行多次。
2. 写多场景误用 CopyOnWriteArrayList，分配和复制激增。
3. 把 LongAdder.sum 当作严格事务计数。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“读取当前桶或槽位”一路检查到“原子复合 API 返回一致结果”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
