# 线程池与任务调度

> **先记住**：线程池通过复用工作线程、队列和拒绝策略控制并发资源。

---

## 1. 它在解决什么问题？

线程池通过复用工作线程、队列和拒绝策略控制并发资源。核心不是背参数，而是根据任务 CPU/I/O 特征、下游容量和延迟目标设置有界队列、超时、隔离和监控，防止流量高峰转化为无限积压。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 执行流程

ThreadPoolExecutor 依次考虑核心线程、工作队列、最大线程和拒绝策略。无界队列会让 maximumPoolSize 基本失效，并把过载变成长延迟和内存风险。

### 容量估算

CPU 密集型并发接近可用核心数；I/O 任务可更高，但仍受连接池、外部限流和内存约束。应以 Little 定律、压测和下游预算校准。

### 调度与生命周期

ScheduledExecutorService 适合进程内调度，但不提供分布式唯一执行和持久化。服务关闭时要停止接收、等待在途任务并处理中断。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
    8, 32,
    30, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(500),
    Thread.ofPlatform().name("payment-", 0).factory(),
    new ThreadPoolExecutor.CallerRunsPolicy());

// 任务自身仍必须设置下游超时，队列也必须有等待时间指标。
Future<Result> future = pool.submit(() -> client.call(request));
Result result = future.get(800, TimeUnit.MILLISECONDS);
```

### 对照着看

- **从哪里开始**：任务提交
- **关键状态变化**：核心线程满后进入有界队列
- **怎样才算完成**：仍过载则执行拒绝策略

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **正确性** | 先定义共享状态、不变量和 happens-before | 用压力测试、竞态测试和线程转储验证 |
| **吞吐** | 线程数不能突破 CPU、连接池和下游容量 | 观察排队时间而非只看完成量 |
| **延迟** | 区分锁等待、队列等待、I/O 等待和调度 | 记录 p95/p99 与超时、取消传播 |
| **故障隔离** | 任务必须有界、可取消、可拒绝 | 按依赖拆池，禁止无限队列与无限重试 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 按业务和依赖隔离线程池，避免一个慢下游拖死全站。
- CallerRuns 可形成背压，但若调用线程是事件循环或关键入口会放大故障。
- 线程池指标至少包含活跃数、队列长度、等待时间、拒绝量和任务耗时。

### 上线前检查

- 队列、等待、重试和并发度全部有界。
- 中断、取消、超时沿调用链传播，finally 释放锁与资源。
- 按依赖隔离执行器，避免一个慢下游占满全部线程。
- 压测同时观察吞吐、排队、上下文切换、锁竞争和尾延迟。

---

## 7. 常见误区与排查

### 容易踩的坑

1. Executors.newFixedThreadPool 默认无界队列，流量高峰 OOM。
2. 任务阻塞且无超时，工作线程永久占用。
3. 多个线程池总线程数失控，栈内存和上下文切换过高。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“任务提交”一路检查到“仍过载则执行拒绝策略”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
