# 图形学、客户端架构与性能

> **优先级**：渲染与性能 P0，底层细节 P1/P2。回答要从“帧预算”开始，而不是只背渲染名词。

## 1. 一帧是怎样生成的

```text
输入/网络 → Gameplay 更新 → 动画/物理 → 可见性裁剪 → Draw Call/Render Pass
         → CPU 提交 → GPU 顶点/光栅/片元 → 后处理 → Present
```

CPU bound 的特征是主线程、脚本或提交线程满而 GPU 有余量；GPU bound 则是片元、带宽、阴影或后处理耗时。先用 Profiler、Frame Debugger、RenderDoc、GPU capture 确认瓶颈，再决定优化方向。

## 2. 渲染基础要会说清

- **坐标变换**：模型矩阵、视图矩阵、投影矩阵把顶点变到裁剪空间；透视除法后做视口变换。
- **光栅化**：三角形覆盖像素后插值顶点属性，再执行深度测试、模板测试和片元着色。
- **材质与 Shader**：纹理采样、分支、精度和带宽共同决定 GPU 成本；移动端要关注 overdraw 和纹理压缩。
- **渲染排序**：不透明物体通常前到后减少 overdraw，透明物体按后到前；排序还要服从材质状态切换和批处理。
- **现代管线**：URP/HDRP 或 UE 的渲染器会拆成多个 pass，阴影、反射、后处理和 UI 都会消耗独立预算。

## 3. 客户端架构

推荐用“模块化 + 数据驱动 + 明确生命周期”：

```text
输入层 → 用例/Gameplay 层 → 状态与配置 → 表现层（动画/UI/VFX）
                    ↘ 网络适配 / 存档 / 埋点
```

依赖倒置让 Gameplay 不直接依赖具体 UI 或网络实现；事件总线只传领域事件，不把它当全局变量。场景切换、热更新和登录流程要有状态机，异步任务要能取消并在回调前验证对象仍属于当前场景。

## 4. 性能检查清单

| 现象 | 优先查看 | 常见修复 |
|---|---|---|
| 主线程尖峰 | CPU Timeline、GC、脚本调用栈 | 批量更新、缓存引用、移到 Job |
| GPU 帧超时 | GPU markers、overdraw、带宽 | 降分辨率、合批、LOD、简化 Shader |
| 加载卡顿 | IO、解压、反序列化 | 异步分片、预热、资源分组 |
| 内存持续上涨 | Native/Managed/Asset 快照 | 释放订阅、卸载场景、检查缓存上限 |
| 联机抖动 | RTT、丢包、快照大小 | 插值、压缩、relevancy、限频 |

性能优化要有基线、目标机和回归场景；平均 FPS 不能替代 1% low、帧时间 P95 和峰值内存。

### 高频追问

#### Q1. Draw Call 越少越好吗？

不是。减少 Draw Call 可能增加 Shader 复杂度、纹理图集大小或 CPU 预处理成本。要看 CPU/GPU 谁是瓶颈，并结合材质切换、批处理成功率、overdraw 和目标平台验证。

#### Q2. 如何定位一次偶发卡顿？

先记录卡顿帧的 CPU/GPU/IO/GC 时间线和资源加载事件，区分同步 IO、编译 Shader、GC、锁竞争还是过度提交；再在同一设备、同一构建和可复现输入下做最小复现，而不是只看平均帧率。
