# 客户端架构、设计模式与 Gameplay

> **优先级**：P0/P1。重点是模式解决什么变化，而不是背名称。

## 1. 常用模式

状态机管理角色、匹配、加载等互斥流程；命令模式支持输入缓冲、撤销和回放；观察者/事件用于低耦合通知，但必须托管订阅生命周期；对象池处理高频短命实体；策略模式替换移动、瞄准或寻路算法。

## 2. ECS 与组件化

组件存数据，系统按查询批量处理，实体只提供身份。ECS 的优势是数据局部性和并行调度，代价是调试、引用和跨系统顺序更复杂。传统 MonoBehaviour/Actor 组件适合内容驱动和编辑器工作流，通常采用混合架构而不是全量重写。

## 3. Gameplay 状态

把权威规则、预测状态、表现状态和 UI 状态分开；状态迁移要有进入/退出动作、取消和错误恢复。服务定位、场景切换、网络重连等跨系统流程使用显式状态机，避免几十个布尔变量互相冲突。

### 高频追问

#### Q1. 全局事件总线有什么风险？
依赖不可见、顺序不明确、订阅泄漏和调试困难。应限制事件范围、定义 payload 和线程边界，并让生命周期 owner 自动解绑。

#### Q2. 什么时候不应该使用 ECS？
对象数量少、行为高度异构、强依赖编辑器和层级关系时，ECS 的迁移和调试成本可能超过收益。应以数据规模和热点测量决定。
