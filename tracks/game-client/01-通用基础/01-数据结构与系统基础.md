# 数据结构、操作系统与内存

> **优先级**：基础 P0，细节 P1。游戏客户端的“八股”不能只背 API，要能把数据结构、线程、缓存和帧时间联系到一起。

## 1. 面试先建立这条主链路

```text
输入 / 网络事件 → 游戏状态 → 组件系统 → 渲染提交 → GPU 执行 → 下一帧
          └── 队列、句柄、对象生命周期和线程同步贯穿始终 ──┘
```

回答任何引擎问题时，先说数据规模和更新频率，再说容器、线程模型与内存代价。

## 2. 数据结构怎么选

| 场景 | 首选 | 追问时要补充 |
|---|---|---|
| 连续遍历、批量更新 | 数组 / `vector` / `NativeArray` | 缓存局部性、扩容和失效引用 |
| 稳定对象身份 | 稠密数组 + ID/Generation | 删除后句柄复用要防 ABA |
| 频繁按 key 查找 | 哈希表 | 哈希冲突、装箱、迭代器失效 |
| 定时器、优先级任务 | 小根堆 / 时间轮 | tick 粒度和取消任务成本 |
| 空间查询 | 四叉树、八叉树、BVH、网格 | 更新成本与查询半径 |
| 帧间消息 | 环形队列 / SPSC 队列 | 生产者、消费者和背压 |

游戏循环里通常更适合“数据导向”：把同类组件放在连续内存中批量处理，而不是每个对象都拥有一棵深继承树。删除实体时可以 swap-remove，但必须用稳定 ID 或反向索引修正引用。

## 3. OS、线程与内存

### 虚拟内存与缓存

进程看到的是虚拟地址，页表把它映射到物理页；缺页会触发昂贵的内核路径。CPU cache 以 cache line（常见 64B）搬运数据，所以遍历连续数组通常比随机访问链表更快。多线程写相邻字段可能产生伪共享，即使逻辑上没有竞争也会让 cache line 反复失效。

### 游戏线程模型

- **主线程**：对象生命周期、脚本回调、UI 与大多数引擎 API 必须在这里执行。
- **渲染线程**：把渲染命令整理并提交给图形 API；不要在主线程和渲染线程之间传递裸指针。
- **Job/Worker**：执行可切分、无共享写入的数据任务，使用依赖图或 job fence 回收结果。
- **IO/网络线程**：只做解码、读写和协议解析，结果通过消息队列回到主线程。

同步原语要按问题选择：原子操作解决单变量的原子性，mutex 保护临界区，condition variable 等待条件，读写锁适合读多写少。不要用“加锁”掩盖长耗时 IO，也不要在锁内调用未知脚本。

## 4. 常见内存与生命周期坑

1. C++ 中 `shared_ptr` 环引用导致泄漏；引擎对象通常应该由引擎 GC、Owner 或显式释放管理。
2. 对象池只重置显示状态，遗漏事件订阅、协程和定时器，复用后会出现“幽灵逻辑”。
3. C# 闭包、LINQ、字符串拼接和装箱在每帧分配，最终表现为 GC spike 而不是平均帧率下降。
4. 异步回调捕获已经销毁的场景对象；回调必须绑定取消令牌、generation 或弱引用。

## 5. 面试答题模板

> 先说明对象数量、访问模式和线程边界；再给出容器或分配策略；最后说最坏复杂度、缓存/GC 代价和如何用 Profiler 验证。若资源或任务可取消，要补充生命周期和异常路径。

### 高频追问

#### Q1. 为什么游戏开发更常用连续数组而不是链表？

连续数组具有更好的空间局部性和预取效果，批量遍历时能减少 cache miss；链表虽然插入节点便宜，但节点分散、指针占用额外内存。只有已持有节点且中间插删明显占主导时，链表才可能有优势。

#### Q2. 对象池一定能提升性能吗？

不一定。它能减少频繁分配和 GC，但会保留峰值内存，并增加重置状态、容量上限和并发访问的复杂度。应在分配热点被 Profiler 证实后使用，并覆盖“取出、归还、场景卸载、取消回调”四条路径。
