# Unity 资源、UI、动画物理与 Gameplay

> **优先级**：P0/P1。重点是资源引用、异步加载和 Gameplay 状态之间的边界。

## 1. 资源与场景

Resources 目录会把资源打进包并支持运行时查找，但依赖难追踪、包体和内存不可控；AssetBundle/Addressables 用显式分组、依赖管理和异步加载改善可维护性。释放资源要考虑引用计数、实例仍在使用、场景切换和缓存上限；“卸载了 bundle 但材质还在用”会造成隐性引用或粉红材质。

序列化要区分运行时状态和设计数据。`ScriptableObject` 适合共享配置和编辑器资产，不能把玩家存档直接写回只读资源。版本升级要有迁移策略，网络或热更新配置要校验 schema 与默认值。

## 2. UI 与输入

UI 层负责展示与交互，不应直接修改战斗核心状态；通过 ViewModel、命令或领域事件连接。Canvas 拆分、Raycast Target、Layout rebuild 和频繁 SetActive 都可能产生 CPU 峰值。滚动列表使用虚拟化，字体、图集和材质要按平台打包。

输入系统应将设备事件映射成动作，再交给 Gameplay；不要让每个按钮直接读取键盘。切换 UI 模式时处理输入焦点、暂停规则和手柄导航。

## 3. 动画、物理与 AI

动画状态机适合表现层，战斗状态应有独立的可测试状态机；Root Motion、Character Controller 和 Rigidbody 的移动权责必须唯一。物理更新使用固定步长，视觉插值放渲染帧。碰撞层、触发器和连续碰撞检测要按对象速度与重要性配置。

AI 通常拆成感知、决策、执行三段：感知缓存视野结果，行为树/状态树做决策，执行层调用移动和技能接口。导航查询和群体避障可能很贵，按距离、可见性和 tick 频率分级。

## 4. 热更新与 DOTS

热更新要区分代码、配置和资源：代码版本、序列化数据与资源 catalog 必须可回滚；加载失败要有旧版本兜底。DOTS/ECS 更适合大量同构实体和批量计算，不是把所有 MonoBehaviour 一次性重写；迁移时先找出数据布局、系统顺序和主线程 API 边界。

### 高频追问

#### Q1. Addressables 释放后为什么资源还不降？

可能仍有实例、材质、Sprite、依赖 bundle 或静态缓存持有引用；释放句柄只减少一层引用。用内存快照和依赖图确认真正的 owner，再决定卸载时机，不要用强制 GC 掩盖引用泄漏。

#### Q2. UI 和 Gameplay 为什么要解耦？

UI 生命周期、场景和分辨率变化频繁，而战斗状态需要稳定、可测试、可网络同步。通过命令/事件或 ViewModel 连接可以替换 UI、支持回放和自动化测试，也避免按钮回调绕过权限与服务器校验。
