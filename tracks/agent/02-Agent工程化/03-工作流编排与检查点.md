# 工作流编排与检查点

> **一句话定位**：工作流编排把 Agent 应用拆成模型、工具、规则、审批和数据处理节点，以图或状态机明确控制路径。

---

## 1. 先给结论

工作流编排把 Agent 应用拆成模型、工具、规则、审批和数据处理节点，以图或状态机明确控制路径。检查点在可靠边界持久化输入、输出和版本，使长任务能够暂停、恢复、重试和回放；关键是确定性控制外层流程，只在确有需要的节点开放模型决策。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 图与状态机

节点负责单一职责，边根据结构化结果选择下一步；循环必须有进度条件和上限。执行状态应与业务状态分离，避免模型自由文本直接决定高风险跳转。

### 检查点语义

检查点保存状态快照、已完成节点、代码/提示版本和未决动作。应在副作用前记录意图、执行后原子提交结果，恢复时通过幂等键或外部查询解决不确定状态。

### 重试与补偿

网络抖动可指数退避重试，参数错误应修正或失败，业务拒绝通常不可重试。跨系统写操作无法原子提交时，使用 Saga 式补偿并保留人工处理通道。

## 3. 工作流程与关键路径

```text
[编排器读取当前状态]
    │
    ▼
[选择可运行节点]
    │
    ▼
[节点执行并产生事件]
    │
    ▼
[原子保存输出和检查点]
    │
    ▼
[失败后从安全边界恢复或补偿]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`编排器读取当前状态` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`选择可运行节点` 与 `节点执行并产生事件` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`失败后从安全边界恢复或补偿` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
def execute_node(run_id, node, state):
    checkpoint = store.load(run_id)
    if checkpoint.completed(node.id):
        return checkpoint.output(node.id)

    output = node.run(state, idempotency_key=f"{run_id}:{node.id}")
    store.commit_atomically(
        run_id=run_id,
        expected_version=checkpoint.version,
        event={"node": node.id, "output": output},
    )
    return output
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `编排器读取当前状态` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `节点执行并产生事件` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `失败后从安全边界恢复或补偿` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **协议与边界** | 模型只提出意图，执行器和策略层掌握权限 | Schema、超时、幂等和审计在协议边界统一 |
| **确定性** | 关键合规节点由工作流控制 | Agent 只在受限工具集和预算内选择 |
| **恢复** | 副作用前写意图，完成后写结果 | 检查点与外部幂等键共同支持接管 |
| **评测** | 离线回归、线上观测和人工抽检闭环 | 版本化数据集并按失败类型切片 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- DAG 易理解但不适合天然循环，通用图灵活却更难静态验证。
- 每节点检查点恢复精细但写放大明显，可按高成本或副作用边界保存。
- 工作流版本升级要考虑运行中实例，通常固定旧版本直到结束或显式迁移。

### 6.1 落地检查表

- 工具、提示、工作流、模型策略和评测集全部版本化。
- 副作用前写意图与幂等键，节点完成后原子保存检查点。
- 每个 run 保留可关联 Trace，但日志不记录密钥和私有推理。
- 发布门禁同时看任务成功、安全违规、成本和尾延迟。

## 7. 常见故障

1. 节点失败后从头重跑，重复发送邮件或创建工单。
2. 恢复时使用新提示和新 schema，旧状态无法解释。
3. 补偿动作也失败却没有告警和人工队列。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `编排器读取当前状态` 逐步检查到 `失败后从安全边界恢复或补偿`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**节点失败后从头重跑，重复发送邮件或创建工单。**
