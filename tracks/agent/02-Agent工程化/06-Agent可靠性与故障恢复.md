# Agent 可靠性与故障恢复

> **一句话定位**：Agent 可靠性依赖可分类错误、有限重试、幂等副作用、超时与取消传播、持久化检查点和明确降级，而不是提示模型永不失败。

---

## 1. 先给结论

Agent 可靠性依赖可分类错误、有限重试、幂等副作用、超时与取消传播、持久化检查点和明确降级，而不是提示模型永不失败。系统应区分模型、工具、编排、数据和策略故障，恢复时从最小安全步骤继续，并用故障注入验证真实行为。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 错误分类

超时、限流和瞬时网络错误可有限重试；认证失败、schema 错误和业务拒绝应修复或终止；内容安全拦截需要安全降级。统一错误码要保留原始上下文但避免泄露敏感信息。

### 幂等与不确定结果

写工具携带业务幂等键，服务端记录请求结果。若调用超时但可能已成功，先查询外部状态再重试，不能把客户端未收到响应等同于未执行。

### 降级与恢复

可切换备用模型、只读模式、确定性工作流或人工处理。取消信号向子任务和工具传播，恢复扫描处理过期租约，死信队列保留无法自动解决的任务。

## 3. 工作流程与关键路径

```text
[步骤写入意图与幂等键]
    │
    ▼
[执行外部副作用]
    │
    ▼
[保存结果或不确定状态]
    │
    ▼
[重试前先对账外部系统]
    │
    ▼
[继续、补偿或升级人工]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`步骤写入意图与幂等键` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`执行外部副作用` 与 `保存结果或不确定状态` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`继续、补偿或升级人工` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
intent = store.begin_step(run_id, step_id, idempotency_key)
try:
    result = external_api.call(payload, idempotency_key=idempotency_key)
    store.complete_step(intent.id, result)
except TimeoutError:
    remote = external_api.lookup_by_idempotency_key(idempotency_key)
    if remote.succeeded:
        store.complete_step(intent.id, remote.result)
    else:
        scheduler.retry(intent.id, backoff="exponential+jitter", max_attempts=3)
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `步骤写入意图与幂等键` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `保存结果或不确定状态` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `继续、补偿或升级人工` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **协议与边界** | 模型只提出意图，执行器和策略层掌握权限 | Schema、超时、幂等和审计在协议边界统一 |
| **确定性** | 关键合规节点由工作流控制 | Agent 只在受限工具集和预算内选择 |
| **恢复** | 副作用前写意图，完成后写结果 | 检查点与外部幂等键共同支持接管 |
| **评测** | 离线回归、线上观测和人工抽检闭环 | 版本化数据集并按失败类型切片 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 备用模型能力不同，切换前要验证工具调用、上下文长度和安全策略兼容性。
- 重试提高成功率也会放大下游压力，应使用抖动退避和全链路重试预算。
- 降级答案必须明确能力受限，不能静默返回看似完整的错误结果。

### 6.1 落地检查表

- 工具、提示、工作流、模型策略和评测集全部版本化。
- 副作用前写意图与幂等键，节点完成后原子保存检查点。
- 每个 run 保留可关联 Trace，但日志不记录密钥和私有推理。
- 发布门禁同时看任务成功、安全违规、成本和尾延迟。

## 7. 常见故障

1. 模型层、SDK 和网关各自重试，形成指数级请求风暴。
2. 取消主任务后子 Agent 和浏览器仍继续运行并产生费用。
3. 工具超时后重复创建相同资源，没有幂等或对账。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `步骤写入意图与幂等键` 逐步检查到 `继续、补偿或升级人工`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**模型层、SDK 和网关各自重试，形成指数级请求风暴。**
