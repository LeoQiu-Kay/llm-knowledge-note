# 多 Agent 协作与路由

> **先记住**：多 Agent 系统通过路由器、主管或共享任务队列，把工作交给具有不同工具、权限或上下文的角色。

---

## 1. 它在解决什么问题？

多 Agent 系统通过路由器、主管或共享任务队列，把工作交给具有不同工具、权限或上下文的角色。它适合可并行、可独立验证的专业任务，不应仅为模拟团队而增加角色；生产重点是契约、上下文隔离、冲突合并、预算和端到端责任归属。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 协作模式

常见模式包括主管分派、专家路由、并行扇出汇总和事件驱动接力。每个 Agent 应声明输入输出 schema、可用工具、权限和完成条件，避免靠含糊对话协作。

### 路由决策

路由可由规则、分类模型或主模型完成。高频稳定请求优先规则，开放问题再使用模型；需要置信度阈值、默认处理器和错误路由回退。

### 合并与冲突

并行结果应保留证据与置信度，由确定性聚合器或专门验证节点处理重复、矛盾和缺失。共享可变状态使用版本或事务控制，不能让多个 Agent 覆盖彼此结果。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```python
route = router.classify(
    task,
    candidates=["research", "coding", "data"],
    constraints={"max_agents": 3, "max_cost": 2.0},
)
results = parallel_map(
    lambda role: agents[role].run(task, context=minimal_context(role)),
    route.roles,
)
checked = [verifier.validate(role, result) for role, result in results]
return coordinator.merge(checked, conflict_policy="evidence_wins")
```

### 对照着看

- **从哪里开始**：入口分类任务与风险
- **关键状态变化**：共享最小必要上下文
- **怎样才算完成**：统一输出、成本和审计

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **协议与边界** | 模型只提出意图，执行器和策略层掌握权限 | Schema、超时、幂等和审计在协议边界统一 |
| **确定性** | 关键合规节点由工作流控制 | Agent 只在受限工具集和预算内选择 |
| **恢复** | 副作用前写意图，完成后写结果 | 检查点与外部幂等键共同支持接管 |
| **评测** | 离线回归、线上观测和人工抽检闭环 | 版本化数据集并按失败类型切片 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 增加 Agent 可能提升专业性和并行度，也会成倍增加调用成本与故障路径。
- 角色提示应聚焦能力边界，不要依赖拟人化人格保证质量。
- 跨 Agent 传递摘要可控成本，但重要原始证据必须可追溯。

### 上线前检查

- 工具、提示、工作流、模型策略和评测集全部版本化。
- 副作用前写意图与幂等键，节点完成后原子保存检查点。
- 每个 run 保留可关联 Trace，但日志不记录密钥和私有推理。
- 发布门禁同时看任务成功、安全违规、成本和尾延迟。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 两个 Agent 相互转交任务形成路由循环。
2. 多个 Agent 使用不同事实版本，最终答案内部矛盾。
3. 主管只看自然语言结论，无法验证专家是否真正完成任务。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“入口分类任务与风险”一路检查到“统一输出、成本和审计”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
