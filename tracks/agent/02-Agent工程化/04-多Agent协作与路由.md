# 多 Agent 协作与路由

> **一句话定位**：多 Agent 系统通过路由器、主管或共享任务队列，把工作交给具有不同工具、权限或上下文的角色。

---

## 1. 先给结论

多 Agent 系统通过路由器、主管或共享任务队列，把工作交给具有不同工具、权限或上下文的角色。它适合可并行、可独立验证的专业任务，不应仅为模拟团队而增加角色；生产重点是契约、上下文隔离、冲突合并、预算和端到端责任归属。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### 协作模式

常见模式包括主管分派、专家路由、并行扇出汇总和事件驱动接力。每个 Agent 应声明输入输出 schema、可用工具、权限和完成条件，避免靠含糊对话协作。

### 路由决策

路由可由规则、分类模型或主模型完成。高频稳定请求优先规则，开放问题再使用模型；需要置信度阈值、默认处理器和错误路由回退。

### 合并与冲突

并行结果应保留证据与置信度，由确定性聚合器或专门验证节点处理重复、矛盾和缺失。共享可变状态使用版本或事务控制，不能让多个 Agent 覆盖彼此结果。

## 3. 工作流程与关键路径

```text
[入口分类任务与风险]
    │
    ▼
[路由到专长 Agent]
    │
    ▼
[共享最小必要上下文]
    │
    ▼
[协调器合并与冲突消解]
    │
    ▼
[统一输出、成本和审计]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`入口分类任务与风险` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`路由到专长 Agent` 与 `共享最小必要上下文` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`统一输出、成本和审计` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
route = router.classify(
    task,
    candidates=["research", "coding", "data"],
    constraints={"max_agents": 3, "max_cost": 2.0},
)
results = parallel_map(
    lambda role: agents[role].run(task, context=minimal_context(role)),
    route.roles,
)
checked = [verifier.validate(role, result) for role, result in results]
return coordinator.merge(checked, conflict_policy="evidence_wins")
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `入口分类任务与风险` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `共享最小必要上下文` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `统一输出、成本和审计` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **协议与边界** | 模型只提出意图，执行器和策略层掌握权限 | Schema、超时、幂等和审计在协议边界统一 |
| **确定性** | 关键合规节点由工作流控制 | Agent 只在受限工具集和预算内选择 |
| **恢复** | 副作用前写意图，完成后写结果 | 检查点与外部幂等键共同支持接管 |
| **评测** | 离线回归、线上观测和人工抽检闭环 | 版本化数据集并按失败类型切片 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 增加 Agent 可能提升专业性和并行度，也会成倍增加调用成本与故障路径。
- 角色提示应聚焦能力边界，不要依赖拟人化人格保证质量。
- 跨 Agent 传递摘要可控成本，但重要原始证据必须可追溯。

### 6.1 落地检查表

- 工具、提示、工作流、模型策略和评测集全部版本化。
- 副作用前写意图与幂等键，节点完成后原子保存检查点。
- 每个 run 保留可关联 Trace，但日志不记录密钥和私有推理。
- 发布门禁同时看任务成功、安全违规、成本和尾延迟。

---

## 7. 常见故障

1. 两个 Agent 相互转交任务形成路由循环。
2. 多个 Agent 使用不同事实版本，最终答案内部矛盾。
3. 主管只看自然语言结论，无法验证专家是否真正完成任务。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `入口分类任务与风险` 逐步检查到 `统一输出、成本和审计`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**两个 Agent 相互转交任务形成路由循环。**
