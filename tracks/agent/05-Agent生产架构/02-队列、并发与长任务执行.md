# 队列、并发与长任务执行

> **一句话定位**：长时间 Agent 任务应通过持久队列和 worker 执行，使用租约、心跳、幂等和检查点实现至少一次交付下的正确处理。

---

## 1. 先给结论

长时间 Agent 任务应通过持久队列和 worker 执行，使用租约、心跳、幂等和检查点实现至少一次交付下的正确处理。并发控制不仅限制 worker 数，还要限制每租户、模型、工具和下游资源；任务取消、优先级、公平性和死信处理是生产必需能力。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 投递与租约

队列通常提供至少一次投递，worker 领取任务后持有可续租 lease 并定期心跳。租约到期允许其他 worker 接管，所以每个 step 必须幂等或能核对外部结果。

### 并发与背压

按租户配额、模型 RPM/TPM、工具容量和数据库连接设置分层 semaphore。队列深度和预计等待时间触发背压，入口可拒绝、降级或转异步通知。

### 长任务控制

任务支持暂停、取消、超时、优先级和检查点；取消信号传播到子任务与工具。失败超过阈值进入死信队列，保留状态、版本和人工重放入口。

## 3. 工作流程与关键路径

```text
[请求转换为持久任务]
    │
    ▼
[队列按租户和优先级调度]
    │
    ▼
[Worker 领取带租约的任务]
    │
    ▼
[心跳、检查点与取消持续生效]
    │
    ▼
[完成后原子写结果并确认消息]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`请求转换为持久任务` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`队列按租户和优先级调度` 与 `Worker 领取带租约的任务` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`完成后原子写结果并确认消息` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
task = queue.claim(worker_id, lease_seconds=30)
while not task.done:
    cancellation.raise_if_requested(task.run_id)
    result = execute_next_step(task)
    checkpoints.save(task.run_id, result, expected_version=task.version)
    queue.renew_lease(task.id, worker_id, lease_seconds=30)
queue.ack(task.id, worker_id)

# Worker 崩溃后租约到期，其他 Worker 从最后检查点接管。
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `请求转换为持久任务` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `Worker 领取带租约的任务` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `完成后原子写结果并确认消息` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **状态持久化** | 会话展示状态与任务执行状态分离 | 断线、重启和 Worker 接管都不丢 run |
| **预算** | 成本、时间、步骤和并行度同时设上限 | 关注每个成功任务成本而非单次 token |
| **路由** | 模型、工具和工作流作为一个版本化 bundle | 降级必须保持安全与输出契约 |
| **观测** | run / step / span / 业务键可关联 | 质量、安全、成本和延迟一起告警 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 严格 FIFO 简单却可能让大任务阻塞小任务，可使用优先级和加权公平队列。
- 预取提高吞吐，但 worker 崩溃会延长任务不可见时间。
- 并行工具调用降低延迟，也可能击穿共享下游，需要总量预算。

### 6.1 落地检查表

- API 请求与长任务解耦，队列、租约、心跳和取消均持久化。
- run、step、模型、工具和业务结果使用同一 trace 关联。
- 路由和缓存以质量门槛为前提，不能用便宜结果静默降级。
- 灰度发布 bundle 化，异常能自动停止流量并整体回滚。

## 7. 常见故障

1. worker 执行时间超过可见性超时，同一任务被重复消费。
2. 高消费租户占满队列，其他租户长期饥饿。
3. 取消只更新数据库，正在运行的浏览器和模型请求未停止。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `请求转换为持久任务` 逐步检查到 `完成后原子写结果并确认消息`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**worker 执行时间超过可见性超时，同一任务被重复消费。**
