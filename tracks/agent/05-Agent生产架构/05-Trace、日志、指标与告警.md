# Trace、日志、指标与告警

> **一句话定位**：Agent 可观测性要把一次 run 下的模型调用、检索、工具、审批、子 Agent 和状态转移串成 Trace，并用结构化日志解释事件、指标监控趋势。

---

## 1. 先给结论

Agent 可观测性要把一次 run 下的模型调用、检索、工具、审批、子 Agent 和状态转移串成 Trace，并用结构化日志解释事件、指标监控趋势。除延迟和错误率，还需跟踪任务成功、循环、拒答、工具副作用、token 与成本；语义约定仍在演进，内部 schema 应版本化。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### Trace 模型

run 作为根 span，model、tool、retrieval、approval 和 workflow node 作为子 span，记录状态、版本、耗时、token 和关联 ID。跨队列传播 trace context，异步恢复仍能连接原任务。

### 日志与指标

日志保存结构化事件和错误上下文，指标聚合成功率、P95/P99、队列、循环次数、工具错误、缓存命中和单位成功成本。高基数字段进入 trace/log，不直接作为指标 label。

### 质量与告警

建立面向用户结果的 SLI，如任务完成率、正确引用率和人工接管率。告警结合错误预算与异常基线，严重写操作、越权拒绝和数据外发单独设安全告警。

## 3. 工作流程与关键路径

```text
[入口创建 trace_id]
    │
    ▼
[模型、检索和工具各生成 span]
    │
    ▼
[结构化日志关联 run / step]
    │
    ▼
[指标聚合成功率、延迟与成本]
    │
    ▼
[告警链接到完整执行证据]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`入口创建 trace_id` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`模型、检索和工具各生成 span` 与 `结构化日志关联 run / step` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`告警链接到完整执行证据` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
with tracer.start_as_current_span("agent.step") as span:
    span.set_attributes({
        "agent.run_id": run_id,
        "agent.step_id": step_id,
        "llm.model": model,
        "tool.name": tool_name,
    })
    result = execute_step()
    metrics.histogram("agent.step.duration").record(result.elapsed)
    metrics.counter("agent.tool.calls").add(1, {"tool": tool_name})
    logger.info("step_completed", run_id=run_id, step_id=step_id)
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `入口创建 trace_id` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `结构化日志关联 run / step` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `告警链接到完整执行证据` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **状态持久化** | 会话展示状态与任务执行状态分离 | 断线、重启和 Worker 接管都不丢 run |
| **预算** | 成本、时间、步骤和并行度同时设上限 | 关注每个成功任务成本而非单次 token |
| **路由** | 模型、工具和工作流作为一个版本化 bundle | 降级必须保持安全与输出契约 |
| **观测** | run / step / span / 业务键可关联 | 质量、安全、成本和延迟一起告警 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 保存完整提示便于调试但风险高，生产默认脱敏、采样和分级访问。
- 全量 trace 成本高，可对错误、高价值任务和异常行为提高采样率。
- 标准语义便于跨平台，当前 GenAI Agent Spans 仍在开发阶段，内部适配层要隔离变化。

### 6.1 落地检查表

- API 请求与长任务解耦，队列、租约、心跳和取消均持久化。
- run、step、模型、工具和业务结果使用同一 trace 关联。
- 路由和缓存以质量门槛为前提，不能用便宜结果静默降级。
- 灰度发布 bundle 化，异常能自动停止流量并整体回滚。

---

## 7. 常见故障

1. 只记录最终答案，无法定位具体工具和证据。
2. 模型名、用户 ID 等高基数字段作为指标标签导致时序库膨胀。
3. 异步 worker 未传播 trace context，长任务链路断裂。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `入口创建 trace_id` 逐步检查到 `告警链接到完整执行证据`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**只记录最终答案，无法定位具体工具和证据。**
