# 成本预算与延迟优化

> **先记住**：Agent 成本和延迟来自多轮模型、长上下文、检索、工具、重排和并行子任务。

---

## 1. 它在解决什么问题？

Agent 成本和延迟来自多轮模型、长上下文、检索、工具、重排和并行子任务。优化应先建立每个 run/step 的 token、费用和时间分解，再通过缩短关键路径、选择合适模型、控制循环、压缩上下文、并行独立 I/O 和缓存稳定结果降低单位成功任务成本。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 成本归因

记录输入/输出 token、缓存 token、模型单价、工具 API、搜索、沙箱和人工成本，并关联租户、功能和任务成功。关注 cost per successful task，而不是只看单次调用价格。

### 延迟分解

区分排队、首 token、生成、工具、检索和后处理时间，用关键路径而非各步骤总和判断优化点。流式响应改善感知延迟，后台任务可先返回进度和可用的阶段性产物。

### 预算控制

为 run 设置 token、费用、墙钟时间、步骤和并行度上限，剩余预算影响后续路由。接近上限时缩小搜索、用小模型总结、请求澄清或安全终止。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```python
budget = RunBudget(max_cost_usd=1.50, max_wall_seconds=45, max_steps=10)
with telemetry.run(run_id) as trace:
    for step in plan:
        budget.reserve(step.estimated_cost, step.timeout)
        result = execute(step, deadline=budget.deadline)
        budget.charge(result.usage.cost, result.elapsed)
        trace.record(step.id, result.usage, result.elapsed)
        if budget.near_limit():
            plan = shrink_scope(plan, preserve_required_outputs=True)
```

### 对照着看

- **从哪里开始**：为 run 分配费用与时间预算
- **关键状态变化**：并行独立 I/O
- **怎样才算完成**：接近预算时缩小范围或安全终止

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **状态持久化** | 会话展示状态与任务执行状态分离 | 断线、重启和 Worker 接管都不丢 run |
| **预算** | 成本、时间、步骤和并行度同时设上限 | 关注每个成功任务成本而非单次 token |
| **路由** | 模型、工具和工作流作为一个版本化 bundle | 降级必须保持安全与输出契约 |
| **观测** | run / step / span / 业务键可关联 | 质量、安全、成本和延迟一起告警 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 并行可降墙钟时间，但会增加无用分支和峰值下游负载。
- 压缩上下文节约费用，也可能丢失约束，需用质量回归守门。
- 更便宜模型需比较任务成功率和人工返工，而非仅比较每 token 价格。

### 上线前检查

- API 请求与长任务解耦，队列、租约、心跳和取消均持久化。
- run、step、模型、工具和业务结果使用同一 trace 关联。
- 路由和缓存以质量门槛为前提，不能用便宜结果静默降级。
- 灰度发布 bundle 化，异常能自动停止流量并整体回滚。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 只设置最大轮数，单轮可产生超长输出和昂贵工具调用。
2. 所有子查询并行启动，即使早期结果已经足够。
3. 成本报表无法关联到功能和成功结果，无法做产品决策。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“为 run 分配费用与时间预算”一路检查到“接近预算时缩小范围或安全终止”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
