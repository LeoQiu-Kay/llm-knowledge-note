# 成本预算与延迟优化

> **一句话定位**：Agent 成本和延迟来自多轮模型、长上下文、检索、工具、重排和并行子任务。

---

## 1. 先给结论

Agent 成本和延迟来自多轮模型、长上下文、检索、工具、重排和并行子任务。优化应先建立每个 run/step 的 token、费用和时间分解，再通过缩短关键路径、选择合适模型、控制循环、压缩上下文、并行独立 I/O 和缓存稳定结果降低单位成功任务成本。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 成本归因

记录输入/输出 token、缓存 token、模型单价、工具 API、搜索、沙箱和人工成本，并关联租户、功能和任务成功。关注 cost per successful task，而不是只看单次调用价格。

### 延迟分解

区分排队、首 token、生成、工具、检索和后处理时间，用关键路径而非各步骤总和判断优化点。流式响应改善感知延迟，后台任务可先返回进度和可用的阶段性产物。

### 预算控制

为 run 设置 token、费用、墙钟时间、步骤和并行度上限，剩余预算影响后续路由。接近上限时缩小搜索、用小模型总结、请求澄清或安全终止。

## 3. 工作流程与关键路径

```text
[为 run 分配费用与时间预算]
    │
    ▼
[记录每一步 token 和耗时]
    │
    ▼
[并行独立 I/O]
    │
    ▼
[压缩上下文并动态路由模型]
    │
    ▼
[接近预算时缩小范围或安全终止]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`为 run 分配费用与时间预算` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`记录每一步 token 和耗时` 与 `并行独立 I/O` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`接近预算时缩小范围或安全终止` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
budget = RunBudget(max_cost_usd=1.50, max_wall_seconds=45, max_steps=10)
with telemetry.run(run_id) as trace:
    for step in plan:
        budget.reserve(step.estimated_cost, step.timeout)
        result = execute(step, deadline=budget.deadline)
        budget.charge(result.usage.cost, result.elapsed)
        trace.record(step.id, result.usage, result.elapsed)
        if budget.near_limit():
            plan = shrink_scope(plan, preserve_required_outputs=True)
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `为 run 分配费用与时间预算` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `并行独立 I/O` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `接近预算时缩小范围或安全终止` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **状态持久化** | 会话展示状态与任务执行状态分离 | 断线、重启和 Worker 接管都不丢 run |
| **预算** | 成本、时间、步骤和并行度同时设上限 | 关注每个成功任务成本而非单次 token |
| **路由** | 模型、工具和工作流作为一个版本化 bundle | 降级必须保持安全与输出契约 |
| **观测** | run / step / span / 业务键可关联 | 质量、安全、成本和延迟一起告警 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 并行可降墙钟时间，但会增加无用分支和峰值下游负载。
- 压缩上下文节约费用，也可能丢失约束，需用质量回归守门。
- 更便宜模型需比较任务成功率和人工返工，而非仅比较每 token 价格。

### 6.1 落地检查表

- API 请求与长任务解耦，队列、租约、心跳和取消均持久化。
- run、step、模型、工具和业务结果使用同一 trace 关联。
- 路由和缓存以质量门槛为前提，不能用便宜结果静默降级。
- 灰度发布 bundle 化，异常能自动停止流量并整体回滚。

## 7. 常见故障

1. 只设置最大轮数，单轮可产生超长输出和昂贵工具调用。
2. 所有子查询并行启动，即使早期结果已经足够。
3. 成本报表无法关联到功能和成功结果，无法做产品决策。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `为 run 分配费用与时间预算` 逐步检查到 `接近预算时缩小范围或安全终止`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**只设置最大轮数，单轮可产生超长输出和昂贵工具调用。**
