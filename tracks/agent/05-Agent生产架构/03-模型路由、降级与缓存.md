# 模型路由、降级与缓存

> **一句话定位**：模型网关根据任务能力、风险、上下文长度、延迟、成本和区域选择模型，并统一处理配额、重试、降级与缓存。

---

## 1. 先给结论

模型网关根据任务能力、风险、上下文长度、延迟、成本和区域选择模型，并统一处理配额、重试、降级与缓存。路由必须基于评测而非模型名印象；备用模型在工具 schema、安全策略和输出格式上需要兼容验证，缓存则只适用于输入稳定且安全上下文完整的场景。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 能力路由

先用规则识别是否需要视觉、长上下文、工具调用或高推理能力，再结合质量门槛和负载选模型。路由版本进入 trace，并保留强制指定与灰度实验能力。

### 故障降级

区分供应商故障、限流、内容拦截和模型能力不足。降级链设置总超时与重试预算；替代模型不满足安全或 schema 要求时，应受控失败而不是强行切换。

### 缓存设计

精确缓存适合确定性分类和嵌入，相似度缓存需防止语义误命中。缓存键包含模型、提示、工具、租户、权限和数据版本，敏感输出加密并设置短 TTL。

## 3. 工作流程与关键路径

```text
[提取任务难度、风险与模态]
    │
    ▼
[路由器选择模型]
    │
    ▼
[失败或预算不足时受控降级]
    │
    ▼
[稳定中间结果按语义缓存]
    │
    ▼
[质量监控反馈更新策略]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`提取任务难度、风险与模态` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`路由器选择模型` 与 `失败或预算不足时受控降级` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`质量监控反馈更新策略` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
route = router.choose(
    difficulty=features.difficulty,
    risk=features.risk,
    modality=features.modality,
    remaining_budget=budget.remaining,
)
key = semantic_cache.key(prompt, tool_versions, knowledge_version)
if cached := semantic_cache.get(key, quality_floor=0.9):
    return cached
return fallback_chain(route.models).invoke(prompt, deadline=budget.deadline)
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `提取任务难度、风险与模态` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `失败或预算不足时受控降级` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `质量监控反馈更新策略` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **状态持久化** | 会话展示状态与任务执行状态分离 | 断线、重启和 Worker 接管都不丢 run |
| **预算** | 成本、时间、步骤和并行度同时设上限 | 关注每个成功任务成本而非单次 token |
| **路由** | 模型、工具和工作流作为一个版本化 bundle | 降级必须保持安全与输出契约 |
| **观测** | run / step / span / 业务键可关联 | 质量、安全、成本和延迟一起告警 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 小模型处理简单任务可降成本，但误路由后的返工可能更贵。
- 多供应商提高韧性，也增加数据治理、SDK 和评测维护。
- 缓存命中改善延迟，动态知识和个性化任务应谨慎使用。

### 6.1 落地检查表

- API 请求与长任务解耦，队列、租约、心跳和取消均持久化。
- run、step、模型、工具和业务结果使用同一 trace 关联。
- 路由和缓存以质量门槛为前提，不能用便宜结果静默降级。
- 灰度发布 bundle 化，异常能自动停止流量并整体回滚。

## 7. 常见故障

1. 备用模型不支持原工具参数格式，降级后所有调用失败。
2. 缓存键缺少用户权限，复用了其他主体的答案。
3. 网关和 SDK 同时重试，超过总时延并放大费用。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `提取任务难度、风险与模态` 逐步检查到 `质量监控反馈更新策略`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**备用模型不支持原工具参数格式，降级后所有调用失败。**
