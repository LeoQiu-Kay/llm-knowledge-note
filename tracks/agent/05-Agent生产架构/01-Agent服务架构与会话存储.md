# Agent 服务架构与会话存储

> **先记住**：生产 Agent 通常由 API/会话层、编排器、模型网关、工具网关、状态存储、队列和可观测平台组成。

---

## 1. 它在解决什么问题？

生产 Agent 通常由 API/会话层、编排器、模型网关、工具网关、状态存储、队列和可观测平台组成。无状态请求服务负责接入，持久化 run 状态支持长任务恢复；会话只是一种用户视图，不能替代任务、消息、产物和权限的独立数据模型。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 服务边界

接入层处理认证、限流和流式响应；编排器推进状态机；模型网关统一路由与配额；工具网关执行鉴权、schema 校验和审计。边界清晰后可分别扩容和故障隔离。

### 存储模型

关系库保存强一致元数据和状态转移，对象存储保存附件与大产物，缓存保存短期热点，向量库保存可检索知识。消息正文、派生摘要和外部引用要有版本与血缘。

### 多租户与会话

所有主键、查询、缓存和队列消息携带 tenant_id，数据库使用行级或库级隔离。会话并发更新采用版本号，分叉任务保留父 run 关系，删除策略覆盖所有派生数据。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```python
# POST /runs -> {run_id, stream_url}

create_run_transactionally(
    run=Run(id=run_id, tenant=tenant_id, status="queued"),
    event=Event(run_id=run_id, type="run.created"),
)
queue.publish(run_id)

# SSE / WebSocket 只消费持久事件；断线重连从 last_event_id 续传，
# 不把前端连接本身当作任务状态。
```

### 对照着看

- **从哪里开始**：API 创建会话与 run
- **关键状态变化**：编排器推进步骤
- **怎样才算完成**：事件流向前端并最终归档

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **状态持久化** | 会话展示状态与任务执行状态分离 | 断线、重启和 Worker 接管都不丢 run |
| **预算** | 成本、时间、步骤和并行度同时设上限 | 关注每个成功任务成本而非单次 token |
| **路由** | 模型、工具和工作流作为一个版本化 bundle | 降级必须保持安全与输出契约 |
| **观测** | run / step / span / 业务键可关联 | 质量、安全、成本和延迟一起告警 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 单体适合早期快速迭代，模块边界仍应明确以便后续拆分。
- 强一致适用于状态和权限，遥测与部分产物可最终一致。
- 流式 token 改善体验，但最终消息与运行终态仍需可靠提交。

### 上线前检查

- API 请求与长任务解耦，队列、租约、心跳和取消均持久化。
- run、step、模型、工具和业务结果使用同一 trace 关联。
- 路由和缓存以质量门槛为前提，不能用便宜结果静默降级。
- 灰度发布 bundle 化，异常能自动停止流量并整体回滚。

---

## 7. 常见误区与排查

### 容易踩的坑

1. HTTP 连接断开就把任务标记失败，但后台实际仍在执行。
2. 会话缓存未按租户隔离，返回其他用户历史。
3. 附件已删除，向量索引和生成引用仍指向孤儿数据。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“API 创建会话与 run”一路检查到“事件流向前端并最终归档”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
