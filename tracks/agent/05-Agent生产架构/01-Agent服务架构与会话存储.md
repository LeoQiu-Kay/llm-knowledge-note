# Agent 服务架构与会话存储

> **一句话定位**：生产 Agent 通常由 API/会话层、编排器、模型网关、工具网关、状态存储、队列和可观测平台组成。

---

## 1. 先给结论

生产 Agent 通常由 API/会话层、编排器、模型网关、工具网关、状态存储、队列和可观测平台组成。无状态请求服务负责接入，持久化 run 状态支持长任务恢复；会话只是一种用户视图，不能替代任务、消息、产物和权限的独立数据模型。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 服务边界

接入层处理认证、限流和流式响应；编排器推进状态机；模型网关统一路由与配额；工具网关执行鉴权、schema 校验和审计。边界清晰后可分别扩容和故障隔离。

### 存储模型

关系库保存强一致元数据和状态转移，对象存储保存附件与大产物，缓存保存短期热点，向量库保存可检索知识。消息正文、派生摘要和外部引用要有版本与血缘。

### 多租户与会话

所有主键、查询、缓存和队列消息携带 tenant_id，数据库使用行级或库级隔离。会话并发更新采用版本号，分叉任务保留父 run 关系，删除策略覆盖所有派生数据。

## 3. 工作流程与关键路径

```text
[API 创建会话与 run]
    │
    ▼
[会话存储保存消息和状态]
    │
    ▼
[编排器推进步骤]
    │
    ▼
[工具执行器隔离副作用]
    │
    ▼
[事件流向前端并最终归档]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`API 创建会话与 run` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`会话存储保存消息和状态` 与 `编排器推进步骤` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`事件流向前端并最终归档` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
# POST /runs -> {run_id, stream_url}

create_run_transactionally(
    run=Run(id=run_id, tenant=tenant_id, status="queued"),
    event=Event(run_id=run_id, type="run.created"),
)
queue.publish(run_id)

# SSE / WebSocket 只消费持久事件；断线重连从 last_event_id 续传，
# 不把前端连接本身当作任务状态。
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `API 创建会话与 run` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `编排器推进步骤` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `事件流向前端并最终归档` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **状态持久化** | 会话展示状态与任务执行状态分离 | 断线、重启和 Worker 接管都不丢 run |
| **预算** | 成本、时间、步骤和并行度同时设上限 | 关注每个成功任务成本而非单次 token |
| **路由** | 模型、工具和工作流作为一个版本化 bundle | 降级必须保持安全与输出契约 |
| **观测** | run / step / span / 业务键可关联 | 质量、安全、成本和延迟一起告警 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 单体适合早期快速迭代，模块边界仍应明确以便后续拆分。
- 强一致适用于状态和权限，遥测与部分产物可最终一致。
- 流式 token 改善体验，但最终消息与运行终态仍需可靠提交。

### 6.1 落地检查表

- API 请求与长任务解耦，队列、租约、心跳和取消均持久化。
- run、step、模型、工具和业务结果使用同一 trace 关联。
- 路由和缓存以质量门槛为前提，不能用便宜结果静默降级。
- 灰度发布 bundle 化，异常能自动停止流量并整体回滚。

## 7. 常见故障

1. HTTP 连接断开就把任务标记失败，但后台实际仍在执行。
2. 会话缓存未按租户隔离，返回其他用户历史。
3. 附件已删除，向量索引和生成引用仍指向孤儿数据。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `API 创建会话与 run` 逐步检查到 `事件流向前端并最终归档`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**HTTP 连接断开就把任务标记失败，但后台实际仍在执行。**
