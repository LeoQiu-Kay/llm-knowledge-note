# 部署、灰度与版本回滚

> **一句话定位**：Agent 发布物不仅是代码，还包括模型、系统提示、工作流、工具 schema、检索索引和安全策略。

---

## 1. 先给结论

Agent 发布物不仅是代码，还包括模型、系统提示、工作流、工具 schema、检索索引和安全策略。部署必须为这些依赖建立组合版本，通过离线回归、影子流量、灰度和在线指标逐步放量；回滚要恢复兼容组合，并正确处理仍在运行的长任务。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### 版本清单

每个 run 记录代码、提示、模型、路由、工具、策略、知识快照和评测版本。制品不可变，配置变更也走审查与发布流程，避免线上状态无法复现。

### 灰度验证

先离线评测和安全测试，再用影子流量比较但禁止真实副作用，随后按租户或比例灰度。守门指标包含质量、延迟、成本、拒绝率和工具错误，而非只看服务 5xx。

### 兼容与回滚

运行中任务通常固定原工作流与 schema 到结束；数据库和状态迁移采用向前/向后兼容。回滚同时处理提示、工具和索引版本，必要时暂停新任务并排空旧 worker。

## 3. 工作流程与关键路径

```text
[版本化提示、模型、工具和工作流]
    │
    ▼
[离线评测通过门禁]
    │
    ▼
[小流量灰度并影子对比]
    │
    ▼
[监控质量、安全、成本与延迟]
    │
    ▼
[异常自动停止并回滚整套配置]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`版本化提示、模型、工具和工作流` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`离线评测通过门禁` 与 `小流量灰度并影子对比` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`异常自动停止并回滚整套配置` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```yaml
release:
  bundle: {prompt: p17, workflow: w9, tools: t31, modelPolicy: m6}
  offlineGate: {successRate: 0.90, safetyRate: 1.0}
  rollout:
    - traffic: 1%
      hold: 30m
    - traffic: 10%
      hold: 2h
    - traffic: 50%
  rollbackOn:
    - success_rate_drop > 3%
    - p95_latency_increase > 20%
    - safety_incident_count > 0
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `版本化提示、模型、工具和工作流` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `小流量灰度并影子对比` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `异常自动停止并回滚整套配置` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **状态持久化** | 会话展示状态与任务执行状态分离 | 断线、重启和 Worker 接管都不丢 run |
| **预算** | 成本、时间、步骤和并行度同时设上限 | 关注每个成功任务成本而非单次 token |
| **路由** | 模型、工具和工作流作为一个版本化 bundle | 降级必须保持安全与输出契约 |
| **观测** | run / step / span / 业务键可关联 | 质量、安全、成本和延迟一起告警 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 快速模型别名升级方便，却降低可复现性，高风险功能宜固定版本。
- 影子请求可验证模型输出，但对收费和数据共享仍要受配额与合规约束。
- 全量回滚简单，局部租户回滚更灵活但版本矩阵复杂。

### 6.1 落地检查表

- API 请求与长任务解耦，队列、租约、心跳和取消均持久化。
- run、step、模型、工具和业务结果使用同一 trace 关联。
- 路由和缓存以质量门槛为前提，不能用便宜结果静默降级。
- 灰度发布 bundle 化，异常能自动停止流量并整体回滚。

---

## 7. 常见故障

1. 只回滚应用代码，工具 schema 和提示仍是新版本。
2. 新 worker 无法读取旧检查点，长任务全部失败。
3. 灰度指标只看基础设施健康，任务成功率已明显下降却继续放量。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `版本化提示、模型、工具和工作流` 逐步检查到 `异常自动停止并回滚整套配置`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**只回滚应用代码，工具 schema 和提示仍是新版本。**
