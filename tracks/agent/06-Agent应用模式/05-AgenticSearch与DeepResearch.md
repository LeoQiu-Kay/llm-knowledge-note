# Agentic Search 与 Deep Research

> **一句话定位**：Agentic Search/Deep Research 将复杂问题拆解为检索子题，迭代搜索、阅读、交叉验证并合成带引用报告。

---

## 1. 先给结论

Agentic Search/Deep Research 将复杂问题拆解为检索子题，迭代搜索、阅读、交叉验证并合成带引用报告。高质量系统要规划覆盖面、控制来源质量和时效、去重与发现矛盾，保存查询和证据链，并在预算内判断何时信息已经足够，而不是无限浏览。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### 研究计划

先澄清问题范围、时间和输出标准，再拆成可验证子问题与关键词。计划随发现更新，但要记录覆盖矩阵，防止只深挖一个方向而遗漏关键维度。

### 来源与证据

优先一手资料、官方文档和高信誉来源，记录发布日期、事件日期、作者和访问时间。重要事实至少交叉核对，区分直接证据、来源观点与系统推断。

### 综合与停止

对重复内容聚类，对冲突展示双方证据与时间，按主题生成结论并逐句引用。停止条件可基于子题覆盖、连续搜索无新信息、置信度和成本预算。

## 3. 工作流程与关键路径

```text
[拆解研究问题]
    │
    ▼
[并行搜索多个独立来源]
    │
    ▼
[抽取证据与发布日期]
    │
    ▼
[交叉验证冲突并补搜]
    │
    ▼
[带引用综合结论和不确定性]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`拆解研究问题` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`并行搜索多个独立来源` 与 `抽取证据与发布日期` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`带引用综合结论和不确定性` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
questions = planner.decompose(research_question)
sources = parallel_map(search, questions)
evidence = [
    extract(source, fields=["claim", "quote", "published_at", "author", "url"])
    for source in deduplicate(sources)
    if source_reliability(source) >= MIN_RELIABILITY
]
conflicts = detect_conflicting_claims(evidence)
evidence += targeted_follow_up_search(conflicts)
return synthesize(evidence, cite_every_claim=True, state_uncertainty=True)
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `拆解研究问题` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `抽取证据与发布日期` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `带引用综合结论和不确定性` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **可验证性** | 每一步都有可观察前置状态和验收条件 | DOM、测试、SQL 计划或引用充当证据 |
| **副作用** | 发送、购买、删除和提交必须明确确认 | 展示 diff、目标、风险和撤销方式 |
| **用户控制** | 计划、进度、暂停、取消和接管始终可见 | 失败时给可恢复下一步，不只报错 |
| **领域约束** | 通用模型不能绕过代码、数据、语音或搜索领域规则 | 专用校验器和最小权限工具守门 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 搜索更广提高召回，却会增加低质量来源和综合成本。
- 只用最新来源可能忽略基础资料，时效性要按问题类型判断。
- 并行研究降低延迟，但需要统一术语、去重和证据合并。

### 6.1 落地检查表

- 对用户展示计划、进度、证据和即将发生的副作用。
- 观察—行动—再观察，每一步都验证真实状态变化。
- 领域校验器限制 SQL、代码、浏览器、语音和搜索的危险边界。
- 支持暂停、取消、重试、编辑、撤销和人工接管。

## 7. 常见故障

1. 引用页面真实存在，但正文没有支持对应结论。
2. 把文章发布日期误当事件发生日期。
3. 搜索结果中的 SEO 聚合站相互引用，形成虚假多源验证。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `拆解研究问题` 逐步检查到 `带引用综合结论和不确定性`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**引用页面真实存在，但正文没有支持对应结论。**
