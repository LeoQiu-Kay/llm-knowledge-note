# Agent 产品设计与用户体验

> **一句话定位**：Agent 产品的核心体验是让用户理解系统能做什么、正在做什么、为何需要权限以及如何纠正和接管。

---

## 1. 先给结论

Agent 产品的核心体验是让用户理解系统能做什么、正在做什么、为何需要权限以及如何纠正和接管。应通过范围明确的入口、渐进授权、计划与进度、可编辑产物、证据和撤销机制建立信任；自主程度按风险分级，而不是用拟人化对话掩盖不确定性。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### 能力与预期

入口展示适用任务、所需数据、预计时间和限制，复杂请求先复述目标与成功标准。系统对不确定和失败要直说，避免把建议包装成已执行结果。

### 可控执行

执行前展示高影响计划，过程中显示当前步骤、等待原因和成本，允许暂停、取消、修改与人工接管。写操作提供预览、diff、确认和可撤销窗口。

### 反馈与信任

答案展示关键证据和数据时间，产物可编辑并保留变更记录。收集“哪里错了”的结构化反馈，而非只有点赞；无障碍、移动端和国际化同样进入任务流程设计。

## 3. 工作流程与关键路径

```text
[用户给出目标与授权]
    │
    ▼
[系统展示计划和可编辑边界]
    │
    ▼
[Agent 持续反馈进度与证据]
    │
    ▼
[关键副作用请求确认]
    │
    ▼
[完成后提供结果、撤销和复盘入口]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`用户给出目标与授权` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`系统展示计划和可编辑边界` 与 `Agent 持续反馈进度与证据` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`完成后提供结果、撤销和复盘入口` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `用户给出目标与授权` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `Agent 持续反馈进度与证据` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `完成后提供结果、撤销和复盘入口` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **可验证性** | 每一步都有可观察前置状态和验收条件 | DOM、测试、SQL 计划或引用充当证据 |
| **副作用** | 发送、购买、删除和提交必须明确确认 | 展示 diff、目标、风险和撤销方式 |
| **用户控制** | 计划、进度、暂停、取消和接管始终可见 | 失败时给可恢复下一步，不只报错 |
| **领域约束** | 通用模型不能绕过代码、数据、语音或搜索领域规则 | 专用校验器和最小权限工具守门 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 过多确认会打断体验，可按风险、用户经验和组织策略动态调整。
- 展示完整推理既不必要也可能混淆，重点展示计划、证据和动作依据。
- 拟人化可提升亲和力，但不应误导用户认为系统具有人类判断与责任。

### 6.1 落地检查表

- 对用户展示计划、进度、证据和即将发生的副作用。
- 观察—行动—再观察，每一步都验证真实状态变化。
- 领域校验器限制 SQL、代码、浏览器、语音和搜索的危险边界。
- 支持暂停、取消、重试、编辑、撤销和人工接管。

---

## 7. 常见故障

1. 进度动画持续运行但没有真实状态，用户无法判断是否卡死。
2. Agent 自动发送或发布内容，没有预览与撤销。
3. 失败只显示“出错了”，不提供已完成步骤、影响和恢复选择。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `用户给出目标与授权` 逐步检查到 `完成后提供结果、撤销和复盘入口`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**进度动画持续运行但没有真实状态，用户无法判断是否卡死。**
