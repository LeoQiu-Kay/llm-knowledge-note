# Data/SQL Agent

> **一句话定位**：Data/SQL Agent 把自然语言目标转换为数据发现、查询、分析和解释。

---

## 1. 先给结论

Data/SQL Agent 把自然语言目标转换为数据发现、查询、分析和解释。安全实现先获取 schema 与业务口径，生成只读、受限查询，经解析器和策略校验后在隔离账户执行，再验证结果与引用；写操作、敏感字段和大规模扫描必须走更严格审批或专用工作流。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### 语义与 schema

向模型提供表、字段、主外键、指标定义、时间口径和样例值，而不是完整数据。语义层统一“活跃用户”等业务指标，避免每次让模型猜 join 和过滤条件。

### 查询护栏

使用只读凭证、允许列表、AST 解析和参数化查询，限制表、列、行数、扫描量、执行时间和并发。先 EXPLAIN 评估成本，禁止多语句、DDL/DML 和不受控函数。

### 结果验证

检查空值、重复、时间范围、单位和总分关系，对关键结论运行交叉查询或规则校验。答案展示 SQL、数据时间和口径，区分观察结果与因果推断。

## 3. 工作流程与关键路径

```text
[解析业务问题与指标口径]
    │
    ▼
[检索 schema 和样例]
    │
    ▼
[生成只读 SQL]
    │
    ▼
[静态校验并限制扫描量]
    │
    ▼
[执行、解释结果并保留查询证据]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`解析业务问题与指标口径` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`检索 schema 和样例` 与 `生成只读 SQL` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`执行、解释结果并保留查询证据` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```sql
-- 生成后先静态校验：只读、单语句、强制 tenant 条件和行数上限。
EXPLAIN
SELECT date_trunc('day', paid_at) AS day,
       COUNT(*) AS orders,
       SUM(amount) AS revenue
  FROM orders
 WHERE tenant_id = :tenant_id
   AND paid_at >= :start_at
   AND paid_at < :end_at
 GROUP BY 1
 ORDER BY 1
 LIMIT 1000;
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `解析业务问题与指标口径` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `生成只读 SQL` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `执行、解释结果并保留查询证据` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **可验证性** | 每一步都有可观察前置状态和验收条件 | DOM、测试、SQL 计划或引用充当证据 |
| **副作用** | 发送、购买、删除和提交必须明确确认 | 展示 diff、目标、风险和撤销方式 |
| **用户控制** | 计划、进度、暂停、取消和接管始终可见 | 失败时给可恢复下一步，不只报错 |
| **领域约束** | 通用模型不能绕过代码、数据、语音或搜索领域规则 | 专用校验器和最小权限工具守门 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 实时 schema 提高准确性，也可能泄露敏感表名，应按用户权限裁剪。
- 自动修复 SQL 提高成功率，但重试必须保持同一安全策略和预算。
- 把常用问题固化为指标 API 更可靠，长尾探索再使用 Agent。

### 6.1 落地检查表

- 对用户展示计划、进度、证据和即将发生的副作用。
- 观察—行动—再观察，每一步都验证真实状态变化。
- 领域校验器限制 SQL、代码、浏览器、语音和搜索的危险边界。
- 支持暂停、取消、重试、编辑、撤销和人工接管。

## 7. 常见故障

1. 模型生成笛卡尔积，扫描量和费用失控。
2. 查询成功但使用错误时区或业务口径，结论错误。
3. 结果集包含个人信息并被完整写入模型日志。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `解析业务问题与指标口径` 逐步检查到 `执行、解释结果并保留查询证据`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**模型生成笛卡尔积，扫描量和费用失控。**
