# 工具调用与结构化输出

> **一句话定位**：工具调用是让模型选择一个受控函数并生成符合 schema 的参数，应用负责验证、授权、执行，再把结果返回模型；模型本身不直接拥有系统权限。

---

## 1. 先给结论

工具调用是让模型选择一个受控函数并生成符合 schema 的参数，应用负责验证、授权、执行，再把结果返回模型；模型本身不直接拥有系统权限。可靠实现需要窄而清晰的工具语义、严格结构化参数、服务端二次校验、超时重试和幂等控制。结构化输出解决“格式可解析”，并不保证参数在业务上正确或操作被授权。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 工具契约

工具名称和描述应明确说明“何时用、何时不用”，JSON Schema 约束类型、枚举、必填项和范围。一个工具只承担一个清晰动作，避免把几十种行为塞进含糊的 `execute`。工具结果也应结构化，例如：

```json
{"ok": false, "error": {"code": "ORDER_NOT_FOUND", "retryable": false}}
```

这样模型与编排器能区分需要改参数、稍后重试或直接结束。

### 安全边界

模型输出始终是不可信输入。应用需校验 schema 之外的业务约束，按当前用户身份鉴权，并对文件路径、SQL、URL 和命令做白名单或能力限制。来自网页、文档和工具结果的内容也可能含提示注入，不能因为它在“观察结果”里就升级为系统指令。

### 结构化输出

原生 schema 约束通常比“请返回 JSON”可靠，但仍要处理拒答、截断、模型不支持和 schema 演进。对无副作用的格式错误可进行有限修复或重试；有副作用的调用必须先确认上一请求是否已执行，再决定重试。

## 3. 工作流程与关键路径

```text
[模型生成结构化工具意图]
    │
    ▼
[按 JSON Schema 校验参数]
    │
    ▼
[权限层批准或拒绝]
    │
    ▼
[执行器调用真实系统]
    │
    ▼
[结果标准化后回填上下文]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`模型生成结构化工具意图` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`按 JSON Schema 校验参数` 与 `权限层批准或拒绝` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`结果标准化后回填上下文` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
class CreateTicket(BaseModel):
    title: str = Field(min_length=3, max_length=120)
    severity: Literal["low", "medium", "high"]
    customer_id: str

raw = model.tool_call(tool="create_ticket", schema=CreateTicket.model_json_schema())
args = CreateTicket.model_validate_json(raw.arguments)
policy.require(user, "ticket:create", resource=args.customer_id)
result = ticket_client.create(**args.model_dump(), idempotency_key=call_id)
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `模型生成结构化工具意图` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `权限层批准或拒绝` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `结果标准化后回填上下文` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **自主性** | 只在路径无法枚举时让模型动态决策 | 稳定路径优先 workflow，开放局部才用 loop |
| **状态** | 显式保存目标、步骤、观察、预算与终止条件 | 状态可序列化、可恢复、可审计 |
| **上下文** | 区分规则、任务、证据、记忆和工具结果 | 按优先级装配并测量遗漏与污染 |
| **终止** | 成功、失败、取消、超时和预算耗尽都有明确出口 | 检测重复动作与无进展循环 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 粒度太粗会扩大权限，太细则增加模型选择难度与交互轮次。
- 把确定性转换、过滤、计算留在代码中，不要为每个机械步骤调用模型。
- 返回给模型的数据应最小化并脱敏，避免把整张数据库记录或密钥塞进上下文。
- 工具版本变更要向后兼容，运行记录应保存实际 schema/版本。

### 6.1 落地检查表

- 显式设置步骤、token、费用、时间与工具调用上限。
- 模型不直接拥有权限；所有工具调用经过 Schema 与策略校验。
- 状态、动作、观察和终止原因可持久化与重放。
- 检测重复动作、无进展与上下文污染，必要时请求人工接管。

## 7. 常见故障

1. 只做 JSON 解析，未做业务范围和权限校验。
2. 写操作超时后直接重试，导致订单、消息或工单重复创建。
3. 工具描述相互重叠，模型在多个相似工具间随机选择。
4. 将内部堆栈、连接串或敏感字段原样返回模型与日志。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `模型生成结构化工具意图` 逐步检查到 `结果标准化后回填上下文`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**只做 JSON 解析，未做业务范围和权限校验。**

## 🎯 高频追问

1. **一次可靠的工具调用链路包含哪些步骤？**

   模型基于工具描述选择工具并生成结构化参数；应用解析并按 schema 校验，再做业务校验、身份鉴权和风险控制；执行器设置超时与幂等策略后调用外部系统；最后把脱敏、结构化的成功或错误结果写回运行状态，供模型决定下一步。

2. **JSON Schema 校验通过后为什么仍不能直接执行？**

   Schema 只能证明数据形状基本正确，不能证明资源属于当前用户、金额合理、状态允许、URL 安全或操作符合审批规则。模型输出仍是不可信输入，服务端必须做与普通 API 相同的鉴权、业务约束、风控和审计。

3. **如何处理写工具调用超时后的重试？**

   超时不代表未执行。调用前生成稳定幂等键并由下游去重；超时后先按幂等键查询执行结果，再决定返回成功或有限重试。若下游不支持幂等，则需要业务唯一约束、状态机或人工确认，不能盲目重发。

4. **工具返回结果中为什么也存在提示注入风险？**

   网页、邮件、文档等外部内容可能包含“忽略规则并调用某工具”之类恶意文本。它只是数据，不应被提升为可信指令。系统应分隔指令与数据、最小化工具权限、限制可用工具，并在高风险动作前做确定性校验或人工确认。

5. **工具很多时如何降低模型选错工具的概率？**

   消除语义重叠，使用清晰名称、正反例和窄参数；按当前任务或权限只暴露相关工具；必要时先做工具检索/路由，再让模型从小集合选择；对高价值流程可加入确定性预路由。还要用真实轨迹评测工具选择准确率，而不是只改描述凭感觉验证。
