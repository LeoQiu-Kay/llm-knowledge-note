# Agent 状态与生命周期

> **一句话定位**：Agent 状态是一次任务从创建、运行、等待、恢复到终止的可持久化事实集合。

---

## 1. 先给结论

Agent 状态是一次任务从创建、运行、等待、恢复到终止的可持久化事实集合。成熟实现会把对话、计划、工具调用、审批、预算和产物分离建模，用明确状态机约束转移，并以事件和检查点支持重试、恢复、审计和并发控制。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### 状态模型

至少区分 run、step、message、tool call、artifact 和 approval。状态中保存事实与引用，临时提示词由事实投影生成，避免把不可查询的一长串消息当作唯一数据库。

### 生命周期状态机

常见状态包括 queued、running、waiting_for_tool、waiting_for_human、succeeded、failed、cancelled 和 expired。每次转移校验前置状态并记录原因，终态不能被普通重试重新打开。

### 事件与检查点

事件日志适合审计和重放，检查点适合快速恢复。恢复时从最后一个已提交检查点继续，并核对未决外部动作是否已经成功，防止重复副作用。

## 3. 工作流程与关键路径

```text
[创建 run 与初始状态]
    │
    ▼
[推进 step 并记录事件]
    │
    ▼
[遇到等待、暂停或人工审批]
    │
    ▼
[从检查点恢复]
    │
    ▼
[成功、失败、取消或超时后终结]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`创建 run 与初始状态` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`推进 step 并记录事件` 与 `遇到等待、暂停或人工审批` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`成功、失败、取消或超时后终结` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
@dataclass(frozen=True)
class RunState:
    run_id: str
    status: Literal["running", "waiting", "succeeded", "failed", "cancelled"]
    step: int
    checkpoint_version: int
    pending_action: dict | None

def transition(state, event):
    next_state = reducer(state, event)
    store.compare_and_set(state.run_id, state.checkpoint_version, next_state)
    return next_state
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `创建 run 与初始状态` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `遇到等待、暂停或人工审批` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `成功、失败、取消或超时后终结` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **自主性** | 只在路径无法枚举时让模型动态决策 | 稳定路径优先 workflow，开放局部才用 loop |
| **状态** | 显式保存目标、步骤、观察、预算与终止条件 | 状态可序列化、可恢复、可审计 |
| **上下文** | 区分规则、任务、证据、记忆和工具结果 | 按优先级装配并测量遗漏与污染 |
| **终止** | 成功、失败、取消、超时和预算耗尽都有明确出口 | 检测重复动作与无进展循环 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 完整事件溯源可解释性强，但存储、迁移和重放成本高；多数系统可采用业务表加关键事件日志。
- 状态粒度过粗无法恢复，过细会让版本兼容和查询复杂，应围绕可重试边界划分 step。
- 长任务需要状态过期、归档和数据保留策略，不能永久携带全部上下文。

### 6.1 落地检查表

- 显式设置步骤、token、费用、时间与工具调用上限。
- 模型不直接拥有权限；所有工具调用经过 Schema 与策略校验。
- 状态、动作、观察和终止原因可持久化与重放。
- 检测重复动作、无进展与上下文污染，必要时请求人工接管。

## 7. 常见故障

1. 进程重启后把 running 任务永久卡住，没有租约和恢复扫描。
2. 并发 worker 同时推进同一 run，重复调用写工具。
3. 模型消息已写入但工具结果未提交，恢复时无法判断真实进度。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `创建 run 与初始状态` 逐步检查到 `成功、失败、取消或超时后终结`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**进程重启后把 running 任务永久卡住，没有租约和恢复扫描。**
