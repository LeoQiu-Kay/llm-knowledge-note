# Agent 状态与生命周期

> **先记住**：Agent 状态是一次任务从创建、运行、等待、恢复到终止的可持久化事实集合。

---

## 1. 它在解决什么问题？

Agent 状态是一次任务从创建、运行、等待、恢复到终止的可持久化事实集合。成熟实现会把对话、计划、工具调用、审批、预算和产物分离建模，用明确状态机约束转移，并以事件和检查点支持重试、恢复、审计和并发控制。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 状态模型

至少区分 run、step、message、tool call、artifact 和 approval。状态中保存事实与引用，临时提示词由事实投影生成，避免把不可查询的一长串消息当作唯一数据库。

### 生命周期状态机

常见状态包括 queued、running、waiting_for_tool、waiting_for_human、succeeded、failed、cancelled 和 expired。每次转移校验前置状态并记录原因，终态不能被普通重试重新打开。

### 事件与检查点

事件日志适合审计和重放，检查点适合快速恢复。恢复时从最后一个已提交检查点继续，并核对未决外部动作是否已经成功，防止重复副作用。

- **从哪里开始**：创建 run 与初始状态
- **关键状态变化**：遇到等待、暂停或人工审批

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **自主性** | 只在路径无法枚举时让模型动态决策 | 稳定路径优先 workflow，开放局部才用 loop |
| **状态** | 显式保存目标、步骤、观察、预算与终止条件 | 状态可序列化、可恢复、可审计 |
| **上下文** | 区分规则、任务、证据、记忆和工具结果 | 按优先级装配并测量遗漏与污染 |
| **终止** | 成功、失败、取消、超时和预算耗尽都有明确出口 | 检测重复动作与无进展循环 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 完整事件溯源可解释性强，但存储、迁移和重放成本高；多数系统可采用业务表加关键事件日志。
- 状态粒度过粗无法恢复，过细会让版本兼容和查询复杂，应围绕可重试边界划分 step。
- 长任务需要状态过期、归档和数据保留策略，不能永久携带全部上下文。

### 上线前检查

- 显式设置步骤、token、费用、时间与工具调用上限。
- 模型不直接拥有权限；所有工具调用经过 Schema 与策略校验。
- 状态、动作、观察和终止原因可持久化与重放。
- 检测重复动作、无进展与上下文污染，必要时请求人工接管。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 进程重启后把 running 任务永久卡住，没有租约和恢复扫描。
2. 并发 worker 同时推进同一 run，重复调用写工具。
3. 模型消息已写入但工具结果未提交，恢复时无法判断真实进度。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“创建 run 与初始状态”一路检查到“成功、失败、取消或超时后终结”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
