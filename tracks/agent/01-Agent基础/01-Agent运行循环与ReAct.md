# Agent 运行循环与 ReAct

## 30 秒回答

Agent 不是一次普通对话，而是“观察状态—决定动作—调用工具—读取结果—继续推理—终止”的受控循环。ReAct 把推理与行动交替组织，便于模型根据外部反馈修正计划。生产实现的关键不是让循环无限自主，而是明确状态、工具权限、步数/成本预算、终止条件和人工接管点，并保证每一步可恢复、可追踪。

## 核心原理

### 状态机视角

一次运行至少包含用户目标、消息历史、当前计划、工具调用与结果、预算、最终状态。循环通常是：

1. 根据当前状态请求模型；
2. 若模型给出最终答案则结束；
3. 若模型请求工具，校验参数与权限后执行；
4. 把结构化结果写回状态，再进入下一轮；
5. 达到步数、时间或费用上限时安全终止。

显式状态比只拼接一长串消息更可靠。状态可以持久化为事件或检查点，进程重启后从已完成步骤继续，避免重复执行有副作用的操作。

### 规划与执行

简单任务用单循环 ReAct 即可；长任务可以先规划再执行，或由调度器把任务拆成确定性节点。规划并不保证正确，计划应允许根据工具结果修订。多 Agent 只有在角色确实具有不同工具、上下文或并行价值时才值得引入，否则会增加通信、评测和故障面。

## 工程权衡

- 自主性越高，未知路径与成本越难控制；高风险操作应要求确认或审批。
- 上下文不能无限增长，应按任务状态选择信息、摘要历史，并保留原始证据引用。
- 工具返回值要区分成功、业务失败、超时和不可重试错误，避免模型从自然语言猜状态。
- 有副作用的动作使用幂等键、读后写校验或补偿机制，防止重试造成重复操作。

## 常见故障

1. 模型重复调用同一个工具，进入无进展循环。
2. 只限制轮数，不限制工具耗时、token 和外部 API 费用。
3. 把工具错误文本当作正常观察继续推理，产生错误结论。
4. 运行状态只存在内存中，服务重启后丢失或重复执行。
