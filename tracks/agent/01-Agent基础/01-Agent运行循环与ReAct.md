# Agent 运行循环与 ReAct

> **先记住**：Agent 不是一次普通对话，而是“观察状态—决定动作—调用工具—读取结果—继续推理—终止”的受控循环。

---

## 1. 它在解决什么问题？

Agent 不是一次普通对话，而是“观察状态—决定动作—调用工具—读取结果—继续推理—终止”的受控循环。ReAct 把推理与行动交替组织，便于模型根据外部反馈修正计划。生产实现的关键不是让循环无限自主，而是明确状态、工具权限、步数/成本预算、终止条件和人工接管点，并保证每一步可恢复、可追踪。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 状态机视角

一次运行至少包含用户目标、消息历史、当前计划、工具调用与结果、预算、最终状态。循环通常是：

1. 根据当前状态请求模型；
2. 若模型给出最终答案则结束；
3. 若模型请求工具，校验参数与权限后执行；
4. 把结构化结果写回状态，再进入下一轮；
5. 达到步数、时间或费用上限时安全终止。

显式状态比只拼接一长串消息更可靠。状态可以持久化为事件或检查点，进程重启后从已完成步骤继续，避免重复执行有副作用的操作。

### 规划与执行

简单任务用单循环 ReAct 即可；长任务可以先规划再执行，或由调度器把任务拆成确定性节点。规划并不保证正确，计划应允许根据工具结果修订。多 Agent 只有在角色确实具有不同工具、上下文或并行价值时才值得引入，否则会增加通信、评测和故障面。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```python
def run_agent(goal, policy, max_steps=12):
    state = {"goal": goal, "events": [], "status": "running"}
    for step_no in range(max_steps):
        action = model.next_action(compose_context(state))
        policy.authorize(action, state)
        observation = tools.execute(action, idempotency_key=f"{run_id}:{step_no}")
        state["events"].append({"action": action, "observation": observation})
        if termination_reached(state):
            return finalize(state)
    raise BudgetExceeded("agent step budget exhausted")
```

### 对照着看

- **从哪里开始**：接收目标与当前状态
- **关键状态变化**：策略层校验工具与预算
- **怎样才算完成**：更新状态，满足终止条件后输出

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **自主性** | 只在路径无法枚举时让模型动态决策 | 稳定路径优先 workflow，开放局部才用 loop |
| **状态** | 显式保存目标、步骤、观察、预算与终止条件 | 状态可序列化、可恢复、可审计 |
| **上下文** | 区分规则、任务、证据、记忆和工具结果 | 按优先级装配并测量遗漏与污染 |
| **终止** | 成功、失败、取消、超时和预算耗尽都有明确出口 | 检测重复动作与无进展循环 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 自主性越高，未知路径与成本越难控制；高风险操作应要求确认或审批。
- 上下文不能无限增长，应按任务状态选择信息、摘要历史，并保留原始证据引用。
- 工具返回值要区分成功、业务失败、超时和不可重试错误，避免模型从自然语言猜状态。
- 有副作用的动作使用幂等键、读后写校验或补偿机制，防止重试造成重复操作。

### 上线前检查

- 显式设置步骤、token、费用、时间与工具调用上限。
- 模型不直接拥有权限；所有工具调用经过 Schema 与策略校验。
- 状态、动作、观察和终止原因可持久化与重放。
- 检测重复动作、无进展与上下文污染，必要时请求人工接管。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 模型重复调用同一个工具，进入无进展循环。
2. 只限制轮数，不限制工具耗时、token 和外部 API 费用。
3. 把工具错误文本当作正常观察继续推理，产生错误结论。
4. 运行状态只存在内存中，服务重启后丢失或重复执行。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“接收目标与当前状态”一路检查到“更新状态，满足终止条件后输出”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。

## 9. 高频追问

### Q1. Agent 运行循环与普通聊天调用的本质区别是什么？

普通聊天通常是一次输入到一次输出；Agent 维护显式任务状态，并在模型决策、工具执行、观察结果和下一轮决策之间循环，直到满足终止条件。它还需要处理权限、预算、持久化、重试与副作用，所以是一个受控执行系统，而不只是更长的提示词。

### Q2. ReAct 的核心思想是什么？

ReAct 让推理/决策与外部行动交替进行：模型基于当前观察选择动作，工具返回新证据后再修正下一步，而不是一开始生成不可变的完整答案。工程上不必暴露模型的私有推理文本，但要保存动作、工具结果和状态变化以便审计。

### Q3. 如何防止 Agent 陷入无限循环？

设置步数、时间、token、费用和工具调用上限；记录近期动作与结果，检测相同调用、状态不变或目标距离没有改善；为可恢复错误设置有限重试和退避；达到阈值后输出受控失败、切换确定性流程或请求人工接管，而不是继续让模型“再试一次”。

### Q4. workflow 和 agentic loop 应如何选择？

路径稳定、合规要求高、步骤可枚举时优先确定性 workflow，便于测试和审计；环境开放、需要根据未知结果动态选择工具时再使用 agentic loop。生产系统常把两者结合：外层由工作流控制关键节点，局部节点允许 Agent 在有限工具和预算内决策。

### Q5. 有副作用的 Agent 任务怎样做到可恢复？

把每一步意图、参数、幂等键、执行状态和结果持久化为事件或检查点。恢复时先读取外部系统确认不确定步骤是否已经成功，再决定继续、补偿或人工介入。写工具必须支持幂等或提供业务唯一键，不能仅靠“异常就重跑整个任务”。
