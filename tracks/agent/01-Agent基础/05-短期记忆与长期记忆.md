# 短期记忆与长期记忆

> **一句话定位**：Agent 记忆不是简单保存所有聊天记录，而是按用途管理工作状态、情节记录、语义知识和用户偏好。

---

## 1. 先给结论

Agent 记忆不是简单保存所有聊天记录，而是按用途管理工作状态、情节记录、语义知识和用户偏好。短期记忆服务当前任务，长期记忆需要经过提取、授权、去重、检索和过期治理；任何被召回的记忆都只是候选上下文，仍需校验来源与时效。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### 记忆分层

工作记忆保存当前计划、变量和近期证据；情节记忆记录曾发生的任务与结果；语义记忆沉淀稳定知识；偏好记忆保存经用户授权的个性化设置。不同类型应使用不同 schema 和保留期。

### 写入策略

不是每条消息都值得长期保存。写入前提取事实，标注主体、来源、时间、置信度和敏感级别，再做去重、冲突检测与用户授权；高风险事实需要显式确认。

### 召回与遗忘

召回结合任务相关性、时间衰减、重要度和权限过滤。记忆应支持更正、删除、过期和冲突共存，生成时向模型说明记忆来源，不能把历史偏好当作永恒事实。

## 3. 工作流程与关键路径

```text
[工作记忆保存当前任务]
    │
    ▼
[候选经历经过价值判断]
    │
    ▼
[长期记忆写入带来源和时间的信息]
    │
    ▼
[检索与当前目标相关的片段]
    │
    ▼
[合并、过期与纠错防止污染]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`工作记忆保存当前任务` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`候选经历经过价值判断` 与 `长期记忆写入带来源和时间的信息` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`合并、过期与纠错防止污染` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
candidate = Memory(
    text=observation.summary,
    source=observation.uri,
    valid_at=observation.timestamp,
    confidence=observation.confidence,
    tenant_id=session.tenant_id,
)
if memory_policy.should_write(candidate):
    memory_store.upsert(candidate, dedupe_key=candidate.semantic_hash())

recalled = memory_store.search(query, tenant_id=session.tenant_id, limit=8)
context = [m for m in recalled if not m.expired and m.confidence >= 0.7]
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `工作记忆保存当前任务` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `长期记忆写入带来源和时间的信息` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `合并、过期与纠错防止污染` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **自主性** | 只在路径无法枚举时让模型动态决策 | 稳定路径优先 workflow，开放局部才用 loop |
| **状态** | 显式保存目标、步骤、观察、预算与终止条件 | 状态可序列化、可恢复、可审计 |
| **上下文** | 区分规则、任务、证据、记忆和工具结果 | 按优先级装配并测量遗漏与污染 |
| **终止** | 成功、失败、取消、超时和预算耗尽都有明确出口 | 检测重复动作与无进展循环 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 摘要省 token 但会丢细节，关键证据应保留原文引用。
- 向量库适合模糊召回，确定性用户配置更适合结构化数据库。
- 个性化收益必须与隐私、跨租户隔离和删除权成本一起评估。

### 6.1 落地检查表

- 显式设置步骤、token、费用、时间与工具调用上限。
- 模型不直接拥有权限；所有工具调用经过 Schema 与策略校验。
- 状态、动作、观察和终止原因可持久化与重放。
- 检测重复动作、无进展与上下文污染，必要时请求人工接管。

---

## 7. 常见故障

1. 把另一个用户的记忆召回到当前会话，造成严重越权。
2. 旧地址、旧岗位等过期事实持续影响答案。
3. 模型生成的猜测被当作用户事实写入，之后不断自我强化。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `工作记忆保存当前任务` 逐步检查到 `合并、过期与纠错防止污染`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**把另一个用户的记忆召回到当前会话，造成严重越权。**
