# 短期记忆与长期记忆

> **先记住**：Agent 记忆不是简单保存所有聊天记录，而是按用途管理工作状态、情节记录、语义知识和用户偏好。

---

## 1. 它在解决什么问题？

Agent 记忆不是简单保存所有聊天记录，而是按用途管理工作状态、情节记录、语义知识和用户偏好。短期记忆服务当前任务，长期记忆需要经过提取、授权、去重、检索和过期治理；任何被召回的记忆都只是候选上下文，仍需校验来源与时效。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 记忆分层

工作记忆保存当前计划、变量和近期证据；情节记忆记录曾发生的任务与结果；语义记忆沉淀稳定知识；偏好记忆保存经用户授权的个性化设置。不同类型应使用不同 schema 和保留期。

### 写入策略

不是每条消息都值得长期保存。写入前提取事实，标注主体、来源、时间、置信度和敏感级别，再做去重、冲突检测与用户授权；高风险事实需要显式确认。

### 召回与遗忘

召回结合任务相关性、时间衰减、重要度和权限过滤。记忆应支持更正、删除、过期和冲突共存，生成时向模型说明记忆来源，不能把历史偏好当作永恒事实。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```python
candidate = Memory(

    source=observation.uri,
    valid_at=observation.timestamp,
    confidence=observation.confidence,

if memory_policy.should_write(candidate):
    memory_store.upsert(candidate, dedupe_key=candidate.semantic_hash())

recalled = memory_store.search(query, tenant_id=session.tenant_id, limit=8)

```

### 对照着看

- **从哪里开始**：工作记忆保存当前任务
- **关键状态变化**：长期记忆写入带来源和时间的信息
- **怎样才算完成**：合并、过期与纠错防止污染

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **自主性** | 只在路径无法枚举时让模型动态决策 | 稳定路径优先 workflow，开放局部才用 loop |
| **状态** | 显式保存目标、步骤、观察、预算与终止条件 | 状态可序列化、可恢复、可审计 |
| **上下文** | 区分规则、任务、证据、记忆和工具结果 | 按优先级装配并测量遗漏与污染 |
| **终止** | 成功、失败、取消、超时和预算耗尽都有明确出口 | 检测重复动作与无进展循环 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

## 6. 放进真实系统，还要考虑什么

- 摘要省 token 但会丢细节，关键证据应保留原文引用。
- 向量库适合模糊召回，确定性用户配置更适合结构化数据库。
- 个性化收益必须与隐私、跨租户隔离和删除权成本一起评估。

### 上线前检查

- 显式设置步骤、token、费用、时间与工具调用上限。
- 模型不直接拥有权限；所有工具调用经过 Schema 与策略校验。
- 状态、动作、观察和终止原因可持久化与重放。
- 检测重复动作、无进展与上下文污染，必要时请求人工接管。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 把另一个用户的记忆召回到当前会话，造成严重越权。
2. 旧地址、旧岗位等过期事实持续影响答案。
3. 模型生成的猜测被当作用户事实写入，之后不断自我强化。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“工作记忆保存当前任务”一路检查到“合并、过期与纠错防止污染”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
