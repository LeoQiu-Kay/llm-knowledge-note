# 规划、反思与任务分解

> **一句话定位**：规划把复杂目标拆为可验证子任务，反思根据执行证据修订下一步；二者的价值是降低搜索空间和及时纠错，而不是让模型无限自我讨论。

---

## 1. 先给结论

规划把复杂目标拆为可验证子任务，反思根据执行证据修订下一步；二者的价值是降低搜索空间和及时纠错，而不是让模型无限自我讨论。生产系统应控制规划深度，给每个步骤定义输入、工具、成功条件与预算，并用外部验证器判断是否继续。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 任务分解

按可独立执行和验证的结果拆分，而不是按自然语言段落拆分。子任务要声明依赖、预期产物、允许工具、超时和失败策略，便于并行调度与局部重试。

### 滚动规划

环境不确定时只细化近期步骤，执行后根据新证据更新后续计划。计划版本应进入状态，避免执行器继续使用已经失效的旧步骤。

### 反思与验证

反思可检查遗漏、证据冲突和目标覆盖，但应结合规则、测试、检索证据或第二模型等外部信号。只有同一个模型重复阅读自己的答案，容易放大原有偏差。

## 3. 工作流程与关键路径

```text
[解析目标和约束]
    │
    ▼
[生成可验证子任务]
    │
    ▼
[按依赖调度执行]
    │
    ▼
[基于观察检查偏差]
    │
    ▼
[修订剩余计划而非无限反思]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`解析目标和约束` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`生成可验证子任务` 与 `按依赖调度执行` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`修订剩余计划而非无限反思` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
plan = planner.decompose(goal, constraints)
while task := plan.next_ready():
    result = executor.run(task)
    verdict = verifier.check(task.acceptance_criteria, result)
    plan.record(task.id, result, verdict)
    if not verdict.ok:
        plan = planner.repair(plan, failed_task=task, evidence=verdict.evidence)
    if plan.repair_count > 2:
        return request_human_help(plan)
return synthesizer.finish(plan.results)
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `解析目标和约束` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `按依赖调度执行` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `修订剩余计划而非无限反思` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **自主性** | 只在路径无法枚举时让模型动态决策 | 稳定路径优先 workflow，开放局部才用 loop |
| **状态** | 显式保存目标、步骤、观察、预算与终止条件 | 状态可序列化、可恢复、可审计 |
| **上下文** | 区分规则、任务、证据、记忆和工具结果 | 按优先级装配并测量遗漏与污染 |
| **终止** | 成功、失败、取消、超时和预算耗尽都有明确出口 | 检测重复动作与无进展循环 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 简单任务直接执行通常比先生成长计划更快、更稳定。
- 并行子任务可降低延迟，但会增加共享上下文、合并冲突和总 token 成本。
- 反思轮数要由风险与评测收益决定，达到边际收益阈值就终止。

### 6.1 落地检查表

- 显式设置步骤、token、费用、时间与工具调用上限。
- 模型不直接拥有权限；所有工具调用经过 Schema 与策略校验。
- 状态、动作、观察和终止原因可持久化与重放。
- 检测重复动作、无进展与上下文污染，必要时请求人工接管。

---

## 7. 常见故障

1. 计划包含不可执行的抽象步骤，执行器无法选择工具。
2. 每轮都重写完整计划，已完成步骤被重复执行。
3. 反思没有新证据，只生成更长但不更正确的答案。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `解析目标和约束` 逐步检查到 `修订剩余计划而非无限反思`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**计划包含不可执行的抽象步骤，执行器无法选择工具。**
