# 上下文工程与 Token 预算

> **一句话定位**：上下文工程是在有限窗口内选择、组织和标注最有用的信息，包括系统规则、任务状态、工具定义、检索证据、记忆和历史。

---

## 1. 先给结论

上下文工程是在有限窗口内选择、组织和标注最有用的信息，包括系统规则、任务状态、工具定义、检索证据、记忆和历史。目标不是塞满窗口，而是提高信噪比、保持指令边界，并在质量、延迟和成本之间进行可测量的预算分配。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 上下文分层

稳定规则、用户目标、运行状态、外部证据和工具结果应使用清晰边界与结构化标签。低信任内容只能作为数据，不应与系统指令混合，来源和时间要随证据一起传递。

### 压缩与选择

优先删除重复和无关内容，再做分层摘要；当前决策依赖的原始证据保留引用。可按最近性、相关性、权威性和任务阶段动态选择，而非固定截取最后 N 条消息。

### 预算与缓存

为系统提示、历史、检索、工具输出和生成分别设 token 上限。稳定前缀可利用提示缓存，长工具结果先结构化提取，预算耗尽时应降级或请求用户缩小范围。

## 3. 工作流程与关键路径

```text
[收集系统规则、任务与证据]
    │
    ▼
[按优先级和预算选择上下文]
    │
    ▼
[压缩历史但保留约束]
    │
    ▼
[模型执行当前步骤]
    │
    ▼
[记录 token、命中率与遗漏错误]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`收集系统规则、任务与证据` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`按优先级和预算选择上下文` 与 `压缩历史但保留约束` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`记录 token、命中率与遗漏错误` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
def build_context(system, task, evidence, history, budget):
    fixed = tokenize(system) + tokenize(task)
    remaining = budget - len(fixed) - RESERVED_OUTPUT_TOKENS
    ranked = rerank(evidence, query=task, authority_first=True)
    selected = pack_without_splitting_citations(ranked, remaining * 0.65)
    summary = summarize_history(history, remaining * 0.35, keep_constraints=True)
    return fixed + tokenize(selected) + tokenize(summary)
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `收集系统规则、任务与证据` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `压缩历史但保留约束` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `记录 token、命中率与遗漏错误` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **自主性** | 只在路径无法枚举时让模型动态决策 | 稳定路径优先 workflow，开放局部才用 loop |
| **状态** | 显式保存目标、步骤、观察、预算与终止条件 | 状态可序列化、可恢复、可审计 |
| **上下文** | 区分规则、任务、证据、记忆和工具结果 | 按优先级装配并测量遗漏与污染 |
| **终止** | 成功、失败、取消、超时和预算耗尽都有明确出口 | 检测重复动作与无进展循环 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 更长上下文不必然更好，中间信息遗失和噪声会降低决策质量。
- 摘要模型节约主模型成本，但引入额外延迟和摘要错误。
- 工具 schema 太多会占窗口并降低选择准确率，应按状态动态暴露。

### 6.1 落地检查表

- 显式设置步骤、token、费用、时间与工具调用上限。
- 模型不直接拥有权限；所有工具调用经过 Schema 与策略校验。
- 状态、动作、观察和终止原因可持久化与重放。
- 检测重复动作、无进展与上下文污染，必要时请求人工接管。

---

## 7. 常见故障

1. 截断时删除了系统约束或用户最新修改。
2. 把网页中的提示注入文本放入高优先级指令区。
3. 工具返回整份日志或数据库结果，挤掉真正的任务证据。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `收集系统规则、任务与证据` 逐步检查到 `记录 token、命中率与遗漏错误`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**截断时删除了系统约束或用户最新修改。**
