# 隐私、脱敏与合规

> **先记住**：Agent 会汇集对话、企业数据、工具结果和长期记忆，隐私治理应覆盖收集、传输、模型调用、存储、展示和删除全生命周期。

---

## 1. 它在解决什么问题？

Agent 会汇集对话、企业数据、工具结果和长期记忆，隐私治理应覆盖收集、传输、模型调用、存储、展示和删除全生命周期。原则是目的限定、数据最小化、租户隔离、敏感信息检测与脱敏、可配置保留期，并为模型供应商和跨境处理建立明确的数据契约。

读这一节时，先带着三个问题：

1. **核心对象是什么？** 哪些状态会在处理过程中发生变化？
2. **主链路怎么走？** 一次处理从哪里开始，到哪里才算结束？
3. **边界在哪里？** 数据量、并发或故障出现后，哪一环最先承压？

## 3. 核心机制，逐层拆开

### 数据分类与最小化

识别个人信息、密钥、健康、财务和企业机密，只采集完成任务必要字段。发送模型前裁剪无关列和历史，日志默认不记录完整提示、工具参数与原文。

### 脱敏与可逆性

展示和分析使用掩码或令牌化，真正不需要时做不可逆删除。需要恢复原值的 token vault 与业务数据分离授权；脱敏规则要处理自由文本和文件，不只结构化字段。

### 生命周期与权利

记录处理目的、来源、法律依据、地域、保留期和下游处理方。支持访问、更正、导出和删除请求，并传播到向量索引、缓存、备份和记忆系统。

## 4. 用一段实现把概念落地

下面只保留最关键的主干。阅读时，把代码与上一节的流程一一对应：

```python
classified = classifier.scan(payload)
minimized = payload.pick(allowed_fields[purpose])
redacted = pii.redact(minimized, strategy={
    "email": "tokenize",
    "phone": "mask",
    "government_id": "drop",

audit.record(subject=user.id, purpose=purpose, categories=classified.categories)
model_response = approved_model(region=user.region).generate(redacted)
retention.schedule_delete(model_response.id, policy.for_purpose(purpose))
```

- **从哪里开始**：识别数据分类与处理目的
- **关键状态变化**：按地区和租户控制存储 / 传输
- **怎样才算完成**：到期删除并支持主体请求

## 5. 怎么选才不容易错

| 关注点 | 怎么理解 | 怎么验证 |
|---|---|---|
| **信任边界** | 用户、网页、文档、模型和工具输出默认不同信任级别 | 不可信数据不能获得指令优先级 |
| **授权** | 身份、动作、资源和字段都要校验 | 短期能力令牌替代共享长期密钥 |
| **隔离** | 高风险执行进入临时沙箱 | 文件、网络、进程、资源和产物同时受控 |
| **响应** | 检测、阻断、取证、吊销和回归是一套流程 | 红队用例进入持续安全门禁 |

没有脱离场景的“最佳方案”。先写清数据规模、读写比例、故障模型和延迟目标，再做选择。

---

## 6. 放进真实系统，还要考虑什么

- 本地模型可减少第三方传输，但仍需内部访问控制和日志治理。
- 过度脱敏会破坏任务效果，可在可信执行边界内使用最小必要原文。
- 审计需要保留证据，与删除权之间要由合规策略明确平衡。

### 上线前检查

- 网页、邮件、附件和检索文档一律标记为不可信数据。
- 凭证短期化、按任务和资源下发，工具端独立验权。
- 代码与浏览器执行进入无长期密钥的临时沙箱。
- 审计记录谁在何时批准了什么动作，并可快速吊销与回滚。

---

## 7. 常见误区与排查

### 容易踩的坑

1. 只删除主数据库记录，向量库和提示缓存仍保留内容。
2. 调试日志记录完整访问令牌和用户附件。
3. 模型供应商配置变化后数据被用于训练，却未重新评审。

### 出现问题时，按这个顺序看

1. **还原现场**：确认受影响的请求、数据、时间窗，以及最近是否有发布或流量变化。
2. **沿链路定位**：从“识别数据分类与处理目的”一路检查到“到期删除并支持主体请求”，找出状态第一次偏离预期的位置。
3. **验证修复**：用最小复现、压力测试或故障注入证明问题消失，同时保留回滚方案。
