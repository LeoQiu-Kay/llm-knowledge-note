# RAG 评测与数据闭环

> **一句话定位**：RAG 评测要拆分摄取、召回、重排、生成和业务结果，使用带证据与不可回答样本的真实数据集。

---

## 1. 先给结论

RAG 评测要拆分摄取、召回、重排、生成和业务结果，使用带证据与不可回答样本的真实数据集。离线指标用于快速比较，在线实验与用户反馈验证业务价值；所有失败案例应进入可分类的数据闭环，驱动文档修复、查询策略、模型和提示迭代。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 分层指标

检索关注 Recall@K、MRR、nDCG 和权限正确性；生成关注答案正确性、faithfulness、引用覆盖、拒答与格式；系统还要测延迟、成本和新鲜度。端到端分数不能替代分层诊断。

### 评测集

从真实查询采样并覆盖热门、长尾、多跳、歧义、时效、越权和不可回答问题。标注相关 chunk、关键事实与允许答案，按版本冻结测试集并防止训练污染。

### 在线闭环

收集显式评价、引用点击、追问、人工修改和任务成功信号，结合 A/B 或交错实验。负反馈先分类根因，再转为回归样本，避免只改提示掩盖数据问题。

## 3. 工作流程与关键路径

```text
[标注问题、答案与证据]
    │
    ▼
[分别评估检索和生成]
    │
    ▼
[按失败类型切片]
    │
    ▼
[线上采集无答案与纠错反馈]
    │
    ▼
[回流到切分、索引、重排和提示版本]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`标注问题、答案与证据` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`分别评估检索和生成` 与 `按失败类型切片` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`回流到切分、索引、重排和提示版本` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
retrieval = evaluate_retrieval(
    expected_evidence=case.evidence_ids,
    returned_evidence=run.retrieval_ids,
    metrics=["recall@5", "mrr", "ndcg@10"],
)
generation = evaluate_answer(
    answer=run.answer,
    reference=case.reference,
    checks=["faithfulness", "citation_precision", "completeness"],
)
dashboard.record(case.slice, retrieval, generation, version=run.pipeline_version)
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `标注问题、答案与证据` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `按失败类型切片` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `回流到切分、索引、重排和提示版本` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **召回** | 先保证正确证据能进入候选集 | 用 recall@k、MRR 和无答案集验证 |
| **排序** | 词法、向量与图检索各有盲区 | 按查询类型切片比较，不只看总分 |
| **生成** | 回答必须受证据约束并绑定引用 | 逐 claim 验证引用支持关系 |
| **新鲜度与权限** | 索引必须携带版本、时间和 ACL | 检索前过滤，删除与更新可追踪 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- LLM-as-judge 扩展性好，但要校准偏差、位置效应和领域能力。
- 人工标注质量高却昂贵，可用于金标集和争议样本。
- 优化单一正确率可能牺牲拒答、安全或延迟，需多目标门槛。

### 6.1 落地检查表

- 文档、chunk、embedding、索引和提示版本可追踪。
- 权限在检索阶段过滤，不能只靠生成阶段提醒模型保密。
- 分别评估召回、排序、事实性、引用精度和无答案拒答。
- 建立删除、更新、反馈和错误证据回流的数据闭环。

---

## 7. 常见故障

1. 只评最终答案，无法知道是没召回还是生成没用证据。
2. 评测集全是能回答的问题，系统学会任何情况都作答。
3. 线上反馈直接作为真值，忽略用户误点和选择偏差。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `标注问题、答案与证据` 逐步检查到 `回流到切分、索引、重排和提示版本`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**只评最终答案，无法知道是没召回还是生成没用证据。**
