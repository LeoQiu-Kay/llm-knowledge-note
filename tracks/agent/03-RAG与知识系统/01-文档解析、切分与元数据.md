# 文档解析、切分与元数据

> **一句话定位**：RAG 的上限首先由摄取质量决定：需要正确解析正文、表格、图片和层级结构，按语义与检索用途切分，并为每个 chunk 保存文档、章节、版本、时间、权限和定位信息。

---

## 1. 先给结论

RAG 的上限首先由摄取质量决定：需要正确解析正文、表格、图片和层级结构，按语义与检索用途切分，并为每个 chunk 保存文档、章节、版本、时间、权限和定位信息。切分不是固定字符数问题，而是召回完整性、精确度和生成上下文成本的权衡。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 解析与规范化

针对 PDF、HTML、Office 和扫描件选择解析器，保留标题、列表、表格关系和页码；去除导航、页眉页脚与重复模板，同时保留原始文件哈希供追溯。

### 切分策略

优先按标题、段落、代码块和表格等语义边界切分，再设置最大长度与少量重叠。事实密集内容用小块，流程和论证需要更大上下文，可保存父子 chunk 以小块召回、大块生成。

### 元数据与版本

记录 source、document_id、section_path、updated_at、language、tenant、ACL 和 parser_version。更新时按稳定 ID 增量替换，删除源文档要同步清理索引。

## 3. 工作流程与关键路径

```text
[解析原始文档]
    │
    ▼
[保留标题、表格与页码结构]
    │
    ▼
[按语义和长度切分]
    │
    ▼
[补充来源、权限和时间元数据]
    │
    ▼
[嵌入并写入可版本化索引]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`解析原始文档` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`保留标题、表格与页码结构` 与 `按语义和长度切分` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`嵌入并写入可版本化索引` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
document = parser.parse(blob, keep_pages=True, keep_tables=True)
for section in document.semantic_sections():
    for chunk in split(section, target_tokens=450, overlap_tokens=60):
        index.upsert(
            id=stable_chunk_id(document.version, chunk.path, chunk.offset),
            text=chunk.text,
            metadata={
                "source": document.uri, "page": chunk.page,
                "heading": chunk.path, "acl": document.acl,
                "valid_at": document.updated_at,
            },
        )
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `解析原始文档` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `按语义和长度切分` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `嵌入并写入可版本化索引` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **召回** | 先保证正确证据能进入候选集 | 用 recall@k、MRR 和无答案集验证 |
| **排序** | 词法、向量与图检索各有盲区 | 按查询类型切片比较，不只看总分 |
| **生成** | 回答必须受证据约束并绑定引用 | 逐 claim 验证引用支持关系 |
| **新鲜度与权限** | 索引必须携带版本、时间和 ACL | 检索前过滤，删除与更新可追踪 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 重叠可缓解边界丢失，但会造成重复召回和索引膨胀。
- OCR 提高覆盖率，也可能引入数字、表格和专有名词错误，需要质量阈值。
- 通用切分简单，领域专用解析效果更好但维护成本更高。

### 6.1 落地检查表

- 文档、chunk、embedding、索引和提示版本可追踪。
- 权限在检索阶段过滤，不能只靠生成阶段提醒模型保密。
- 分别评估召回、排序、事实性、引用精度和无答案拒答。
- 建立删除、更新、反馈和错误证据回流的数据闭环。

## 7. 常见故障

1. 表格被逐行打散，生成答案失去列关系。
2. 文档更新只新增新 chunk，旧版本仍被检索。
3. 索引未携带 ACL，检索后才过滤导致越权与召回不足。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `解析原始文档` 逐步检查到 `嵌入并写入可版本化索引`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**表格被逐行打散，生成答案失去列关系。**
