# 混合检索、重排与查询改写

> **一句话定位**：高质量检索通常把 BM25 等词法召回与向量召回融合，再用重排模型对较小候选集精排。

---

## 1. 先给结论

高质量检索通常把 BM25 等词法召回与向量召回融合，再用重排模型对较小候选集精排。查询改写可补全缩写、拆分多跳问题或生成多个检索视角，但必须保留原意；完整链路应分别评估召回、重排和最终答案，不能只看一次相似度。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

---

## 2. 核心原理

### 混合召回

词法检索擅长专有名词、编号和精确短语，向量检索擅长语义改写。可用 Reciprocal Rank Fusion 等方法合并不同分数量纲的排名，并对字段和来源设权重。

### 重排

Cross-encoder 或生成式重排器联合读取 query 与候选，相关性通常更高但成本更大。先宽召回几十到几百条，再重排到生成所需少量证据，并设置超时降级。

### 查询改写

规范化实体、扩展同义词、将复杂问题拆成子查询，或用假设答案辅助召回。所有改写要与原查询一起保留，防止模型臆造条件后只检索错误方向。

## 3. 工作流程与关键路径

```text
[理解查询意图]
    │
    ▼
[生成词法与语义检索请求]
    │
    ▼
[BM25 和向量召回并集]
    │
    ▼
[RRF / Cross-Encoder 重排]
    │
    ▼
[按证据覆盖选择上下文]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`理解查询意图` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`生成词法与语义检索请求` 与 `BM25 和向量召回并集` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`按证据覆盖选择上下文` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
dense = vector_index.search(embed(query), top_k=50)
sparse = bm25.search(query, top_k=50)

def rrf(rank, k=60):
    return 1.0 / (k + rank)

fused = reciprocal_rank_fusion(dense, sparse, score_fn=rrf)
rewritten = query_rewriter.add_required_entities(query, conversation)
return cross_encoder.rerank(rewritten, fused[:40])[:8]
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `理解查询意图` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `BM25 和向量召回并集` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `按证据覆盖选择上下文` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **召回** | 先保证正确证据能进入候选集 | 用 recall@k、MRR 和无答案集验证 |
| **排序** | 词法、向量与图检索各有盲区 | 按查询类型切片比较，不只看总分 |
| **生成** | 回答必须受证据约束并绑定引用 | 逐 claim 验证引用支持关系 |
| **新鲜度与权限** | 索引必须携带版本、时间和 ACL | 检索前过滤，删除与更新可追踪 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 多路召回提高覆盖，也增加重复、延迟和融合调参成本。
- 重排模型应在真实领域数据上验证，通用排行榜效果不能直接代表线上。
- 多查询适合复杂问题，简单事实查询会徒增成本。

### 6.1 落地检查表

- 文档、chunk、embedding、索引和提示版本可追踪。
- 权限在检索阶段过滤，不能只靠生成阶段提醒模型保密。
- 分别评估召回、排序、事实性、引用精度和无答案拒答。
- 建立删除、更新、反馈和错误证据回流的数据闭环。

---

## 7. 常见故障

1. 直接线性相加 BM25 与向量分数，量纲不同导致一路完全支配。
2. 重排只看片段文本，没有标题、时间和权限元数据。
3. 查询改写删除了否定词或关键约束，召回结果方向相反。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `理解查询意图` 逐步检查到 `按证据覆盖选择上下文`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**直接线性相加 BM25 与向量分数，量纲不同导致一路完全支配。**
