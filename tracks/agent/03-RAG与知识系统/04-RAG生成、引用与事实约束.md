# RAG 生成、引用与事实约束

> **一句话定位**：RAG 生成阶段要把检索证据作为低信任数据提供给模型，要求基于证据回答、区分事实与推断，并生成可验证引用。

---

## 1. 先给结论

RAG 生成阶段要把检索证据作为低信任数据提供给模型，要求基于证据回答、区分事实与推断，并生成可验证引用。系统还需检测证据不足、相互冲突和过期，必要时拒答或请求澄清；有引用不等于有依据，引用必须真正支持对应陈述。

### 面试答题路线

回答这类题不要从名词堆砌开始，按下面四步展开最稳：

1. **先定边界**：它解决什么问题，不解决什么问题。
2. **再讲机制**：把核心数据结构、状态机或调用链讲清楚。
3. **补充取舍**：说明复杂度、正确性、资源和可维护性的代价。
4. **落到生产**：给出超时、幂等、观测、压测与回滚方案。

## 2. 核心原理

### 证据编排

对证据去重、按主题分组并附 source_id、标题、时间和定位。提示中明确外部内容不得覆盖系统规则，长文先选择相关段落而不是无差别塞入。

### 引用对齐

让模型按稳定 source_id 引用，并在生成后校验引用存在、权限有效、文本蕴含陈述。句级引用比答案末尾罗列链接更易审计，关键结论可使用 NLI 或二次验证。

### 不足与冲突

定义最低证据阈值和时效要求；找不到答案时返回缺失信息而非依赖模型参数记忆。多来源冲突要展示差异、优先权威/最新来源或升级人工判断。

## 3. 工作流程与关键路径

```text
[检索可引用证据]
    │
    ▼
[按来源组织上下文]
    │
    ▼
[提示模型只基于证据回答]
    │
    ▼
[句子级绑定引用]
    │
    ▼
[验证引用是否真的支持结论]
```

### 3.1 每一步分别承担什么

- **入口与约束**：`检索可引用证据` 决定后续处理的语义、权限和容量边界。
- **核心决策**：`按来源组织上下文` 与 `提示模型只基于证据回答` 是最容易答成“只会背名词”的地方，要讲清状态如何变化。
- **执行与副作用**：中间步骤必须说明失败是否可重试、是否会重复，以及资源何时释放。
- **完成条件**：`验证引用是否真的支持结论` 不能只看“没有抛异常”，还要有业务结果、指标或持久化证据。

### 3.2 复杂度不只是一行大 O

面试里给出时间复杂度后，还要补三件事：**数据规模是否会放大常数项、最坏路径何时触发、资源上限在哪里**。生产环境更常被队列等待、锁竞争、网络、序列化、缓存失效或外部限流拖慢；因此复杂度分析必须和实际访问分布、尾延迟及容量模型一起讲。

## 4. 关键实现

下面的片段不是完整框架，而是把最关键的边界写出来：

```python
evidence = retriever.search(question, acl=user.acl)
answer = model.generate(
    question=question,
    evidence=[{"id": e.id, "text": e.text} for e in evidence],
    rules="Only claim facts supported by evidence; cite evidence ids per sentence.",
)
for claim in answer.claims:
    support = citation_checker.verify(claim.text, claim.citation_ids, evidence)
    if not support.entails:
        claim.mark_unsupported()
return answer
```

### 4.1 实现时盯住的状态

| 状态 | 需要回答的问题 |
|---|---|
| 输入 | `检索可引用证据` 是否已经校验语义、权限、大小与版本？ |
| 中间状态 | `提示模型只基于证据回答` 能否持久化、观测或在并发下保持不变量？ |
| 副作用 | 失败重试会不会重复执行？是否有幂等键、事务或补偿？ |
| 完成 | `验证引用是否真的支持结论` 由什么证据确认？调用方能否区分成功、部分成功与失败？ |

## 5. 对比与选型

| 决策维度 | 面试中要说清 | 生产验证 |
|---|---|---|
| **召回** | 先保证正确证据能进入候选集 | 用 recall@k、MRR 和无答案集验证 |
| **排序** | 词法、向量与图检索各有盲区 | 按查询类型切片比较，不只看总分 |
| **生成** | 回答必须受证据约束并绑定引用 | 逐 claim 验证引用支持关系 |
| **新鲜度与权限** | 索引必须携带版本、时间和 ACL | 检索前过滤，删除与更新可追踪 |

真正的选型结论应带条件：**在什么规模、读写比例、故障模型、SLO 和团队维护能力下选择它**。离开约束谈“谁更快”“谁更高级”没有工程意义。

## 6. 工程实践

- 严格只按证据回答可降低幻觉，但对开放建议类问题可能过度保守。
- 逐句验证质量更高，也增加模型调用和延迟。
- 引用原文片段有助核验，同时要遵守版权、隐私和展示长度限制。

### 6.1 落地检查表

- 文档、chunk、embedding、索引和提示版本可追踪。
- 权限在检索阶段过滤，不能只靠生成阶段提醒模型保密。
- 分别评估召回、排序、事实性、引用精度和无答案拒答。
- 建立删除、更新、反馈和错误证据回流的数据闭环。

## 7. 常见故障

1. 模型引用真实文档，但该文档并不支持对应数字。
2. 把检索文本中的恶意指令当成系统命令执行。
3. 证据来自旧政策，回答却使用现在时且不标日期。

### 7.1 推荐排查顺序

1. **先确认现象**：影响哪些请求、数据、租户与时间窗，是否与发布或流量变化相关。
2. **再沿关键路径定位**：从 `检索可引用证据` 逐步检查到 `验证引用是否真的支持结论`，不要跳过排队、缓存、代理或外部依赖。
3. **区分原因和结果**：高 CPU、线程多、token 多、连接满可能只是症状；用日志、指标、Trace 和状态快照互相印证。
4. **最后验证修复**：用最小复现、压力或故障注入证明问题消失，同时保留一键回滚。

最常见的错误是：**模型引用真实文档，但该文档并不支持对应数字。**
