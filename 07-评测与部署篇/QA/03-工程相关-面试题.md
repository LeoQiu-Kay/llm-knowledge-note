## Q1: TTFT、TPOT、吞吐量分别是什么？它们对应推理的哪个阶段？
> 难度 ⭐⭐ ｜ 高频 🔥🔥🔥

**三大核心指标**：

| 指标 | 全称 | 含义 | 对应阶段 | 计算特性 |
|---|---|---|---|---|
| **TTFT** | Time To First Token | 请求 → 收到首个 token 的耗时 | Prefill | compute-bound（计算密集）|
| **TPOT** | Time Per Output Token | 后续每个 token 的间隔 | Decode | memory-bound（带宽密集）|
| **吞吐量** | Throughput | 单位时间内 tokens 数 / 请求数 | 系统级 | 取决于 batch、并发 |

**单请求体验**：

$$T_{\text{total}} = \text{TTFT} + n_{\text{out}} \times \text{TPOT}$$

**直觉**：
- chat 体验关心 TTFT 和 TPOT（首字快 + 后续流畅）
- 批处理只关心吞吐量
- 流式输出能"隐藏"长 TPOT（用户边读边等）

**追问：为什么 prefill 是 compute-bound 而 decode 是 memory-bound？** Prefill 一次处理几千 token，矩阵 × 矩阵，算术强度高，吃满算力；Decode 一次只生成 1 token，每步都把全部模型权重从 HBM 读到 SRAM，但实际计算量很少，带宽是瓶颈。

## Q2: 吞吐量和延迟为什么矛盾？工程上怎么平衡？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

**矛盾本质**：

```
大 batch → 多请求共享一次权重读取 → 吞吐 ↑，但每个请求等所有人完成 → TPOT ↑
小 batch → 每请求独占 GPU 响应快 → TPOT ↓，但 GPU 没吃饱 → 吞吐 ↓
```

数学上，decode 每 step 耗时近似为：

$$t_{\text{step}} \approx \frac{\text{模型权重大小}}{\text{HBM 带宽}} + O(\text{batch})$$

第一项是固定开销（无论 batch 多大都要读一遍权重），第二项随 batch 线性增长但远小于第一项 → batch 翻倍，吞吐几乎翻倍，TPOT 涨幅很小。**直到 KV Cache 占满显存或第二项变主导**。

**工程平衡**：
- **Chat / 在线**：偏 latency。batch 上限 16-32，开 Continuous Batching、Chunked Prefill
- **离线批处理**：偏 throughput。batch 拉到 256+，关心总耗时
- **混合负载**：PD 分离 + 优先级调度

**追问：怎么决定 batch 上限？** 算 KV Cache 显存需求：$\text{KV} = 2 \times L \times n_{kv} \times d_h \times \text{seq\_len} \times \text{batch} \times \text{dtype}$，留 10-20% buffer。OOM 比慢更可怕。

## Q3: 怎么降低 TTFT？列举 5 种手段
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

TTFT 由 prefill 决定，是 compute-bound。

| 手段 | 原理 | 典型收益 |
|---|---|---|
| **Prefix Caching** | 命中前缀的 KV Cache 直接复用 | 命中后 TTFT 降 80%+ |
| **Chunked Prefill** | 长 prompt 切 chunk 与 decode 交错 | P99 TTFT 显著下降 |
| **PD 分离**（Prefill-Decode Disaggregation）| prefill / decode 在不同集群 | 长 prompt 不阻塞 decode |
| **缩短 prompt** | 删冗余 system prompt、压缩 few-shot | 线性下降 |
| **升级硬件** | H100 prefill 比 A100 快 2-3× | 硬上限拉高 |

**Chunked Prefill 细节**：没有 Chunked Prefill 时，一个 32K 长 prompt 占满 GPU 几百 ms，期间所有正在 decode 的请求 TPOT 飙升。Chunked Prefill 把 prefill 切 512 token 的 chunk，每 step 既跑 prefill chunk 又跑 decode batch，公平调度 → 既不让长请求"饿死短请求"，又不让短请求"饿死长请求"。

**追问：什么时候 PD 分离才划算？** 大规模部署（数百卡以上）且配高速网络（RDMA / NVLink），否则 prefill 结果跨节点传输 KV Cache 的开销吃掉收益。

## Q4: 怎么降低 TPOT？列举 5 种手段
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

TPOT 由 decode 决定，是 memory-bound，瓶颈在权重读取带宽。

| 手段 | 原理 | 典型收益 |
|---|---|---|
| **权重量化**（W4A16、FP8）| 模型小一半 → 读取快一半 | TPOT 降 30-50% |
| **KV Cache 量化**（FP8 / INT8）| 每 step 读 KV 也省一半 | 长 context 下显著 |
| **投机解码**（Speculative Decoding / EAGLE）| 小模型 draft N token，大模型 verify | TPOT 降 2-3× |
| **MoE 架构** | 激活参数少（DeepSeek-V3 总 671B 激活 37B）| 实际计算量大降 |
| **升级硬件** | H100 HBM3 3.35 TB/s vs A100 HBM2e 2 TB/s | 线性提升 |

**投机解码原理**：
1. 小 draft 模型快速生成 N 个候选 token（如 N=4）
2. 大目标模型把这 N 个 token 拼一起，一次 forward 同时算 N+1 个位置的概率
3. 从左到右验证：draft 和大模型一致就接受，第一个不一致处截断、用大模型该位置输出
4. 期望每次 forward 接受 2-3 个 token → TPOT 降 2-3×

**关键**：第 2 步那次 forward 仍是 memory-bound 一次读权重，但产出多个 token，"摊薄"了 decode 成本。

**追问：投机解码为什么不能无限加速？** 接受率受 draft 模型质量制约（一般 50-80%）；N 越大草稿越长但接受概率指数下降，最优 N 通常 3-5。

## Q5: SLA 是什么？P50 / P95 / P99 延迟分别意味着什么？
> 难度 ⭐⭐ ｜ 高频 🔥🔥

**SLA**（Service Level Agreement）：服务等级承诺。

**典型 LLM 服务 SLA**：
1. **可用性**：99.9%（每月停机 < 43 分钟）/ 99.99%（< 4 分钟）
2. **TTFT P95** < 1s
3. **TPOT P95** < 100ms（>10 tokens/s）
4. **错误率** < 0.1%
5. **吞吐保证**：承诺 QPS（Queries Per Second）

**百分位延迟**：把所有请求按延迟排序后：
- **P50**：中位数延迟（50% 请求快于此）
- **P95**：95% 请求快于此（剩 5% 慢请求）
- **P99**：99% 请求快于此（**尾延迟**，最难优化）

**为什么关心 P99 而不是平均**：用户记得最慢的那一次。P99 反映极端情况是否还能保证体验。

**长尾来源**：
- 长 prompt（prefill 时间长）
- 调度问题（batch 排队）
- 显存压力 → swap 或 preempt
- GC / 节点抖动

**优化方向**：
- **Chunked Prefill**：降 P99 TTFT
- **优先级调度**：保护关键请求
- **拒绝策略**：满载时拒绝新请求，避免雪崩（fail fast 优于 fail slow）

**追问：P50 30ms、P99 2s 这种长尾正常吗？** 不正常。健康系统 P99 通常 < 3 × P50。两个数量级差距说明有调度或显存问题。

## Q6: 流式输出（Streaming）的实现方式？为什么用户感知更快？
> 难度 ⭐⭐ ｜ 高频 🔥🔥

**实现方式**：
1. **SSE**（Server-Sent Events）：HTTP 长连接，服务端持续推送 `data:` 行
2. **WebSocket**：双向通信，更灵活但复杂
3. **gRPC streaming**：内部服务常用

**OpenAI API 协议示例**：
```
data: {"choices": [{"delta": {"content": "Hello"}}]}
data: {"choices": [{"delta": {"content": " world"}}]}
data: {"choices": [{"delta": {"content": "!"}}]}
data: [DONE]
```

每生成一个 token 就推一行 `data:`，前端用 EventSource 监听。

**为什么"感觉快"**：
- 总耗时不变（TTFT + n × TPOT 没变）
- 但用户在 TTFT 之后就看到首字 → 心理等待时间大幅缩短
- 边读边等，几乎察觉不到 TPOT

**对比**：
- 流式：TTFT 0.5s 就开始出字，体感"瞬间响应"
- 非流式：等 10s 一次性输出，体感"卡死了"

**追问：流式输出和函数调用（function calling）冲突吗？** 不冲突，但实现复杂。模型可能边生成边判断要不要调工具，流式协议要支持 partial tool call delta（OpenAI 协议有 `tool_calls: [{...}]` 的增量字段）。

## Q7: 多卡部署的 TP 怎么选？跨节点 TP 行不行？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

**TP**（Tensor Parallel）大小决定单请求 latency：
- TP 越大 → 单请求计算分摊到更多卡 → latency 越低
- 但 TP 越大 → 通信开销越大、卡数越多 → 成本上升

**经验配置**：

| 模型规模 | 推荐 TP | 卡 |
|---|---|---|
| 7-13B | TP=1 | 单卡 A100/H100 |
| 70B | TP=2（80GB H100）或 TP=4（40GB A100）| 单节点内 |
| 175B+ | TP=4 或 8 | 单节点 8 卡内 |
| 671B（DeepSeek-V3）| TP=8 + EP 或多节点 | 多节点 |

**跨节点 TP 为什么不行**：
- TP 每个 attention/FFN 层都要 all-reduce 同步
- 节点内 NVLink 带宽 ~900 GB/s（H100 NVLink 4.0）
- 节点间 RDMA InfiniBand ~50-200 GB/s，**慢一个数量级**
- TP 跨节点 → 通信成为绝对瓶颈，速度反而比 TP=8 单节点慢

**正确做法**：跨节点用 **PP**（Pipeline Parallel）或 **EP**（Expert Parallel for MoE），通信量少得多。

**追问：推理时 PP 为什么不流行？** PP 需要"流水线"才高效，而推理 decode 阶段一次只走一步，PP 各 stage 大部分时间在等 → bubble 严重。除非超大模型实在装不下，否则单节点 TP 是首选。

## Q8: 模型并行（TP）vs 多 replica 部署，怎么选？
> 难度 ⭐⭐ ｜ 高频 🔥🔥

| | TP（单请求跨多卡）| 多 replica（每卡/每组卡一份模型）|
|---|---|---|
| 目的 | 降单请求 latency | 增容量、增并发 |
| 适用 | 大模型装不下单卡，或追求 latency | 小模型，或 QPS 要求高 |
| 通信 | 每层 all-reduce，开销大 | 几乎无（请求级负载均衡）|
| 扩缩容 | 复杂（重启） | 简单（加 pod）|

**典型生产部署模式**：
```
70B 模型，单节点 8 × H100：
  方案 A: 4 个实例 × TP=2  → 4 路并发，单请求中等延迟
  方案 B: 2 个实例 × TP=4  → 2 路并发，单请求低延迟
  方案 C: 8 个实例 × TP=1  → ❌ 70B 装不下单卡
```

**自动扩缩容**：K8s + HPA（Horizontal Pod Autoscaler）根据 QPS / 队列长度自动加减 replica。

**追问：什么场景该用 TP=8 而不是 4 × TP=2？** 单请求 latency 极致敏感（如实时对话、agent 链路），且 QPS 不高（因为单实例 batch 上限有限）；多数 chat 场景 TP=2 + 多 replica 性价比最高。

## Q9: 部署需要监控哪些指标？关键告警阈值？
> 难度 ⭐⭐ ｜ 高频 🔥🔥

**两类指标**：

**业务指标**：
- QPS、TTFT P50/P95/P99、TPOT、错误率、token 消耗（输入/输出）

**系统指标**：
- GPU 算力利用率（SM）、显存利用率
- GPU 带宽利用率（HBM 实际带宽 / 标称）
- KV Cache 占用率
- 队列长度（pending requests）
- 单 batch 内 tokens 数（batch size 实际值）
- Power / 温度

**关键告警**：
| 指标 | 阈值 | 含义 |
|---|---|---|
| GPU 利用率 > 95% 持续 5min | 容量告急，需扩容 |
| 显存使用率 > 90% | OOM 风险 |
| KV Cache 占用 > 85% | 即将驱逐请求 |
| 队列长度 > 100 持续 1min | 请求堆积 |
| TTFT P99 > SLA × 1.5 | SLA 即将违约 |
| 错误率 > 1% | 异常请求或服务故障 |

**工具栈**：
- **vLLM 自带 Prometheus metrics**（`/metrics` endpoint）
- **DCGM**（NVIDIA Data Center GPU Manager）：GPU 硬件指标
- **Grafana**：可视化 dashboard
- **AlertManager / PagerDuty**：告警分发

**追问：怎么排查"GPU 利用率高但吞吐低"？** 可能是 prefill / decode 调度不均（开 Chunked Prefill）、batch 没充分利用（看 batch tokens 数指标）、或者全在算 KV Cache attention 但没产出（看 active sequences 数）。

## Q10: 部署常见 5 大问题怎么排查和解决？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

| 问题 | 现象 | 排查 | 解决 |
|---|---|---|---|
| **OOM** | 显存爆，服务挂 | 看 max_num_seqs、max_model_len | 降并发、限 max_tokens、加 KV Cache 量化 |
| **首请求慢** | 启动后第一个请求几秒 | CUDA Graph、kernel JIT 编译 | 启动后跑 warmup（10 个 dummy 请求）|
| **请求堆积** | 队列暴涨、TTFT 飙升 | 突发流量 / GPU 不够 | 拒绝过载（return 429）、加 replica、限队列长度 |
| **GPU 利用率低** | 显存有空、吞吐不行 | batch 太小、prefill 阻塞 | 调 Continuous Batching 参数、开 Chunked Prefill |
| **输出乱码 / 错误** | 输出和模型质量不符 | 量化精度不够、tokenizer 版本错 | 验证 chat template、提高量化精度、对齐 tokenizer |

**满载场景的核心原则**：**fail fast**，宁愿快速拒绝部分请求，也不要让队列无限堆积导致全部用户超时（雪崩）。

**追问：怎么压测推理服务？** 主流工具：
- `vllm.benchmarks.benchmark_serving`：vLLM 官方，模拟真实分布
- `wrk` + 自定义 Lua 脚本：通用 HTTP 压测
- `k6`：JS 脚本化、易出报告
- 压测要覆盖：稳态 QPS、突发 burst、长 prompt + 短 prompt 混合
