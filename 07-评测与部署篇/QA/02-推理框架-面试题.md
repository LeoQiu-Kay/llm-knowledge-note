## Q1: 主流推理框架有哪些？怎么选型？
> 难度 ⭐⭐ ｜ 高频 🔥🔥🔥

**主流 5+1**：

| 框架 | 主导方 | 适用场景 | 关键技术 |
|---|---|---|---|
| **vLLM** | UC Berkeley + 社区 | 通用 GPU 服务（首选）| PagedAttention、Continuous Batching、Prefix Caching |
| **SGLang** | LMSYS + 社区 | 复杂程序流（agent、多请求）| RadixAttention、结构化输出 |
| **TensorRT-LLM**（TRT-LLM）| NVIDIA | 极致性能 GPU | 算子融合、FP8、In-flight Batching |
| **llama.cpp** | Georgi Gerganov | CPU / 边缘 / Apple Silicon | GGUF 量化、Metal 加速 |
| **HuggingFace TGI** | HuggingFace | HF 生态一站式 | Continuous Batching |
| **Ollama** | Ollama | 本地易用 | 基于 llama.cpp |

**选型指南**：
- **通用云端**：vLLM（社区活跃、覆盖全、迭代快）
- **极致性能 + NVIDIA 资源**：TensorRT-LLM
- **Agent / 结构化输出**：SGLang
- **本地 / 边缘 / Mac**：llama.cpp / Ollama
- **国产硬件**：昇腾 MindIE、LMDeploy（上海 AI Lab）

**追问：研究/快速实验用什么？** HuggingFace Transformers，功能全但慢、不适合上生产。

## Q2: vLLM 的核心三件套是什么？解决了什么问题？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

vLLM 的三大杀手锏：

**1. PagedAttention**（核心创新）
- 借鉴操作系统虚拟内存分页：KV Cache 切成固定 block（如 16 token/block）
- 解决了传统 KV Cache 的"连续显存预留 → 内存碎片"问题
- 显存利用率从 ~30% 提升到 ~90%
- 同一 GPU 能跑 2-4× 的并发请求

**2. Continuous Batching**（in-flight batching）
- 传统 static batching：等整个 batch 都生成完再下一个 step
- Continuous Batching：每个 decode step 重新组 batch，一个序列结束立刻被新请求替换
- 吞吐量提升 2-23× （论文数据）

**3. Automatic Prefix Caching**
- 跨请求复用相同前缀的 KV Cache（如 system prompt、few-shot examples）
- 命中前缀直接跳过 prefill，TTFT 大幅下降

**追问：PagedAttention 怎么处理 beam search 等共享 prefix？** block 级别引用计数，多个序列指向同一物理 block，类似 Linux 进程的 COW（copy-on-write），只在写时复制。

## Q3: SGLang 和 vLLM 比有什么独特优势？什么场景碾压 vLLM？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

**SGLang 的 4 大差异化**：

1. **RadixAttention**（基于 Radix Tree 的 KV Cache 复用）
   - vLLM 的 Prefix Caching 是"哈希前缀"
   - SGLang 用 Radix Tree 自动管理任意公共前缀，**更细粒度**、树搜索友好
2. **结构化输出**：原生支持 JSON Schema、正则约束生成（compressed FSM），比外挂 outlines 快
3. **前端 DSL**：Python 写复杂 prompt 流（fork、merge），多个分支共享 prefix
4. **某些场景比 vLLM 快 20-50%**

**碾压 vLLM 的场景**：
- **Agent 应用**：多轮调用、prompt 重复度高
- **Tree of Thoughts / 多分支搜索**：同一 prefix 派生多分支，RadixAttention 全复用
- **结构化输出**：强约束 JSON / SQL 输出
- **多模态融合 prompt**：复杂模板

**追问：vLLM 在追赶吗？** 是的，vLLM 0.6+ 也在做 prefix caching 优化、structured output 支持，差距在缩小。但 SGLang 在多分支 KV 共享上仍领先。

## Q4: TensorRT-LLM 为什么快？又有什么劣势？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

**TRT-LLM**（NVIDIA 官方推理引擎）的快源于"全链路优化"：

**优势**：
1. **自定义 CUDA kernel**：针对 H100/B200 深度调优，比 PyTorch 通用 kernel 快
2. **算子融合**：把多个 ops 编译成一个 kernel，减少 kernel launch 开销
3. **FP8 / INT4 原生支持**：H100 的 FP8 Tensor Core 全开
4. **In-flight Batching**：类似 vLLM 的 Continuous Batching
5. **CUDA Graph**：减少 launch overhead

**典型快多少**：相同硬件下比 vLLM 快 20-50%（特定场景甚至 2×）。

**劣势**：
- **学习曲线陡**：C++ + TRT engine 编译流程
- **模型适配麻烦**：每换模型/改 prompt 模板都要重新 build engine
- **生态封闭**：只在 NVIDIA 卡上跑
- **迭代慢**：新模型支持比 vLLM 晚 1-2 周

**追问：什么时候值得用 TRT-LLM？** 生产部署、规模够大（数十/百卡级）、延迟/吞吐每提升 10% 都能省大钱、且团队有 NVIDIA C++ 工程能力。其他场景 vLLM 性价比更高。

## Q5: llama.cpp 是怎么做到 CPU 上跑大模型的？性能如何？
> 难度 ⭐⭐ ｜ 高频 🔥🔥

**llama.cpp** 是 Georgi Gerganov 的纯 C++ 实现，跨平台、低门槛。

**核心技术**：
1. **GGUF 量化格式**（GGML Universal Format）：单文件含模型 + tokenizer + 元数据
2. **多硬件 backend**：CPU（AVX/AVX-512）、Apple Metal、CUDA、ROCm、Vulkan
3. **mmap 加载**：模型文件直接内存映射，启动快、可共享
4. **激进量化**：Q2_K（~2.5 bits/param） → Q8_0（8 bit 近无损）

**GGUF 量化档位**（常考）：
| 档位 | 每参数 bits | 用途 |
|---|---|---|
| Q2_K | ~2.5 | 极端压缩，质量差 |
| Q4_K_M | ~4.8 | **推荐**（效果/显存平衡最佳）|
| Q5_K_M | ~5.5 | 质量更好 |
| Q8_0 | 8 | 几乎无损 |

**典型性能**：
- i9 CPU 跑 7B：5-15 tokens/s
- M3 Max + 70B Q4：~5 tokens/s
- 树莓派 5 跑 3B：1-2 tokens/s

**适用场景**：本地开发调试、边缘部署、Apple Silicon（Metal 加速）、数据合规要求高（不出本机）。

**追问：Ollama 和 llama.cpp 什么关系？** Ollama 是 llama.cpp 的封装，加上 model registry、CLI、Modelfile，主打"一行命令本地跑"。底层推理还是 llama.cpp。

## Q6: 部署的 3 大关键指标是什么？它们的关系？
> 难度 ⭐⭐ ｜ 高频 🔥🔥🔥

**3 大指标**：

| 指标 | 含义 | 决定因素 |
|---|---|---|
| **TTFT**（Time To First Token）| 请求 → 收到第一个 token 的时间 | prefill 阶段（计算密集，compute-bound）|
| **TPOT**（Time Per Output Token）| 后续每个 token 的间隔 | decode 阶段（带宽密集，memory-bound）|
| **吞吐量**（Throughput）| 单位时间总 tokens / 总请求数 | batch size、并发 |

**单请求总耗时**：

$$T_{\text{end-to-end}} = \text{TTFT} + n_{\text{out}} \times \text{TPOT}$$

其中 $n_{\text{out}}$ 是输出 token 数。

**典型 SLA**（Service Level Agreement）：
- TTFT P95 < 1s（chat 体验）
- TPOT < 100ms（流畅阅读速度，>10 tok/s）
- P99 < 2 × P50（尾延迟可控）

**追问：TTFT 多少算好？** P50 < 0.5s 优秀，<1s 可接受，>2s 用户体感差。RAG 场景因 prefill 长，TTFT 通常更高。

## Q7: 吞吐量和延迟的矛盾是什么？怎么平衡？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

**矛盾本质**：
- **大 batch** → 单 step 多个序列共享一次权重读取 → 吞吐高，但每个序列等待时间长 → **TPOT 升**
- **小 batch** → 每个序列响应快 → TPOT 低，但 GPU 没吃饱 → **吞吐低**

Decode 是 memory-bound：每生成一个 token 都要把全部模型权重从 HBM 读到 SRAM，**多个序列共享这次读取**就摊薄成本，所以大 batch 提升吞吐效率。但 batch 越大每个序列等 GPU 完成所有人的计算时间越长。

**平衡策略**（看业务）：
- **Chat / 在线对话**：偏 latency，batch 不要超过 32，开 Continuous Batching、Chunked Prefill
- **离线批处理 / 蒸馏数据生成**：偏 throughput，batch 拉到 256+，关心总耗时不关心单请求
- **混合负载**：用 PD（Prefill-Decode）分离，prefill 集群和 decode 集群独立调度

**关键洞察**：Decode 阶段 batch size 上限取决于 **KV Cache 占满显存的时机**——所以 PagedAttention 让 KV Cache 利用率高 → 同显存能装更多 batch → 吞吐天花板上升。

**追问：怎么决定 batch 上限？** 算 KV Cache 显存：$2 \times L \times n_{kv} \times d_h \times \text{seq\_len} \times \text{batch} \times \text{dtype}$，留出 10-20% buffer 给波动。

## Q8: 怎么降低 TTFT？常见手段有哪些？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

TTFT 由 prefill 决定，prefill 是计算密集（compute-bound）。

**5 大手段**：

1. **Prefix Caching**：命中前缀的 KV Cache 直接复用，跳过 prefill。典型收益：system prompt + few-shot 占 prompt 80%，命中后 TTFT 降 80%+
2. **Chunked Prefill**：长 prompt 切成 chunk（如 512 token/chunk），和 decode 交错调度
   - 不让单个长 prompt 阻塞后面短请求 → 降 P99 TTFT
3. **PD 分离**（Prefill-Decode Disaggregation）：prefill 和 decode 跑在不同集群
   - prefill 集群侧重算力（多 SM）
   - decode 集群侧重带宽（多 HBM）
   - 互不干扰，长 prompt 不影响在线 decode
4. **更短 prompt**：去冗余 system prompt、压缩 few-shot
5. **更快硬件**：H100 比 A100 prefill 快 2-3×（FP8 + 更高算力）

**追问：Chunked Prefill 为什么能降尾延迟？** 没有它的时候，一个 32K 长 prompt 进来会占满 GPU 几百 ms，期间所有 decode 都卡住，导致这些请求 TPOT 飙升。切 chunk 后，每个 step 既跑 prefill chunk 又跑 decode batch，公平调度。

## Q9: 怎么降低 TPOT 和提升吞吐量？
> 难度 ⭐⭐ ｜ 高频 🔥🔥

**降低 TPOT**（decode 阶段是 memory-bound，瓶颈在权重读取带宽）：
1. **量化权重**（W4A16、FP8）：模型小一半 → 读取快一半 → TPOT 降 30-50%
2. **量化 KV Cache**（FP8 / INT8 KV）：每 step 读 KV 也省一半
3. **投机解码**（Speculative Decoding，含 EAGLE）：小模型 draft 多 token，大模型一次 verify → 摊薄 forward 成本
4. **MoE 架构**：激活参数少，单 token 实际计算少（如 DeepSeek-V3 671B 总参激活仅 37B）
5. **FlashAttention**：attention 计算更高效
6. **更高带宽硬件**：H100 HBM3 3.35 TB/s vs A100 HBM2e 2 TB/s

**提升吞吐量**：
1. **Continuous Batching**（vLLM 标配）
2. **更大 batch size**（在 KV Cache 显存允许范围内）
3. **Prefix Caching**：跨请求复用 prefill
4. **量化**：单卡装更多并发
5. **更多 GPU**：横向扩 replica

**追问：投机解码为什么能加速？** 大模型一次 forward 能 verify N 个 draft token（拼一起做 attention 仍是 memory-bound 一次读权重），平均一次 forward 出 2-3 个 token，TPOT 降 2-3×。

## Q10: 推理框架的部署流程是什么？OpenAI-compatible API 是什么意思？
> 难度 ⭐⭐ ｜ 高频 🔥

**完整部署 6 步**：
1. **训练**：PyTorch / Megatron-LM 训出 checkpoint
2. **保存**：HuggingFace format / safetensors
3. **量化（可选）**：GPTQ / AWQ / FP8 / GGUF
4. **格式转换**：
   - vLLM / TGI：直接读 HF format
   - TRT-LLM：build engine（C++ 编译，几十分钟）
   - llama.cpp：转 GGUF
5. **服务化**：启动 server，暴露 HTTP API
6. **监控**：Prometheus + Grafana + 告警

**vLLM 启动示例**：
```bash
python -m vllm.entrypoints.openai.api_server \
    --model meta-llama/Llama-3-70B \
    --tensor-parallel-size 4 \
    --enable-prefix-caching
```

**OpenAI-compatible API**：所有主流框架（vLLM、SGLang、TGI、Ollama）都实现 OpenAI 的 `/v1/chat/completions` 接口协议。

好处：
- 客户端代码不用改，OpenAI SDK 直接换 base_url 即可切换后端
- 现有的 LangChain / LlamaIndex 等工具开箱即用
- 灰度切流量方便（同协议）

**追问：自定义模型能用 vLLM 服务吗？** 可以，继承 vLLM 的模型抽象类，实现 forward。社区有详细模板，主流架构（LLaMA-like、MoE）几小时能搞定。
