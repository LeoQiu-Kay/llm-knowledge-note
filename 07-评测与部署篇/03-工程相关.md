# 工程相关（吞吐 / 延迟 / 部署）

> LLM 工程化部署的关键指标与权衡。

---

## 1. TTFT vs TPOT vs 吞吐量

**关键指标定义**：

- **TTFT**（Time To First Token）：从请求到收到第一个 token 的时间
  - 由 prefill 决定
  - 影响用户感知响应速度

- **TPOT**（Time Per Output Token）：每个后续 token 的间隔
  - 由 decode 决定
  - 影响流畅度

- **吞吐量**（Throughput）：单位时间总 tokens / 总请求数

**关系**：
- 单请求体验：$\text{TTFT} + n \times \text{TPOT}$（$n$ 是输出 token 数）
- 系统容量：吞吐量

**矛盾**：
- 高吞吐（大 batch）→ TPOT 升
- 低 TPOT（小 batch）→ 吞吐降
- **工程是找平衡**

---

## 2. 怎么降低 TTFT？

1. **Prefix Caching**：命中前缀跳过 prefill
2. **Chunked Prefill**：长 prefill 不阻塞短请求
3. **PD 分离**：prefill 专用集群
4. **更短 prompt**：去冗余 system prompt
5. **更快硬件**：H100 比 A100 快 2-3×

## 3. 怎么降低 TPOT？

1. 量化 KV Cache
2. 量化权重
3. 投机解码
4. MoE（激活参数少）
5. FlashAttention
6. 更高带宽硬件

## 4. 怎么提高吞吐量？

1. Continuous Batching
2. 大 batch size
3. Prefix Caching
4. 量化（单卡装更多请求）
5. 更多 GPU

**关键洞察**：Decode 是 memory-bound，batch 越大每张卡能服务越多请求，**直到 KV Cache 占满显存**。

---

## 5. SLA（Service Level Agreement）

**典型 SLA**：
1. **可用性**：99.9% / 99.99%
2. **TTFT P95** < 1s
3. **TPOT P95** < 100ms
4. **错误率** < 0.1%
5. **吞吐**：保证 QPS

**P50 vs P99**：
- P50：中位数延迟
- P99：尾延迟（1% 最慢请求）
- 长尾延迟主要由长 prompt、调度问题、显存压力引起

**优化方向**：
- Chunked Prefill：降低 P99 TTFT
- 优先级调度：保护重要请求
- 拒绝策略：满载时拒绝新请求，避免雪崩

## 6. 流式（Streaming）输出

**实现**：通过 SSE（Server-Sent Events）或 WebSocket 逐 token 推送。

**OpenAI API 协议**：
```
data: {"choices": [{"delta": {"content": "Hello"}}]}
data: {"choices": [{"delta": {"content": " world"}}]}
data: [DONE]
```

**效果**：
- 流式：感觉快（首 token 就响应）
- 非流式：感觉慢（要等全部生成）

不降低总时间，但显著提升用户体验。

---

## 7. 多卡部署的 TP 选择

**TP（Tensor Parallel）大小**：
- 决定单请求 latency（更多卡 = 更快）
- 需要更多卡（成本高）

**经验**：
- 7-13B：单卡（TP = 1）
- 70B：TP = 2（80GB H100）或 TP = 4（40GB A100）
- 175B+：TP = 4 或 8

**TP 跨节点不可行**：节点间带宽不够。

---

## 8. 模型并行 vs 数据并行（推理）

| | TP（单请求跨多卡） | 多 replica（每卡一份模型） |
|---|---|---|
| 目的 | 降 latency | 增容量 |
| 适用 | 大模型 | 小模型或高 QPS |

**典型部署**：
- 大模型：单实例 TP + 多实例 replica
- 例：70B 模型 H100 TP=2，部署 4 个实例 → 8 卡集群

**自动扩缩容**：K8s + HPA 监控 QPS。

---

## 9. 监控指标

**业务指标**：
- QPS、TTFT、TPOT、错误率、token 消耗

**系统指标**：
- GPU 利用率（算力、显存、带宽）
- KV Cache 占用率
- 队列长度
- 单 batch tokens 数

**关键告警**：
- GPU 利用率 > 95%（容量告急）
- TTFT P99 > SLA
- 显存使用率 > 90%（OOM 风险）
- 队列堆积

**工具**：vLLM 自带 Prometheus metrics、DCGM、Grafana。

---

## 10. 成本估算

**关键变量**：
- 单卡时租成本（A100 ~$2/h，H100 ~$4/h，公有云）
- 单卡能服务的 QPS
- 平均 token 数 / 请求

**示例**：LLaMA-3-70B，TP=2，2 张 H100
- 单实例 ~50 QPS（短请求）
- 月成本：$2 \times \$4 \times 720 \times 30\% \approx \$1700$（按需折扣）
- 单 QPS 月成本：~$34
- 单 1M tokens 成本：估算几美元

**优化点**：
- 量化（FP8 / INT4）→ 单卡更多并发
- MoE → 激活小，并发高
- Prefix Caching → 计算复用
- 投机解码 → 加速

---

## 11. A/B 测试与灰度发布

**A/B 测试**：
- 把流量切分到不同模型版本
- 对比指标（满意度、点击率、成本）

**灰度发布**：
- 新模型先 1% → 10% → 50% → 100%
- 监控异常，出问题立即回滚

**工程注意**：
- 同请求双发到新旧模型（影响延迟）
- 或哈希用户 ID 分流
- KV Cache 不能跨版本共享

---

## 12. 部署常见问题

1. **OOM**：显存爆 → 降低 max concurrency、限制 max_tokens
2. **首请求慢**：CUDA Graph、kernel JIT 未预热 → 启动后跑 warmup 请求
3. **请求堆积**：突发流量 → 拒绝过载、加 replica、队列限长
4. **GPU 利用率低**：batch 小、prefill 阻塞 → 调 Continuous Batching 参数、Chunked Prefill
5. **奇怪输出**：量化精度不够、tokenizer 版本错 → 验证模型版本、提高精度

---

## 13. 最简记忆

```text
三大指标：
  TTFT（首 token，受 prefill 影响）
  TPOT（每 token 间隔，受 decode 影响）
  吞吐量（总 QPS）

吞吐 ↔ 延迟 矛盾：大 batch 高吞吐但 TPOT 升

降 TTFT：Prefix Caching + Chunked Prefill + PD 分离
降 TPOT：量化 + 投机解码 + MoE
增吞吐：Continuous Batching + 大 batch + Prefix Caching

监控：TTFT/TPOT P95 + GPU 利用率 + KV Cache 占用
```

## 🎯 高频追问

1. **延迟 vs 吞吐怎么平衡**？根据业务：chat 偏 latency，批 API 偏 throughput。

2. **TTFT 多少算好**？P50 < 0.5s 优秀，< 1s 可接受，> 2s 用户体验差。

3. **怎么压测**？vLLM 的 benchmark_serving.py，或 wrk + 自定义。

4. **多模态部署的特殊性**？图像编码占 prefill 大量计算，TTFT 长；可缓存图像 KV。

5. **PD 分离何时值得**？大规模部署（数百卡以上）+ 高速网络（RDMA）。
