## Q1: 长上下文的三大瓶颈是什么？分别用什么技术解决？
> 难度 ⭐⭐ ｜ 高频 🔥🔥🔥

| 瓶颈 | 现象 | 解法 |
|---|---|---|
| **计算** | Attention 是 $O(n^2)$，4K → 128K 计算量增 1024× | FlashAttention、稀疏 attention、SWA |
| **显存** | KV Cache 线性增长，128K 单请求几十 GB | GQA / MLA、INT8 量化、淘汰 |
| **效果** | 位置外推使训练范围外的位置编码失真 | YaRN / NTK / LongRoPE |

**衍生问题**：
- 训练成本（长序列每步算力翻倍）
- **lost in the middle**（中间信息漏）
- 长数据稀缺（128K 的高质量数据集少）

**追问：哪个瓶颈最难？** **效果**最难。计算/显存是工程问题，砸资源能解；效果涉及"位置编码外推"和"注意力稀疏化"的根本理论限制，名义 128K 但有效长度只有 30-60K 是常态。

## Q2: RoPE 的 Position Interpolation（PI）是怎么做的？为什么有效？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

**思路**：把推理位置"压回"训练范围。

$$m = m' \cdot \frac{L_{\text{train}}}{L_{\text{infer}}}$$

**符号**：
- $m'$ 推理时实际位置（如 $m' = 8000$）
- $m$ 缩放后给 RoPE 的"等效位置"（如训练长 2K、推理 8K → $m = 8000 \cdot 2K/8K = 2000$）

**为什么有效**：RoPE 的旋转角 $\theta_i \cdot m$ 是位置的连续函数；让推理位置"线性压缩"到训练区间，模型见过的频率分布就不会被外推到陌生区域。

**缺点**：
- 模糊**局部位置**：1 和 2 的"实际距离"被压缩成 0.25 和 0.5，短距离判别能力下降
- 需要少量长上下文 finetune 才能恢复局部能力

**追问：为什么直接外推不工作？** RoPE 的低频维度（大 $i$）在训练范围内只转过一小段；推理外推时旋转到训练**从未见过**的角度区域，模型在这里完全无经验，attention 模式崩坏。

## Q3: NTK-Aware Scaling 比 PI 强在哪？写出关键公式
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

**核心改进**：**不同频率维度差异化缩放**，而不是 PI 的"统一压缩"。

RoPE 频率公式：

$$\theta_i = b^{-2i/d}, \quad b = 10000$$

**符号**：
- $\theta_i$ 第 $i$ 对维度的旋转角速率
- $b$ base（典型 10000）
- 小 $i$ → 高频（短距离精细）
- 大 $i$ → 低频（长距离平滑）

**NTK-Aware**：改 base：

$$b' = b \cdot s^{d / (d - 2)}$$

**符号**：$s$ 扩展比（如 4× 上下文 → $s = 4$）。

**关键现象**：
- 高频维度：base 变化对它影响小（指数项 $-2i/d$ 很小） → **几乎不变** → 短距离精细保留
- 低频维度：base 变化对它影响大 → **大幅缩放** → 长距离覆盖扩展

**效果**：零样本即可扩展 2-4× 上下文，**比 PI 在短距离任务上效果更好**。

**追问：为什么叫"NTK-Aware"？** NTK = Neural Tangent Kernel。原作者从"保持模型对位置变化的响应核不变"角度推导出这个 scaling，等价于保持高频细节的同时延展低频范围。

## Q4: YaRN 是什么？为什么是当前主流方案？
> 难度 ⭐⭐⭐⭐ ｜ 高频 🔥🔥🔥

**YaRN**（Yet another RoPE extensioN）：组合多个技巧的"集大成"方案。

**三个关键改进**：

### 1. 频率维度差异化缩放（继承 NTK）

### 2. NTK-by-parts：分三段处理

| 频段 | 处理 | 理由 |
|---|---|---|
| 高频（小 $i$） | **保留**（不缩放） | 短距离精细不能损 |
| 中频 | 插值（PI 式） | 平滑过渡 |
| 低频（大 $i$） | 缩放（NTK 式） | 长距离覆盖扩展 |

按"波长 vs 训练上下文"的比例分段：波长 << $L_{\text{train}}$ 是高频，波长 >> $L_{\text{train}}$ 是低频。

### 3. 温度修正（Length Scaling）

缩放后 attention logits 的分布会偏，加一个温度因子：

$$\text{attn} = \text{softmax}\left(\frac{QK^T}{\sqrt{d} \cdot t}\right), \quad t = 0.1 \ln(s) + 1$$

**符号**：$s$ 扩展比，$t$ 随扩展比对数增长。

**效果**：
- **零样本** 4× 扩展
- 加少量短训能达 8-16×
- LLaMA-3 / Qwen-2/3 等主流模型采用

**追问：YaRN 和 LongRoPE 关系？** LongRoPE 是 YaRN 的进一步——用搜索算法找每个维度的最佳缩放因子，零样本可扩 200K+。但工程上 YaRN 已够用。

## Q5: Ring Attention 是什么？和 FlashAttention 关系？
> 难度 ⭐⭐⭐⭐ ｜ 高频 🔥🔥🔥

**目的**：训练超长序列时**跨设备**并行（单卡装不下整个序列的 QKV）。

**核心流程**：

1. 把序列分成 $N$ 段，分给 $N$ 张卡：第 $k$ 张卡持有 $Q_k, K_k, V_k$
2. 每张卡先用**本地** $K, V$ 算 attention
3. **环形传递** $K, V$ 到下一张卡（卡 $k$ 把 $K_k V_k$ 发给卡 $k+1$）
4. 卡 $k$ 用新收到的 $K, V$ 继续累积 attention
5. $N$ 步循环后，每张卡都用全部 $K, V$ 算过 $Q_k$ 的 attention
6. 类似 FlashAttention 的"在线 softmax"方式增量累积，不需存中间矩阵

**与 FlashAttention 关系**：
- **正交、互补**
- 每张卡内部用 **FlashAttention**（IO 优化，单卡块内高效）
- 跨设备用 **Ring** 传 K/V（分布式延展序列）
- 二者结合 = 超长序列高效训练

**应用**：
- Gemini 1.5（1M context）
- LLaMA-3 长上下文继续训练

**追问：Ring Attention 是不是只在训练用？** 主要训练用。推理一般单卡或张量并行，序列也短到能放下；只有极少数 1M+ 推理场景会用 Ring。

## Q6: KV Cache 量化和淘汰是怎么做的？StreamingLLM / H2O 的核心思想？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

**KV Cache 量化**：把 KV 从 BF16/FP16 压缩到 INT8 / INT4：
- INT8：显存减半，精度几乎无损
- INT4：显存 1/4，长上下文略损
- 工程上 KV 量化 + GQA/MLA 是主流组合

**KV Cache 淘汰**（不存所有 token）：

### StreamingLLM（attention sink）

观察：序列开头几个 token 拿到极多 attention（"sink"），中间/末尾按相对位置。

策略：永远保留 **开头 4 个 token + 最近窗口** → 中间淘汰。

适合：流式对话（无限长输入只看局部）。

### H2O（Heavy Hitter Oracle）

观察：少数 token 被频繁注意（"heavy hitter"），多数 token 注意力很低。

策略：维护一个"重要 token"队列，按 attention 累积分数淘汰冷门 token。

**对比**：

| 方案 | 保留策略 | 适用 |
|---|---|---|
| StreamingLLM | 开头 + 最近窗 | 流式对话 |
| H2O | 累积注意力高的 token | 长 QA |
| FastGen | 多策略混合 | 通用 |

**追问：淘汰会损失多少效果？** 取决于任务。NIAH 等"针在草堆"会显著掉（中间被淘汰）；流式对话掉得少（用户主要关心最近上下文）。

## Q7: "lost in the middle"现象是什么？怎么缓解？
> 难度 ⭐⭐ ｜ 高频 🔥🔥

**现象**（Liu et al., 2023）：把关键信息放在长上下文的不同位置：
- 开头：召回率高
- 末尾：召回率高
- **中间：召回率显著掉**（U 型曲线）

**原因猜测**：
1. **训练数据偏置**：网页/文档常把关键信息放头尾
2. **Attention sink**：开头几个 token 拿到不成比例的 attention
3. **因果 mask**：末尾自然受最多关注（看到全部历史）
4. **CLM 目标**：训练时主要预测末尾，偏向末尾依赖

**缓解方法**：
- 训练数据增强：刻意把关键信息放中间
- 改进位置编码（YaRN/LongRoPE）
- 检索增强（RAG）替代纯长上下文
- 引导式 prompt（"逐段总结再回答"）

**追问：NIAH 测试为什么仍能高分？** NIAH 的"针"是显著的短句（如"the magic number is 42"），与正文风格差异大；模型靠"形式差异"召回，不靠"位置记忆"。真实任务中信息混在同质化文本里，中间信息就漏了。

## Q8: 长上下文评测有哪些？NIAH、RULER、LongBench 各侧重什么？
> 难度 ⭐⭐ ｜ 高频 🔥🔥

| 评测 | 类型 | 特点 |
|---|---|---|
| **NIAH**（Needle in a Haystack） | 合成 | 长文档插一个"针"（短句），问针的内容；可视化为热图 |
| **RULER**（NVIDIA） | 合成 | 13 个任务，包括多针、变量追踪等，比 NIAH 全面 |
| **LongBench** | 真实 | QA、摘要、代码补全等真实任务 |
| **∞Bench** | 真实 | 100K+ 任务，更接近实际 |

**典型现象**：
- 100K 模型在 NIAH 上 ~100%（针的位置全召回）
- 但 LongBench 真实任务上效果远不如短上下文模型
- **名义长度 ≠ 有效长度**

**评估建议**：
- 不能只看 NIAH（太简单）
- RULER + LongBench 组合更可信
- 关心代码 → 跑 RepoBench；关心文档 → 跑 DocQA

**追问：有效长度怎么定义？** 通常用 RULER 在某个长度上召回率 >85% 的最大长度。LLaMA-3-8B 128K：NIAH 几乎全过，但 RULER 32K 才达标 → 有效长度约 32K。

## Q9: 长上下文模型的训练流程是什么？为什么不直接 128K 预训练？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

**典型流程**：
1. **预训练**：4K-8K 短序列（绝大部分算力在这里）
2. **长上下文继续训练**：32K → 128K 渐进，几千步
3. **位置编码扩展**：YaRN 调整 base/scaling
4. **SFT**：长上下文指令数据
5. **评测**：NIAH + RULER + LongBench

**为什么不直接 128K 预训练**：

| 原因 | 解释 |
|---|---|
| **算力代价** | Attention $O(n^2)$，128K 比 4K 贵 1024× |
| **长数据稀缺** | 互联网上 128K 连贯文档极少（PDF 切片质量差） |
| **效果不优** | 实验显示先短后长 > 直接长，前者基础语言能力更好 |
| **训练稳定性** | 长序列梯度更不稳，Adam 状态难收敛 |

**经验比例**：长上下文训练数据占总数据 < 5%（其余仍是短序列）。

**追问：长上下文 SFT 数据怎么造？** ① 长文档 + 多跳问答；② 拼接多个相关短文档模拟长上下文；③ "Repo-level 代码"（GitHub 仓库整理）；④ 长合成对话。质量比数量重要。

## Q10: 128K 上下文推理需要多大 GPU？KV Cache 是怎么算的？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

**KV Cache 公式**：

$$\text{KV Cache} = 2 \cdot L \cdot H \cdot d_h \cdot n \cdot \text{bytes}$$

**符号**：
- $2$：K 和 V
- $L$：层数
- $H$：KV 头数（GQA 后变小）
- $d_h$：每头维度
- $n$：序列长度
- bytes：BF16 = 2, INT8 = 1, INT4 = 0.5

**LLaMA-3-70B 128K 单请求**（BF16，GQA KV 头 8）：

$$2 \times 80 \times 8 \times 128 \times 131072 \times 2 \approx 43 \text{ GB}$$

**估算结论**：
- LLaMA-3-70B 128K 单请求约 40 GB KV Cache
- 加上权重 140 GB → **至少 2-4 张 80GB GPU**
- 服务多个请求需更多

**优化方法**：
- **GQA / MLA**：架构层减 KV 头
- **INT8 量化**：直接减半
- **PagedAttention**（vLLM）：内存碎片管理
- **Prefix Caching**：共享前缀的 KV 复用

**追问：为什么 MLA 比 GQA 省更多？** GQA 减少头数，但每个 KV 头维度不变；MLA 把整个 KV 压到 latent（如 512 维），等价于"虚拟 1 个超低维头"，存储再减一半。
