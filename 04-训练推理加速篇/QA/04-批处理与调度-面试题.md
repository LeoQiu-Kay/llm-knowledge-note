## Q1: Static / Dynamic / Continuous Batching 有什么区别？
> 难度 ⭐⭐ ｜ 高频 🔥🔥🔥

| 策略 | 调度时机 | 优 | 缺 |
|---|---|---|---|
| **Static** | 同时启动、同时结束 | 实现简单 | GPU 利用率低、**队头阻塞** |
| **Dynamic** | 短时间窗口聚合请求 | 比 Static 好 | 仍受最长请求影响 |
| **Continuous** | **每个 token step 都重组 batch** | 利用率高、无队头阻塞 | 实现复杂 |

**Continuous Batching 关键**：每生成一个 token 就检查"有谁完成了""有谁能加入"，让 GPU 持续满载。

**示意**：生成长度 5/10/15 的三个请求——
- Static：请求 1 早完成也要等到 15 才返回
- Continuous：请求 1 完成立即返回，新请求 4 无缝接入

**典型加速**：Continuous 比 Static 提升 2-3× 吞吐。

---

## Q2: Continuous Batching 的实现关键数据结构和流程？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

**两个核心队列**：
- **Running queue**：当前在 batch 中的请求
- **Waiting queue**：等待加入的请求

每个请求维护：prompt、KV Cache 指针、已生成 token、剩余 max_tokens。

**每步流程**：
1. 检查完成的请求（生成 EOS 或达 max_tokens）→ 移出 batch、返回结果
2. 从 waiting queue 加入新请求（如显存够装 KV Cache）
3. 对 running queue 中所有请求做一次 forward step
4. 重复

**关键依赖**：不同请求 KV Cache 长度不同 → 需要 **PagedAttention** 灵活管理；prefill 和 decode 性质差异 → 需要 **Chunked Prefill** 或 **PD 分离**。

## Q3: Chunked Prefill 解决什么问题？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

**问题**：
- 标准做法把整个 prompt 一次性 prefill（几百 ms 到数秒）
- prefill 阶段 GPU 被独占，正在 decode 的请求**全部被阻塞**
- 长 prompt（32K）让短请求等很久 → **队头阻塞**

**Chunked Prefill**：把长 prompt 切成 chunk（典型 512-2048 token），每 step 算一个 chunk 的 prefill **+ 其他请求的 decode**。

```text
混合 batch:
[chunk_prefill | request_2_decode | request_3_decode]
```

**效果**：
- TTFT 略升（prefill 被切分）
- P99 延迟、整体吞吐显著改善
- 短请求不再被长 prompt 卡住

**追问：chunk 大小怎么选？** 典型 512-2048。小 chunk 平滑好但调度开销大；大 chunk 反之。

## Q4: PD 分离是什么？什么场景值得？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

**PD 分离**（Prefill-Decode Disaggregation）：用不同集群专门跑 prefill 和 decode。

**动机**：两阶段的硬件需求差异巨大。

| 阶段 | 特性 | 适合硬件 |
|---|---|---|
| Prefill | Compute-bound、并行 | 高算力（H100） |
| Decode | Memory-bound、串行 | 高带宽（A100/H100，便宜的也行） |

**做法**：
- prefill 节点专门跑 prefill，算完把 KV Cache 传给 decode 节点
- decode 节点专门跑 decode
- 各自独立扩缩容

**典型系统**：DistServe（OSDI 2024）、Mooncake（Moonshot AI）、SplitWise（Microsoft）。

**何时值得**：大规模部署（数百卡以上）+ 高速网络（RDMA）传 KV。否则 KV 跨节点传输的开销吃掉收益。

## Q5: TTFT、TPOT、吞吐量分别受什么影响？三者怎么权衡？
> 难度 ⭐⭐ ｜ 高频 🔥🔥🔥

**符号定义**：
- **TTFT**（Time To First Token）：从请求到首 token 的时间，受 **prefill** 主导
- **TPOT**（Time Per Output Token）：每个后续 token 间隔，受 **decode** 主导
- **吞吐量**（Throughput）：tokens/sec 或 req/sec

**单请求体验**：$\text{延迟} = \text{TTFT} + n \cdot \text{TPOT}$（$n$ 是输出 token 数）

**核心矛盾**：
- 高吞吐（大 batch）→ TPOT 上升（单步算更多请求）
- 低 TPOT（小 batch）→ 吞吐下降
- 工程是找业务最佳点

**追问：为什么大 batch 会让 TPOT 升？** Decode memory-bound 时加 batch "近似免费"，但终究有上限——KV Cache 总读量主导后，TPOT 开始线性升。

## Q6: 怎么降低 TTFT、TPOT、提高吞吐？分别列对策
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

**降 TTFT**：
1. Prefix Caching：命中前缀直接跳过 prefill
2. Chunked Prefill：长 prefill 不阻塞短请求
3. PD 分离：prefill 集群独享资源
4. 缩短 prompt：去冗余 system prompt
5. 更快硬件：H100 vs A100 ~2-3×

**降 TPOT**：
1. 量化 KV Cache（减内存读）
2. 量化权重（减权重读）
3. **投机解码**（一步生成多 token）
4. MoE（激活参数少）
5. FlashAttention（减 IO）
6. 高带宽硬件（HBM3e）

**提高吞吐**：
1. Continuous Batching（GPU 满载）
2. 大 batch size（摊薄权重读取）
3. Prefix Caching（复用）
4. 量化（每卡装更多请求）
5. 横向扩 GPU

## Q7: vLLM 的默认调度策略是什么？
> 难度 ⭐⭐ ｜ 高频 🔥🔥

**默认栈**：FCFS + PagedAttention + Continuous Batching + Auto Prefix Caching。

- **FCFS**（先到先服务）：默认公平
- **PagedAttention**：内存管理
- **Continuous Batching**：每步重组 batch
- **Auto Prefix Caching**：自动复用前缀

**生产环境常加**：优先级队列（多租户、SLA 分级）、Chunked Prefill（新版本默认开）、（可选）投机解码。

## Q8: FCFS / 优先级 / SJF 几种调度策略各有什么优劣？
> 难度 ⭐⭐ ｜ 高频 🔥

| 策略 | 优 | 劣 |
|---|---|---|
| **FCFS**（先到先服务） | 公平、简单 | 长请求阻塞短请求 |
| **优先级队列** | 适合多租户、SLA 分级 | 低优请求可能饿死 |
| **SJF**（最短作业优先） | 短请求快返回、平均延迟低 | 长请求饥饿 |
| **混合 / 加权** | 灵活 | 调参复杂 |

LLM 推理的难点：**输出长度未知**（生成到 EOS 才停），SJF 不可直接用，常用估计长度或用户提示。

## Q9: 显存不够时（preemption）怎么处理？
> 难度 ⭐⭐⭐ ｜ 高频 🔥

vLLM 的 **Preemption** 机制：当新请求到达但显存不足时，**抢占**某个进行中请求的 KV Cache。

两种处理：
- **重 prefill**：丢弃 KV，被抢请求恢复时重新 prefill
- **Swap 到 CPU**：KV offload 到 CPU，恢复时拷回

**抢占策略**：优先抢低优先级 / 短请求 / 最近加入的请求。

**追问：为什么要 preempt 不直接拒绝？** 拒绝会丢失请求 → 重 prefill 的代价比拒绝低（特别是配合 Prefix Caching 时复用率高）。

## Q10: 典型生产 SLA 和监控指标有哪些？
> 难度 ⭐⭐ ｜ 高频 🔥

**典型 SLA**：
- TTFT P95 < 1s
- TPOT P95 < 100ms（10 token/s 体感流畅）
- 错误率 < 0.1%

**关键监控**：
| 类别 | 指标 |
|---|---|
| 业务 | QPS、TTFT、TPOT、错误率、token 消耗 |
| 系统 | GPU 利用率、KV Cache 占用、queue 长度 |
| 调度 | preemption 次数、prefix cache 命中率 |

**追问：为什么看 P95/P99 而非平均？** LLM 输出长度差异大，长尾请求拉高均值意义有限，P95/P99 更反映用户体验。
