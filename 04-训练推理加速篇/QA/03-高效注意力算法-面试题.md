## Q1: FlashAttention 解决了什么问题？加速的本质是什么？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

**问题**：标准 attention 要在 HBM 里**实例化完整** $n \times n$ 的 $S = QK^T$ 和 $P = \text{softmax}(S)$ 矩阵。
- 显存：$O(n^2)$
- HBM 读写量：极大

**关键洞察**：GPU 上 attention 是 **memory-bound**，不是 compute-bound——瓶颈在 HBM 访存。
- A100：算力 ~300 TFLOPs，HBM 带宽 ~2 TB/s，算力/带宽比远大于 attention 的算术强度
- 减少 HBM IO > 减少 FLOPs

**FlashAttention 核心**：**IO-aware** 算法。
- 不在 HBM 实例化 $S, P$
- 用**分块（tiling）+ online softmax + 重计算**
- 数据保持在 SRAM 中复用

**结果**：HBM IO 从 $O(n^2)$ 降到 $O(n)$，FLOPs 不变，但**真实墙钟时间** 2-4× 加速。

**符号说明**：HBM = High Bandwidth Memory（GPU 主显存）；SRAM = on-chip 高速缓存（A100 每 SM ~192 KB）。

## Q2: 分块（tiling）的伪代码是怎样的？为什么 Q 在外层？
> 难度 ⭐⭐⭐⭐ ｜ 高频 🔥🔥

```text
for i in range(N / B_q):              # Q 块循环（外层，v2 改成这样）
    load Q_i into SRAM
    init O_i, m_i, l_i in SRAM
    for j in range(N / B_kv):         # K, V 块循环（内层）
        load K_j, V_j into SRAM
        S_ij = Q_i @ K_j.T
        在 SRAM 中做 online softmax 累积更新 O_i, m_i, l_i
    write O_i, m_i, l_i back to HBM
```

**Q 在外层**（v2 起）：
- 每个输出 $O_i$ 一旦在外层确定，可一次性写回 HBM（避免反复读写）
- v1 是 K 在外层，每次都要重新读 Q 和写部分输出 → IO 大
- v2 优化后再加速 ~2×

**符号说明**：$B_q, B_{kv}$ 是块大小；$O_i$ 是第 $i$ 个 Q 块的输出；$m_i, l_i$ 是 online softmax 的 running max 和 sum。

## Q3: Online Softmax 是怎么工作的？为什么需要它？
> 难度 ⭐⭐⭐⭐ ｜ 高频 🔥🔥🔥

**问题**：softmax 需要**全局** max（数值稳定）和 sum（分母），分块时不知道全局值。

**算法**：维护 running max $m$ 和 running sum $\ell$，每见一个新块就**回头修正**之前累积的 $O$ 和 $\ell$：

```python
m = -inf; l = 0; O = 0
for block in blocks:
    m_new = max(m, max(block))
    # 缩放旧累积值（之前用旧 m 减过，要换成新 m）
    scale = exp(m - m_new)
    O = O * scale
    l = l * scale
    # 加入新块贡献
    l += sum(exp(block - m_new))
    O += exp(block - m_new) @ V_block
    m = m_new
O = O / l   # 最后统一除分母
```

**关键**：和一次性算 softmax **数值等价**——任意旧块结果都可以通过乘 $e^{m_{\text{old}} - m_{\text{new}}}$ 重新缩放到新基准。

**符号说明**：$m$ 保证 $\exp$ 不上溢；$\ell$ 是 $\sum e^{z-m}$。

## Q4: FlashAttention v1 / v2 / v3 各自的关键创新是什么？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

| 版本 | 关键创新 | 加速 |
|---|---|---|
| **v1**（Tri Dao 2022） | tiling + online softmax + recomputation | 2-4× vs naive |
| **v2**（2023） | Q 外层循环、减非矩阵乘运算、更好 work partitioning | 再加速 ~2× |
| **v3**（2024） | 针对 Hopper（H100）：TMA 异步加载、warp specialization、FP8 | 接近峰值算力 ~75% |

**TMA**（Tensor Memory Accelerator）：H100 引入的异步内存搬运单元，让数据加载与计算重叠。

**典型对比**（H100 上 v3 vs PyTorch SDPA）：约 2-3×。

## Q5: FlashAttention 的反向传播怎么处理 S、P 矩阵？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

**问题**：反向需要 $S = QK^T$ 和 $P = \text{softmax}(S)$，但前向**没保存**。

**解法**：只保存 $O$、softmax 的归一化常数（$m, \ell$，每行一个数）；反向时**重算** $S, P$。

**代价收益**：
- 多算 ~30% FLOPs
- 显存从 $O(n^2)$ 降到 $O(n)$（不存 $S, P$）

**追问：和 Gradient Checkpointing 什么关系？** 思想完全一致——前向丢中间结果，反向重算。FlashAttention 是 attention 版的 checkpointing，只是粒度更细。

## Q6: PagedAttention 解决什么问题？为什么借鉴 OS 分页？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

**问题**：朴素 KV Cache 给每个请求一次性分配 `max_seq_len` 连续内存——大部分时间未填满 → **内部碎片 + 外部碎片** → 实际利用率仅 20-40%。

**借鉴 OS 分页**：
1. KV Cache 切成固定大小的 **block**（vLLM 默认 16 个 token/块）
2. 每个请求维护一张 **block table**（类似页表）
3. 物理上 block 散布在显存中，逻辑上通过 block table 串起来
4. 按需分配、用完即释放

**效果**：
- 内存利用率 > 90%
- 支持更高并发
- 自然支持 **block 级共享**（多个请求的 block table 指向同一物理 block → Prefix Caching 基础）

**追问：block size 怎么选？** 典型 16。太小调度开销大，太大碎片回来。

## Q7: PagedAttention 的 block sharing 怎么实现 Copy-on-Write？
> 难度 ⭐⭐⭐ ｜ 高频 🔥

**前提**：多个请求共享相同前缀的 KV block。

**机制**：
1. 检测前缀 block 的 hash 相同 → 多请求的 block table 都指向**同一物理 block**
2. 用**引用计数**管理生命周期（计数为 0 时释放）
3. 若某请求要"修改"共享 block（罕见，如 beam search 分叉）：先拷贝该 block 再改 → **Copy-on-Write**

**典型场景**：beam search、parallel sampling（一个 prompt 生成多份 response）。

## Q8: FlashAttention 和 PagedAttention 是什么关系？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

它们在**不同层**，**互补**而非替代：

```text
┌─────────────────────────────────────┐
│   推理引擎（vLLM / SGLang / TRT-LLM）│
│  调度层：Continuous Batching、PD 分离 │
│  内存层：PagedAttention、RadixAttention│  ← 管理 KV Cache 的"分配与寻址"
│  Kernel 层：FlashAttention v2/v3      │  ← 在 SRAM/HBM 间最优搬数算
└─────────────────────────────────────┘
```

- **FlashAttention**：kernel 级，IO-aware 的 attention 计算
- **PagedAttention**：内存管理级，KV Cache 的分配/寻址

**vLLM** 同时用 FlashAttention（算）+ PagedAttention（管），缺一不可。

## Q9: RadixAttention（SGLang）和 vLLM Prefix Caching 有什么区别？
> 难度 ⭐⭐⭐ ｜ 高频 🔥

| | vLLM Prefix Caching | SGLang RadixAttention |
|---|---|---|
| 数据结构 | block 级 hash 表 | **Radix Tree（基数树）** |
| 粒度 | 粗（按 block，16 token 一致才匹配） | **细（按字符/token 级前缀）** |
| 多分支共享 | 一般 | **好**（同 prompt 不同 few-shot 分支） |
| 淘汰策略 | LRU | LRU（按 tree 节点） |
| 适用 | 通用 | **Tree-of-Thoughts、多分支推理** |

**RadixAttention 优势场景**：同一前缀派生出多个分支（如 ToT、self-consistency），共享比例高。

## Q10: Ring Attention 是干什么用的？和 FlashAttention 怎么协作？
> 难度 ⭐⭐⭐ ｜ 高频 🔥

**目标**：训练**超长上下文**（百万 token+），单卡装不下完整 attention。

**核心**：在多设备间**环形传递** K/V 块。
1. 把序列按设备数 $N$ 切分，每设备持有一段 Q/K/V
2. 每个设备先用本地 K/V 算注意力
3. 在环形拓扑中**异步**传 K/V 到下一设备
4. 累积所有设备的贡献，得到全局 attention 输出

**与 FlashAttention 兼容**：每段内部用 FlashAttention 算（节省单设备显存），段间用 Ring（跨设备）。

**应用**：Gemini 1.5（1M context）、LLaMA-3 长上下文训练。
