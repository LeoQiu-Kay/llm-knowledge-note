# 高效注意力算法（FlashAttention / PagedAttention）

> 现代 LLM 推理引擎的两大基石，必考。

---

## Q1: FlashAttention 解决了什么问题？

**答**：
**问题**：标准 Attention 实现需要在 HBM 中读写一个 $n \times n$ 的注意力矩阵 $S = QK^T$。
- 显存 $O(n^2)$
- HBM 读写次数巨大 → IO 瓶颈

**FlashAttention 核心**：**IO-aware** 算法。
- 重新组织计算，**永远不在 HBM 中实例化完整 $S$ 和 $P=\text{softmax}(S)$**
- 用分块（tiling）+ online softmax + 重计算（recomputation）
- 减少 HBM 读写，把数据保持在 SRAM 中复用

**关键认识**：GPU 上 attention 不是 compute-bound，而是 **memory-bound**（IO 瓶颈）。FlashAttention 把内存访问从 $O(n^2)$ 降到 $O(n)$，同时计算量不变。

---

## Q2: FlashAttention 的分块策略？

**答**：
**分块思想**：把 $Q, K, V$ 都按行分块，每块塞进 SRAM 计算。

**算法**：
```
for j in 0..N/B:   # K, V 的块循环（外层）
    load K_j, V_j into SRAM
    for i in 0..N/B:  # Q 的块循环（内层）
        load Q_i into SRAM
        S_ij = Q_i @ K_j^T  (块矩阵乘)
        在 SRAM 中做 online softmax
        累积更新 O_i
    write O_i back to HBM
```

**关键技巧**：
- **Online Softmax**：分块计算 softmax 时维护 running max 和 running sum
- **重计算**：反向时重算 $S, P$ 而不保存（用激活值换显存）

---

## Q3: Online Softmax 怎么做？

**答**：
**问题**：softmax 需要全局 max 和 sum，分块计算时不知道全局值。

**算法**：维护两个变量 $m$（running max）和 $\ell$（running sum）。
```python
m = -inf, l = 0, O = 0
for block in blocks:
    m_new = max(m, max(block))
    # 缩放旧的累积值
    O = O * exp(m - m_new)
    l = l * exp(m - m_new)
    # 加入新块的贡献
    l += sum(exp(block - m_new))
    O += exp(block - m_new) @ V_block
    m = m_new
O = O / l
```

**保证**：与一次性算的 softmax 数值等价。

## Q4: FlashAttention v1 vs v2 vs v3？

**答**：

**FlashAttention v1**（Tri Dao et al., 2022）：
- 引入 tiling + online softmax
- 比标准 attention 快 2-4×

**FlashAttention v2**（2023）：
- **优化 work partitioning**：让 Q 循环放外层（v1 是 K 外层），更好的并行性
- 减少非矩阵乘运算（rescaling）
- 加速 2× over v1

**FlashAttention v3**（2024）：
- **针对 Hopper（H100）优化**
- 利用 TMA（Tensor Memory Accelerator）异步加载
- FP8 支持
- 接近峰值算力（~75% utilization）

**典型加速**（H100 上 v3 vs PyTorch SDPA）：约 2-3×。

---

## Q5: FlashAttention 在反向传播怎么做？

**答**：
**问题**：反向需要 $S, P$ 矩阵，但前向没保存。

**解法**：**重计算**（Recomputation）。
- 只保存 $O$ 和 softmax 归一化常数（$m, \ell$）
- 反向时重新算 $S = QK^T$ 和 $P$
- 用 ~30% 额外算力换大量显存

**显存优化**：从 $O(n^2)$ 降到 $O(n)$。

## Q6: PagedAttention 是什么？

**答**：
**vLLM**（Kwon et al., SOSP 2023）提出，借鉴**操作系统虚拟内存分页**思想管理 KV Cache。

**问题**：朴素 KV Cache 分配方式低效：
- 每个请求一次性分配 max_seq_len 大小的连续内存
- 大部分时间未填满 → **内存碎片化**
- 实际有效利用率往往只有 20-40%

**PagedAttention 解法**：
1. KV Cache 切成固定大小的 **block**（如 16 个 token 一块）
2. 每个请求维护一个 **block table**（类似页表）
3. 物理上 block 分散在内存中，逻辑上通过 block table 连接
4. 按需分配，用完即释放

**优势**：
- 内存利用率 > 90%
- 支持更高并发
- 自然支持 **block 级共享**（多个请求共享 prefix block）

**示意**：
```
请求1 [token1, token2, ..., token35]
逻辑视图: [block 0][block 1][block 2]
block table: [phys 7][phys 3][phys 11]
物理内存: 离散分散
```

---

## Q7: PagedAttention 的 Block Sharing 怎么实现？

**答**：
**场景**：多个请求共享相同前缀（如同一 system prompt）。

**实现**：
1. 检测前缀 block hash 相同
2. 多个请求的 block table 指向同一物理 block
3. 引用计数管理生命周期
4. **Copy-on-Write**：如果某请求要修改共享 block，先拷贝再改

**结合 Prefix Caching**：
- vLLM 自动检测 prefix 命中
- SGLang 用 Radix Tree 做更细粒度的前缀复用

## Q8: Continuous Batching 是什么？

**答**：
**朴素 Batching**（Static / Dynamic）：
- 所有请求一起开始，等最长的请求结束才返回
- 短请求白白浪费 GPU
- 利用率低

**Continuous Batching**（也叫 In-flight Batching）：
- **每个 token 步骤后重新决定 batch 组成**
- 完成的请求立即返回
- 新请求随时加入
- GPU 持续保持高利用率

**关键挑战**：
- 不同请求处于不同阶段（一些 prefill，一些 decode）
- 序列长度不同
- 需要 PagedAttention 这样的内存管理配合

**框架**：
- **Orca**（OSDI 2022）首次提出
- **vLLM** 实现并开源
- 现在所有主流推理引擎都支持

---

## Q9: Chunked Prefill 是什么？

**答**：
**问题**：长 prompt 的 prefill 一次性算完，会卡住其他正在 decode 的请求（队头阻塞）。

**Chunked Prefill**：
- 把长 prompt 分成多个 chunk（如每 chunk 512 token）
- 每个 step 算一个 chunk 的 prefill + 其他请求的 decode
- 平滑 prefill 与 decode

**优势**：
- 降低长请求阻塞短请求的概率
- 提高整体吞吐
- 改善尾延迟（P99 TTFT）

**框架支持**：vLLM、TRT-LLM 均支持。

---

## Q10: RadixAttention（SGLang）？

**答**：
**核心**：基于 **Radix Tree**（基数树）的 KV Cache 前缀复用。

**与 vLLM Prefix Caching 的区别**：
- vLLM：基于 block 的哈希匹配（粒度较粗）
- SGLang：基于字符级 Radix Tree，更精细的前缀共享

**优势**：
- 多分支共享更好（如同一 prompt 不同 few-shot 例子）
- LRU 自动淘汰
- 长上下文 / 多分支推理场景明显加速

**适用场景**：
- 复杂 prompt 结构（系统提示 + 工具调用模板）
- Tree-of-Thoughts 风格的搜索

---

## Q11: Ring Attention 是什么？

**答**：
**目标**：训练超长上下文（百万 token+）。

**核心**：在多设备间**环形传递** K/V 块。

**算法**：
1. 把序列按设备数 N 切分，每设备持有一段 Q/K/V
2. 每个设备先用本地 K/V 算注意力
3. 在环形拓扑中传递 K/V 到下一设备
4. 累积所有设备贡献，得到全局 attention 输出

**优势**：
- 支持**任意长度**（与设备数线性扩展）
- 与 FlashAttention 兼容（每设备内部用 FA）

**应用**：
- Gemini 1.5（1M context）
- LLaMA-3 长上下文版本
- 训练时用得多，推理少（推理更倾向 KV Cache 压缩）

## Q12: 这些技术的层次关系？

**答**：

```
┌─────────────────────────────────────┐
│       推理引擎（vLLM/SGLang/TRT-LLM） │
│                                     │
│  ┌────────────────────────────────┐ │
│  │   调度层                       │ │
│  │  - Continuous Batching         │ │
│  │  - Chunked Prefill             │ │
│  │  - PD 分离                     │ │
│  └────────────────────────────────┘ │
│                                     │
│  ┌────────────────────────────────┐ │
│  │   内存管理                     │ │
│  │  - PagedAttention              │ │
│  │  - RadixAttention              │ │
│  │  - Prefix Caching              │ │
│  └────────────────────────────────┘ │
│                                     │
│  ┌────────────────────────────────┐ │
│  │   Kernel 层                    │ │
│  │  - FlashAttention v2/v3        │ │
│  │  - 量化 kernel                 │ │
│  └────────────────────────────────┘ │
└─────────────────────────────────────┘
```

每一层解决不同维度的问题，组合使用。

## 🎯 高频追问

1. **FlashAttention 加速的本质是什么**？减少 HBM IO，把计算保持在 SRAM 中。
2. **PagedAttention 的 block size 怎么选**？典型 16（vLLM 默认），太小调度开销大，太大碎片回来。
3. **Continuous Batching 为什么能大幅提速**？消除短请求等待长请求的浪费；GPU 持续满载。
4. **FlashAttention 必须用 GPU 吗**？是，专为 GPU 内存层级（HBM/SRAM）设计。CPU 上 attention 没有相同瓶颈。
5. **训练和推理都能用 FlashAttention 吗**？都能。训练用 v2/v3 的 forward + backward；推理只用 forward。
6. **PagedAttention 比 FlashAttention 更上层吗**？两者层级不同：FA 是 kernel 优化，PA 是内存管理；通常一起用。
