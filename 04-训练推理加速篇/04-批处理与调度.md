# 批处理与调度

> Continuous Batching、Chunked Prefill、PD 分离是面试高频。

---

## 1. Static / Dynamic / Continuous Batching

| 策略 | 调度时机 | 优 | 缺 |
|---|---|---|---|
| **Static Batching** | 同时启动、同时结束 | 实现简单 | GPU 利用率低、尾延迟差 |
| **Dynamic Batching** | 短时间窗口聚合请求 | 比 Static 好 | 仍受最长请求影响 |
| **Continuous Batching** | 每个 token step 重新组 batch | 利用率高、无队头阻塞 | 实现复杂 |

**示意**（生成长度 5、10、15 的三个请求）：

```
Static Batching：
请求1 [生成 5 token]_________________  
请求2 [生成 10 token]_______________
请求3 [生成 15 token]_______________
                 ↑请求1早完成但要等到 15 token 才返回

Continuous Batching：
请求1 [生成 5 token, 返回][空闲]....
请求2 [生成 10 token, 返回][空闲]...
请求3 [生成 15 token, 返回]
新请求4 [无缝接入]......................
                 ↑GPU 持续满载
```

---

## 2. Continuous Batching 实现要点

**核心数据结构**：
- **Running queue**：当前在 batch 中的请求
- **Waiting queue**：等待加入的请求
- 每个请求状态：prompt、KV Cache 指针、已生成 token、剩余 max_tokens

**每步流程**：
1. 检查完成的请求（生成 EOS 或达 max_tokens）→ 移出 batch 返回
2. 从 waiting queue 加入新请求（如显存足够）
3. 对 running queue 中所有请求做一个 forward step
4. 重复

**关键挑战**：
- 不同请求 KV Cache 长度不同 → 需要 PagedAttention 灵活管理
- prefill 和 decode 性质不同 → Chunked Prefill 或 PD 分离

---

## 3. Chunked Prefill

**问题**：
- 标准做法：prefill 一次性算完所有 prompt token（几百 ms 到几秒）
- prefill 阶段 GPU 被独占，其他正在 decode 的请求被阻塞
- 长 prompt（如 32K）让短请求等很久（**队头阻塞**）

**Chunked Prefill**：把长 prompt 切成 chunk（如每 chunk 512 token），每个 step 算一个 chunk 的 prefill + 其他请求的 decode。

```
混合 batch:
[chunk prefill | request_2 decode | request_3 decode]
```

**效果**：
- TTFT 略升（prefill 被切分）
- 但 P99 延迟、整体吞吐显著改善
- 短请求不再被长 prompt 卡住

---

## 4. PD 分离（Prefill-Decode Disaggregation）

**动机**：Prefill 和 Decode 的硬件需求差异很大。

| 阶段 | 特性 | 适合硬件 |
|---|---|---|
| Prefill | Compute-bound、并行 | 高算力（H100） |
| Decode | Memory-bound、串行 | 高带宽（A100/H100） |

**PD 分离**：
- 用一组节点专门做 prefill（计算密集集群）
- 另一组节点专门做 decode（带宽密集集群）
- 中间通过 KV Cache 传输衔接

**典型系统**：
- **DistServe**（OSDI 2024）
- **Mooncake**（Moonshot AI 的 KV Cache as a Service）
- **SplitWise**（Microsoft）

**优势**：
- 不同阶段独立扩缩容
- 资源利用更精细
- 大流量场景显著提速

**挑战**：
- KV Cache 跨节点传输（高带宽网络如 RDMA）
- 调度复杂

---

## 5. 关键指标：TTFT vs TPOT vs 吞吐量

**符号定义**：
- **TTFT**（Time To First Token）：从请求到首 token 的时间，受 prefill 影响
- **TPOT**（Time Per Output Token）：每个后续 token 间隔，受 decode 影响
- **吞吐量**（Throughput）：tokens/sec 或 req/sec

**关系**：
- 单请求体验：$\text{TTFT} + n \times \text{TPOT}$（$n$ 是输出 token 数）
- 系统容量：吞吐量

**矛盾**：
- 高吞吐（大 batch）→ TPOT 升
- 低 TPOT（小 batch）→ 吞吐降
- 工程是找平衡

---

## 6. 怎么降低 TTFT？

1. **Prefix Caching**：命中前缀直接跳 prefill
2. **Chunked Prefill**：长 prefill 不阻塞短请求
3. **PD 分离**：prefill 专用集群、资源独享
4. **更短的 prompt**：去冗余 system prompt
5. **更快的硬件**：H100 比 A100 快 2-3×

## 7. 怎么降低 TPOT？

1. **量化 KV Cache**：减少内存读
2. **量化权重**：减少权重读
3. **投机解码**：一步生成多 token
4. **MoE**：激活参数少
5. **FlashAttention**：减少 IO
6. **更高带宽硬件**：H100 HBM3e

## 8. 怎么提高吞吐量？

1. **Continuous Batching**：GPU 持续满载
2. **大 batch size**：摊薄权重读取成本
3. **Prefix Caching**：跨请求复用
4. **量化**：每张卡装更多请求
5. **更多 GPU**：横向扩展

---

## 9. SLA 与监控

**典型 SLA**：
- TTFT P95 < 1s
- TPOT P95 < 100ms
- 错误率 < 0.1%

**关键监控指标**：
- 业务：QPS、TTFT、TPOT、错误率、token 消耗
- 系统：GPU 利用率、KV Cache 占用、队列长度

**显存不够时的处理**（vLLM 称 Preemption）：
- 抢占某请求的 KV Cache（重 prefill 或 swap 到 CPU）
- 优先抢占低优先级 / 短请求

---

## 10. 调度策略

| 策略 | 优劣 |
|---|---|
| **FCFS**（先到先服务） | 默认，公平，但长请求阻塞短的 |
| **优先级队列** | 适合多租户、SLA 分级 |
| **SJF**（最短作业优先） | 短请求快返回，长请求饥饿 |
| **混合** | 加权或动态调整 |

**实际**：vLLM 默认 FCFS + Continuous Batching；生产系统常加优先级。

---

## 11. 最简记忆

```text
Static Batching      → 一起开一起停（差）
Dynamic Batching     → 短时窗合并（一般）
Continuous Batching  → 每步重组（最优）

Chunked Prefill：把长 prompt 切块，平滑 prefill 和 decode
PD 分离：prefill 集群 + decode 集群，独立扩缩容

关键指标：
  TTFT（首 token 时间）→ 受 prefill 影响
  TPOT（每 token 间隔）→ 受 decode 影响
  吞吐量（QPS）→ 取决于 batch 大小和并发

工程平衡：吞吐 ↑ ≈ 延迟 ↑，找业务最佳点。
```

## 🎯 高频追问

1. **Continuous Batching 比 Static 提速多少**？典型 2-3× 吞吐提升。

2. **Chunked Prefill 的 chunk 大小怎么选**？典型 512-2048。小 chunk 平滑好但调度开销大。

3. **PD 分离何时值得**？大规模部署（数百卡以上）+ 需要高速网络（RDMA）传 KV。

4. **vLLM 默认调度逻辑**？FCFS + PagedAttention + Continuous Batching + Auto Prefix Caching。

5. **怎么减少 TTFT**？Chunked Prefill 提供局部 TTFT、Prefix Caching 命中跳过 prefill、PD 分离让 prefill 节点更快。
