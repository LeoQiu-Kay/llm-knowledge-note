# 批处理与调度

> Continuous Batching、Chunked Prefill、PD 分离是面试高频。

---

## Q1: Static / Dynamic / Continuous Batching 的区别？

**答**：

| 策略 | 调度时机 | 优点 | 缺点 |
|------|---------|------|------|
| **Static Batching** | 同时启动，同时结束 | 实现简单 | GPU 利用率低，尾延迟差 |
| **Dynamic Batching** | 短时间窗口聚合请求 | 比 Static 好 | 仍受最长序列影响 |
| **Continuous Batching** | 每个 token step 重新组 batch | 利用率高，无队头阻塞 | 实现复杂 |

**示意**（生成长度 5、10、15 的三个请求）：

```
Static Batching：
请求1 [生成 5 个 token]_____________  
请求2 [生成 10 个 token]____________
请求3 [生成 15 个 token]____________
                 ↑请求1早完成但要等到15 token步骤才返回

Continuous Batching：
请求1 [生成 5 token, 返回][空闲]....
请求2 [生成 10 token, 返回][空闲]...
请求3 [生成 15 token, 返回]
新请求4 [无缝接入]......................
                 ↑GPU 持续满载
```

## Q2: Continuous Batching 的实现要点？

**答**：
**核心数据结构**：
- **Running queue**：当前在 batch 中的请求
- **Waiting queue**：等待加入的请求
- **每个请求状态**：prefill 已完成的 prompt、KV Cache 指针、生成的 token、剩余 max_tokens

**每步流程**：
1. 检查是否有请求完成（生成了 EOS 或达到 max_tokens）
2. 完成的请求从 batch 中移出，返回结果
3. 从 waiting queue 中加入新请求（如显存足够）
4. 对 running queue 中所有请求做一个 forward step
5. 重复

**关键挑战**：
- 不同请求 KV Cache 长度不同 → 需要 PagedAttention 这种灵活内存管理
- prefill 和 decode 性质不同 → Chunked Prefill 或 PD 分离

## Q3: Chunked Prefill 详解？

**答**：
**问题**：标准做法分两阶段：
1. Prefill：所有 prompt token 一次性算（计算密集，几百毫秒到几秒）
2. Decode：逐个生成

**对其他请求的影响**：
- Prefill 阶段 GPU 被独占
- 其他正在 decode 的请求被阻塞
- 长 prompt（如 32K）会让短请求等待很久（队头阻塞）

**Chunked Prefill**：
- 把长 prompt 分成 chunk（如每 512 token）
- 每个 step 算一个 chunk + 其他请求的 decode
- 混合 batch：[some prefill chunks] + [some decode steps]

**效果**：
- TTFT 略升（prefill 被切分）
- 但 P99 延迟、整体吞吐显著改善
- 短请求不再被长 prompt 卡住

**框架**：vLLM、TRT-LLM、SGLang 都支持。

## Q4: PD 分离（Prefill-Decode Disaggregation）？

**答**：
**动机**：Prefill 和 Decode 的硬件需求差异很大。

| 阶段 | 特性 | 适合硬件 |
|------|------|---------|
| Prefill | Compute-bound、并行 | 高算力（如 H100） |
| Decode | Memory-bound、串行 | 高带宽（如 A100/H100） |

**PD 分离**：
- 用一组节点专门做 prefill（计算密集集群）
- 另一组节点专门做 decode（带宽密集集群）
- 中间通过 KV Cache 传输衔接

**典型系统**：
- **DistServe**（OSDI 2024）
- **Mooncake**（Moonshot AI 的 KV Cache as a Service）
- **SplitWise**（Microsoft）

**优势**：
- 不同阶段独立扩缩容
- 资源利用更精细
- 大流量场景显著提速

**挑战**：
- KV Cache 跨节点传输（高带宽网络）
- 调度复杂
- 适合大规模部署

## Q5: 调度策略：FCFS vs 优先级 vs 最短作业优先？

**答**：

| 策略 | 描述 | 优劣 |
|------|------|------|
| **FCFS**（先到先服务） | 默认 | 公平，但长请求阻塞短请求 |
| **优先级队列** | 按 SLA 等级 | 适合多租户 |
| **SJF**（最短作业优先） | 按估计长度 | 短请求快返回，长请求饥饿 |
| **混合** | 加权或动态调整 | 复杂但效果好 |

**实际**：vLLM 默认 FCFS + Continuous Batching；生产系统常加优先级。

## Q6: Speculative Decoding 与 Continuous Batching 怎么配合？

**答**：
**简单情况**：单请求做投机解码 → 每步多产生几个 token。

**复杂情况**：批处理 + 投机解码
- 不同请求的接受率不同
- 每步每个请求生成的 token 数不同（动态）
- 需要 reshape 处理后续

**Anthropic、DeepSeek 等的实践**：
- 投机解码在低并发场景（如长 CoT）显著加速
- 高并发时与 batching 的优势重叠，加速变小

## Q7: 吞吐量 vs 延迟的权衡？

**答**：
**吞吐量（Throughput）**：单位时间能服务多少 token / 多少请求。
**延迟（Latency）**：单个请求多久返回。

**矛盾**：
- 大 batch → 吞吐高，但每个请求慢
- 小 batch → 延迟低，但 GPU 利用率低

**关键指标**：
- **TTFT**（Time To First Token）：从请求到首 token，受 prefill 影响
- **TPOT**（Time Per Output Token）：每个后续 token 间隔，受 decode 影响
- **吞吐量**：tokens/sec total

**实际选择**：
- 在线 chat：低 TTFT 优先
- 批量 API（如 OpenAI Batch）：高吞吐优先
- 实时翻译：低 TPOT 优先

## Q8: 实际请求生命周期？

**答**：
1. **接收**：HTTP 请求到达 API gateway
2. **Tokenize**：把 prompt 转成 token id
3. **入队**：进入 waiting queue
4. **调度**：调度器评估能否加入 running batch（KV Cache 空间够？算力够？）
5. **Prefill**：算完整 prompt 的 KV（或分块 prefill）
6. **首 token**：第一个 token 生成（用户感知到响应）
7. **Decode 循环**：逐个生成
8. **流式返回**：每个 token 通过 SSE 推送
9. **结束**：EOS / max_tokens / stop sequence
10. **清理**：释放 KV Cache

---

## Q9: 显存不够时的处理？

**答**：
**Preemption（抢占）**：
- vLLM 在显存不足时会"抢占"请求
- 把某请求的 KV Cache **重计算**（重新 prefill）或 **swap 到 CPU**
- 优先抢占低优先级 / 短请求

**调度优化**：
- 限制最大并发
- 拒绝新请求（503）
- offload 远端历史

---

## Q10: 推理引擎如何衡量调度好坏？

**答**：
**关键指标**：
1. **吞吐量**：总 tokens/sec、req/sec
2. **延迟分布**：TTFT P50/P95/P99，TPOT P50/P95/P99
3. **GPU 利用率**：算力 + 显存带宽
4. **KV Cache 利用率**：实际使用 / 分配
5. **拒绝率**：因满载拒绝的请求数

**调优**：
- 基准测试不同 max_num_seqs、max_num_batched_tokens
- 看 P99 是否符合 SLA
- 看 GPU 是否吃满

## 🎯 高频追问

1. **Continuous Batching 与 Static Batching 性能差距**？典型 2-3× 吞吐提升。
2. **Chunked Prefill 的 chunk 大小怎么选**？小 chunk 平滑性好但调度开销大；大 chunk 反之。典型 512-2048。
3. **PD 分离的成本**？需要高速网络（如 RDMA）传输 KV，部署复杂；规模够大才划算。
4. **vLLM 默认调度逻辑**？FCFS + PagedAttention + Continuous Batching + Auto Prefix Caching。
5. **如何减少 TTFT**？Chunked Prefill 提供局部 TTFT，Prefix Caching 命中可跳过 prefill，PD 分离让 prefill 专用节点更快。
