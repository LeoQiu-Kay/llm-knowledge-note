# 通信与显存

> 集合通信 + 显存估算是分布式训练面试常考。

---

## Q1: AllReduce / AllGather / ReduceScatter / All-to-All 的语义？

**答**：

**AllReduce**：
- 每个进程都有一个 tensor
- 所有进程的 tensor 按某操作（sum/avg）聚合
- 所有进程最终拥有相同的聚合结果
- 用于：DP 梯度同步

```
GPU 0: [1, 2]    AllReduce(sum)    GPU 0: [4, 6]
GPU 1: [3, 4]   ─────────────→     GPU 1: [4, 6]
```

**AllGather**：
- 每个进程有一个 tensor 分片
- 所有进程聚合得到完整 tensor
- 每个进程拥有完整结果
- 用于：ZeRO-3 还原参数

```
GPU 0: [1, 2]    AllGather    GPU 0: [1, 2, 3, 4]
GPU 1: [3, 4]   ──────────→   GPU 1: [1, 2, 3, 4]
```

**ReduceScatter**：
- AllReduce 的"反向"
- 每个进程做 reduce，但每个进程只保留一部分结果
- 用于：ZeRO-3 梯度规约

```
GPU 0: [1, 2, 3, 4]   ReduceScatter   GPU 0: [6]
GPU 1: [5, 6, 7, 8]   ────────────→   GPU 1: [10]
                                       # 假设 sum，每卡只持有一部分
```

**All-to-All**：
- 每个进程有 N 份数据（N 是进程数）
- 第 i 份发给进程 i
- 用于：MoE 专家路由、序列并行

**算法关系**：
- AllReduce = ReduceScatter + AllGather（数学等价）
- ZeRO-3 把 AllReduce 拆成 ReduceScatter + AllGather，更节省显存

## Q2: NCCL 通信的硬件层级？

**答**：
**节点内（intra-node）**：
- **NVLink**（A100 ~600GB/s，H100 ~900GB/s）：GPU 间直连
- **NVSwitch**：让一个节点内所有 GPU 全互联
- **PCIe**：备用，远慢于 NVLink

**跨节点（inter-node）**：
- **InfiniBand**（IB）：HPC 标准，HDR 200Gb/s，NDR 400Gb/s
- **以太网 + RoCE**：成本低，性能略低

**优化**：
- Tree / Ring / Double-Tree 等拓扑算法
- NCCL 自动选择最优算法

## Q3: 梯度累积（Gradient Accumulation）？

**答**：
**问题**：想用大 batch 但显存不够。

**方案**：每个 micro-batch 算梯度，**不立即更新**，累积 N 个 micro-batch 后再更新。

**等价效果**：
- 等效 batch size = micro_batch × accum_steps
- 等效一次大 batch

**实现**：
```python
optimizer.zero_grad()
for i in range(accum_steps):
    micro_batch = get_micro_batch(i)
    loss = model(micro_batch).loss / accum_steps  # 注意除以 accum_steps
    loss.backward()
optimizer.step()
```

**注意**：
- loss 要除以 accum_steps（取平均，而非求和）
- LayerNorm/RMSNorm 不受影响（per-sample）
- BatchNorm 会有偏（但 LLM 不用 BN）
- LR 调度器的"step"指优化步，不是 micro-step

## Q4: 梯度检查点（Gradient Checkpointing）？

**答**：
**问题**：反向传播需要前向激活值，全部保存爆显存。

**思路**：
- 前向只保存少量"检查点"（如每 N 层一个）
- 反向时**重新计算**中间激活
- 用计算换显存

**显存节省**：
- 标准：$O(\text{layers} \times \text{batch} \times \text{seq} \times \text{hidden})$
- Checkpointing：$O(\sqrt{\text{layers}} \times \text{batch} \times \text{seq} \times \text{hidden})$

**代价**：约 33% 额外计算（一次完整前向）。

**PyTorch 实现**：
```python
from torch.utils.checkpoint import checkpoint

def forward(x):
    for layer in layers:
        x = checkpoint(layer, x)
    return x
```

**Selective Checkpointing**：
- 不是所有层都 checkpoint，只对显存大的层
- 通常 attention 的 KQV、softmax 输出最值得 checkpoint
- 工程上需要细调

## Q5: CPU Offload 是什么？

**答**：
**思路**：把优化器状态 / 梯度 / 参数卸载到 CPU 内存，需要时再调到 GPU。

**DeepSpeed ZeRO-Offload**：
- 把 Adam 状态（FP32 momentum + variance）放 CPU
- CPU 上做参数更新
- GPU 只做前向 + 反向

**优点**：
- 单卡可训练更大模型（甚至单 4090 训 13B）

**缺点**：
- PCIe 带宽是瓶颈
- 训练速度大幅下降
- 适合"装得下就行"，不在意速度

**NVMe Offload**：进一步把 CPU 内存放不下的卸载到 NVMe SSD（更慢但更便宜）。

## Q6: 显存占用怎么估算？

**答**：

**训练时显存**（FP16 训练 + Adam）：

| 项 | 大小 | 备注 |
|----|------|------|
| 参数（FP16） | $2\Psi$ | $\Psi$ 是参数量 |
| 梯度（FP16） | $2\Psi$ | |
| Adam m（FP32） | $4\Psi$ | 一阶动量 |
| Adam v（FP32） | $4\Psi$ | 二阶动量 |
| 参数 FP32 副本 | $4\Psi$ | 主权重 |
| **小计模型状态** | **$16\Psi$** | |
| 激活值 | $\sim BL H \cdot \text{layers}$ | 看序列长度 |
| 临时缓冲 | 小 | |

**示例**：7B 模型 BF16 训练
- 模型状态：$16 \times 7 = 112$ GB
- 激活（4K seq, batch 4）：~30 GB
- 总：~140 GB（远超单卡 80GB）→ 必须 ZeRO 或 TP/PP

**推理时显存**：
- 参数：$2\Psi$（FP16）
- KV Cache：见专门章节
- 激活：小（无梯度）
- 总：参数 + KV Cache 占主导

## Q7: ZeRO 各阶段对显存的影响？

**答**：

| 阶段 | 模型状态显存 / GPU | 通信开销 |
|------|------------------|---------|
| 基线 DP | $16\Psi$ | $2\Psi$（AllReduce gradient） |
| ZeRO-1 | $4\Psi + 12\Psi/N$ | $2\Psi$ |
| ZeRO-2 | $4\Psi + 14\Psi/N$ | $2\Psi$ |
| ZeRO-3 | $16\Psi / N$ | $3\Psi$（额外 AllGather） |

$\Psi$：参数量，$N$：GPU 数。

**ZeRO-3 是显存最省的，但通信最多**。

---

## Q8: 激活值显存怎么估算？

**答**：
**单层 Transformer 激活值**（粗估）：
- Attention 的 Q, K, V, scores: $\sim 4 \cdot BLH$
- Attention 输出: $BLH$
- FFN 中间: $\sim 4BLH$（4 倍扩展）
- 总：$\sim 12 BLH$ per layer

**全模型**：$12 BL H \cdot L_{\text{layers}}$

**例**：7B 模型，$B=4, L=4096, H=4096, L_{\text{layers}}=32$
- $12 \times 4 \times 4096 \times 4096 \times 32 \times 2$ bytes（BF16）
- $\approx 50$ GB

**所以 Gradient Checkpointing 很必要**——降到 $\sqrt{L_{\text{layers}}} \cdot ...$ 量级。

## Q9: 通信与计算的 overlap？

**答**：
**机会**：
- DP 中，反向算靠后层时，靠前层的梯度可以同时 AllReduce
- ZeRO-3 中，参数 AllGather 可与前向计算的前几层重叠

**PyTorch DDP**：
- 自动桶（bucket）合并小 tensor
- 反向计算与 AllReduce 重叠
- 充分利用 GPU 计算 / 网络带宽并行

**ZeRO**：
- 预取参数（prefetch）
- 分层 AllGather

## Q10: 显存碎片怎么处理？

**答**：
**问题**：训练 / 推理过程中频繁分配释放，导致内存碎片，可用大块减少。

**PyTorch 措施**：
- `torch.cuda.empty_cache()`：清理 cached 但未使用的 block
- `PYTORCH_CUDA_ALLOC_CONF` 环境变量调整 allocator 策略
- 例：`expandable_segments:True`（PyTorch 2.1+）

**推理（vLLM）**：PagedAttention 直接解决碎片问题。

## 🎯 高频追问

1. **AllReduce 的通信量**？Ring AllReduce：$2(N-1)/N \cdot \Psi \approx 2\Psi$，与 GPU 数无关。
2. **ZeRO-3 比 ZeRO-2 多多少通信**？多一次 AllGather（前向时），总通信约 1.5×。
3. **CPU Offload 适合什么场景**？资源极有限（单卡）+ 不在意速度（实验性微调）。
4. **NVLink 满载时 AllReduce 多快**？A100 节点内 8 卡 AllReduce 100GB 数据约 200ms（NCCL 实测）。
5. **激活值能像参数一样切分吗**？可以，SP（序列并行）和 Megatron-SP 就是切激活值。
