# 通信与显存

> 多卡训练绕不开两个工程问题：**多卡之间怎么传数据**（集合通信）和**单卡显存怎么算**（显存估算）。
> 这一篇用具体例子把它们讲清楚。

---

## 1. 集合通信 4 个原语：先上 ASCII 图

> "**集合通信**" = "**所有 GPU 一起参与**的通信操作"。
> 不是点对点（P2P）那种"GPU0 把数据发给 GPU1"，而是"4 张 GPU 一起完成某种数据交换"。
> 由 **NCCL**（NVIDIA Collective Communication Library）这种底层库实现。

### 1.1 AllReduce：求和后大家都拿到一样的结果

**用一个比喻**：4 个人各自算了数学题答案，**算出全班平均分，然后所有人都知道这个平均分**。

```
做之前:
  GPU0: [1, 2]
  GPU1: [3, 4]
  GPU2: [5, 6]
  GPU3: [7, 8]

做完 AllReduce(sum):
  GPU0: [16, 20]   ← 16 = 1+3+5+7,  20 = 2+4+6+8
  GPU1: [16, 20]
  GPU2: [16, 20]
  GPU3: [16, 20]
```

**用在哪**：DP 中的梯度同步——每张卡算出梯度后，AllReduce 求平均，所有卡得到同样的"全 batch 平均梯度"，再各自更新。

### 1.2 AllGather：每人有一段，最后大家都拿到完整版

**比喻**：4 个人各自抄了字典的一部分，**互相分享后每人都有完整字典**。

```
做之前:
  GPU0: [a, b]
  GPU1: [c, d]
  GPU2: [e, f]
  GPU3: [g, h]

做完 AllGather:
  GPU0: [a, b, c, d, e, f, g, h]
  GPU1: [a, b, c, d, e, f, g, h]
  GPU2: [a, b, c, d, e, f, g, h]
  GPU3: [a, b, c, d, e, f, g, h]
```

**用在哪**：ZeRO-3 中"参数被切成 4 段"，每个 GPU 只存一段；前向计算前先 AllGather 凑齐完整参数。

### 1.3 ReduceScatter：求和后每人只拿一段

**比喻**：4 个人各自算了 4 道题答案，**汇总求和后每人只负责保存一道题的总分**。

```
做之前:
  GPU0: [a0, a1, a2, a3]
  GPU1: [b0, b1, b2, b3]
  GPU2: [c0, c1, c2, c3]
  GPU3: [d0, d1, d2, d3]

做完 ReduceScatter(sum):
  GPU0: [a0+b0+c0+d0]    ← 只拿到第 0 段的总和
  GPU1: [a1+b1+c1+d1]
  GPU2: [a2+b2+c2+d2]
  GPU3: [a3+b3+c3+d3]
```

**用在哪**：ZeRO-3 中"梯度也分片"——每张卡只需要保存一段梯度，所以求和后只拿那一段。

### 1.4 All-to-All：每人发不同的东西给不同的人

**比喻**：4 个学生互相交换作业，每人**给每个人都发一份不同的内容**。

```
做之前（每人有 4 份数据）:
  GPU0: [给0自己的, 给1的, 给2的, 给3的]
  GPU1: [给0的, 给1自己的, 给2的, 给3的]
  ...

做完 All-to-All:
  GPU0: [GPU0自己留的, GPU1给0的, GPU2给0的, GPU3给0的]
  GPU1: [GPU0给1的, GPU1自己留的, GPU2给1的, GPU3给1的]
  ...
```

**用在哪**：MoE 中"token 按路由分发到不同专家所在的卡"——每张卡的 token 要去不同的专家，需要 All-to-All 把 token 发到目标卡。

### 1.5 一个数学等式

$$\text{AllReduce} = \text{ReduceScatter} + \text{AllGather}$$

直觉：**先求和分发（每人拿一段），再聚拢（每人拿完整）= 先求和再大家都拿完整 = AllReduce**。

ZeRO-3 利用这个等式，把 AllReduce **拆成两步**，中间那一步每张卡只存一段，**显存更省**。

## 2. 硬件层级：通信"快不快"差别巨大

不是所有 GPU 之间通信都一样快。

### 2.1 节点内（同一台服务器里的 GPU）

| 互联 | 带宽 |
|---|---|
| **NVLink**（A100） | ~600 GB/s |
| **NVLink**（H100） | ~900 GB/s |
| **NVSwitch** | 让节点内所有 GPU 全互联（消除"GPU0 到 GPU3 必须经过 GPU1"的瓶颈） |

### 2.2 跨节点（不同服务器之间）

| 互联 | 带宽 |
|---|---|
| **InfiniBand HDR** | 200 Gb/s ≈ 25 GB/s |
| **InfiniBand NDR** | 400 Gb/s ≈ 50 GB/s |
| 普通以太网 | 远更慢 |

```text
节点内 NVLink 比跨节点 IB 快 10-30 倍。
所以 TP（每层都通信）必须放节点内，PP（边界才通信）才能跨节点。
```

## 3. 训练时显存怎么算？

> 这是面试常问、上手训练的第一道关：**单卡能装下多大模型？**

### 3.1 模型状态（与 batch 无关）

设参数量为 $\Psi$（如 7B = $7 \times 10^9$）。**BF16 训练 + Adam** 的标准配方：

| 项 | 含义 | 大小 |
|---|---|---|
| 参数（BF16，2 字节） | 模型权重 | $2 \Psi$ |
| 梯度（BF16） | 反向得到 | $2 \Psi$ |
| Adam $m$（FP32，4 字节） | 一阶动量 | $4 \Psi$ |
| Adam $v$（FP32） | 二阶动量 | $4 \Psi$ |
| FP32 主权重 | 高精度参数副本（混合精度训练用） | $4 \Psi$ |
| **小计** | | **$16 \Psi$ 字节** |

> **为什么要 FP32 主权重副本？** BF16 精度低，连续累积小更新会"丢精度"。所以训练时 Adam 在 FP32 上更新主权重，再把主权重 cast 成 BF16 给前向用。

### 3.2 激活值（与 batch 和序列长度有关）

激活值 = "前向时算出来的中间结果，反向要用"。

**单层 Transformer 大约**：
- Attention 的 Q/K/V/scores：$\sim 4 BLH$
- Attention 输出：$BLH$
- FFN 中间：$\sim 4 BLH$
- **每层合计**：$\sim 12 BLH$

**符号说明**：
- $B$：batch（一次几个样本）
- $L$：序列长度（每个样本几个 token）
- $H$：hidden dim（每个 token 多少维）

**全模型**：$12 BLH \times L_{\text{layers}} \times \text{bytes}$。

### 3.3 实际算一下：7B 模型 BF16 训练

参数：$\Psi = 7 \times 10^9$，$L_{\text{layers}} = 32$，$H = 4096$。

**Case A：batch=4, seq=4096，无任何优化**

- 模型状态：$16 \times 7 = 112$ GB
- 激活值：$12 \times 4 \times 4096 \times 4096 \times 32 \times 2 \approx 50$ GB
- **合计：~162 GB → 单张 80GB 卡装不下！**

**Case B：开 Gradient Checkpointing（用 33% 计算换显存）**

- 激活值：$\sqrt{32} \approx 5.7$ 倍缩减 → ~9 GB
- 合计：~121 GB → 还是装不下

**Case C：Case B + ZeRO-3（8 卡分片）**

- 模型状态分片：$112 / 8 = 14$ GB
- 激活值：~9 GB
- **合计：~23 GB → 装得下！**

```text
所以训 7B 模型基本都用 ZeRO-3（FSDP）+ Gradient Checkpointing。
```

## 4. 推理时显存（更简单）

推理时**没有梯度、没有优化器状态**：

| 项 | 大小 |
|---|---|
| 参数（BF16） | $2 \Psi$ |
| KV Cache（自回归生成时缓存历史 K/V） | 见 [KV Cache 篇](../04-训练推理加速篇/01-KVCache.md) |
| 临时激活 | 小 |

**推理显存 ≈ 参数 + KV Cache + 余量**。

## 5. 三种"换"显存的工具

> "显存不够"是分布式训练的常态。可以拿不同代价去换显存。

### 5.1 梯度累积（Gradient Accumulation）：用时间换 batch

**问题**：想要 batch=64，但单卡只能装 batch=8。

**解法**：跑 8 次 batch=8，**梯度累加**到一起，最后做一次更新——等价于 batch=64。

```python
optimizer.zero_grad()
for i in range(8):                                    # 8 次累积
    loss = model(micro_batch_i).loss / 8              # 注意除以 8
    loss.backward()                                    # 梯度自动累加到 .grad 上
optimizer.step()                                       # 一次更新
```

**注意**：
- 必须 `loss / accum_steps`（让累加后的梯度等于"平均"而非"求和"）
- LayerNorm/RMSNorm 不受影响（per-sample 计算）
- 学习率调度的"step"指**优化步**，不是 micro 步

### 5.2 梯度检查点（Gradient Checkpointing）：用计算换显存

**问题**：反向需要前向激活，全保存 → 显存爆。

**解法**：前向时**只存少数检查点**，反向时**重算**中间激活。

```python
from torch.utils.checkpoint import checkpoint
# 训练时把每个 block 包一下
out = checkpoint(transformer_block, x)
```

**效果**：
- 显存：$O(L_{\text{layers}}) \to O(\sqrt{L_{\text{layers}}})$
- 计算：约 +33%（多一次前向）

> **FlashAttention 也用了这个思想**：前向不存 attention 矩阵，反向重算。

### 5.3 CPU/NVMe Offload：用速度换显存

**思路**：把 Adam 状态、甚至参数搬到 CPU 内存或 NVMe 硬盘，需要时再调回 GPU。

**适用**：单卡超小（如消费级 24GB）+ 不在意速度。
**缺点**：PCIe 带宽是瓶颈，训练慢得多。

**DeepSpeed ZeRO-Offload** / **DeepSpeed ZeRO-Infinity** 是常见实现。

## 6. 通信和计算可以"重叠"

GPU 既能算又能传数据——这两件事**可以并行进行**。

**典型机会**：
- DP 中：反向算完最后几层时，前面几层的梯度可以**同时** AllReduce
- ZeRO-3：前向算第 i 层时，**预取**第 i+1 层的参数（AllGather）

PyTorch DDP 通过"**bucket**"机制自动做这件事——把多个小 tensor 合并成一个大 tensor 再通信，减少调用次数。

```text
通信和计算重叠 = 把"等通信"的时间用来"算下一步"
                 → 训练时间能减少 20-40%
```

## 7. 显存碎片：长训练的隐形杀手

**问题**：PyTorch 频繁 `cudaMalloc`/`cudaFree`，导致显存被切碎，
明明剩余总量够，但找不到一块**连续**的大空间。

**症状**：训练 N 个 step 后突然 OOM（即使任务量没增加）。

**应对**：
- `torch.cuda.empty_cache()`：清理缓存的 unused block
- 设置 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`（PyTorch ≥ 2.1）：让 allocator 可扩展，不再依赖固定段

> 推理服务的显存碎片问题更严重，**vLLM 的 PagedAttention 就是为此设计的**。

## 8. 最简记忆

```text
4 个集合通信原语：
  AllReduce      ←→ DP 梯度同步
  AllGather      ←→ ZeRO-3 还原参数
  ReduceScatter  ←→ ZeRO-3 梯度规约
  All-to-All     ←→ MoE 路由 / 序列并行

数学等式：AllReduce = ReduceScatter + AllGather

硬件带宽：节点内 NVLink ~600-900 GB/s
         跨节点 IB    ~25-50 GB/s

训练显存（BF16 + Adam）：
  模型状态 16 Ψ + 激活值 ~12 BLH × 层数
  没有 Gradient Checkpointing 几乎一定 OOM

显存优化三件套：
  Gradient Accumulation  时间换 batch
  Gradient Checkpointing 计算换显存（+33% 时间）
  CPU/NVMe Offload       速度换显存
```

## 🎯 高频追问

1. **AllReduce 通信量是多少**？Ring AllReduce ≈ $2(N-1)/N \cdot \Psi \approx 2\Psi$ 字节，**与 GPU 数 $N$ 几乎无关**——这就是为什么 AllReduce 在大集群仍可扩展。

2. **ZeRO-3 比 ZeRO-2 多多少通信**？ZeRO-3 多一次 AllGather（前向时拉参数），总通信约 1.5×。所以 ZeRO-3 显存最省，但通信最多。

3. **CPU Offload 适合什么场景**？资源极有限（如消费级单 GPU 24GB 训练 13B）+ 不在意速度（实验性微调）。

4. **NVLink 满载 AllReduce 多快**？A100 节点内 8 卡 AllReduce 100 GB 数据约 200 ms。

5. **激活值能切吗**？可以——SP（序列并行，按 $L$ 维切）、Megatron-SP（按头维切）就是切激活。
