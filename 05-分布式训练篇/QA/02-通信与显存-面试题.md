## Q1: 集合通信 4 个原语分别做什么？各用在哪？
> 难度 ⭐⭐ ｜ 高频 🔥🔥🔥

"**集合通信**" = 所有 GPU 一起参与的通信操作（区别于 P2P 点对点），由 **NCCL** 等底层库实现。

| 原语 | 做什么 | 一句话比喻 | 用在哪 |
|---|---|---|---|
| **AllReduce** | 求和后大家都拿到完整结果 | "算出全班平均分，所有人都知道" | **DP 梯度同步** |
| **AllGather** | 每人有一段，最后大家都拿完整 | "互相分享后人手一本字典" | **ZeRO-3 前向凑参数** |
| **ReduceScatter** | 求和后每人只拿一段 | "汇总后每人只负责一道题总分" | **ZeRO-3 梯度规约** |
| **All-to-All** | 每人发不同的东西给不同的人 | "互相交换作业，每人发不同内容" | **MoE 路由** / SP |

**追问：AllReduce 和 broadcast 有啥区别？** broadcast 是"GPU0 把自己的数据复制给所有人"（不带规约）；AllReduce 是"所有人的数据先按规则合并（如 sum），再让所有人都拿到合并结果"。

## Q2: 推导 AllReduce = ReduceScatter + AllGather
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

**数学等式**：

$$\text{AllReduce} = \text{ReduceScatter} + \text{AllGather}$$

**直觉**：
- ReduceScatter：先求和 + 分发 → 每人拿一段完整规约后的结果
- AllGather：把每人拿的那段聚拢 → 每人拿完整规约后的结果
- 两步合起来 = 所有人都有完整的规约结果 = AllReduce

**ZeRO-3 利用这个等式**把 AllReduce 拆成两步：
- 反向时 ReduceScatter 梯度——每张卡只存自己负责那段的梯度（不存完整）
- 前向时 AllGather 参数——临时凑齐当前层的完整参数，算完丢掉

中间那一步**每卡只存一段**，所以显存更省。代价：多了一次 AllGather，总通信约 1.5×。

**追问：Ring AllReduce 通信量是多少？** $\approx 2(N-1)/N \cdot \Psi \approx 2\Psi$ 字节，**与 GPU 数 $N$ 几乎无关**——这就是为什么 AllReduce 在大集群仍可扩展。

## Q3: 默写 BF16 + Adam 训练的"模型状态" 16 字节/参数 公式
> 难度 ⭐⭐ ｜ 高频 🔥🔥🔥

设参数量为 $\Psi$，每参数的"模型状态"开销：

| 项 | 含义 | 大小 |
|---|---|---|
| 参数（BF16，2 字节） | 模型权重 | $2\Psi$ |
| 梯度（BF16，2 字节） | 反向算出 | $2\Psi$ |
| Adam $m$（FP32，4 字节） | 一阶动量 | $4\Psi$ |
| Adam $v$（FP32，4 字节） | 二阶动量 | $4\Psi$ |
| FP32 主权重 | 高精度参数副本 | $4\Psi$ |
| **合计** |  | **$16\Psi$ 字节** |

**例**：7B 模型 → 模型状态 $= 16 \times 7 = 112$ GB，单张 80 GB H100 都装不下。

**追问：为什么要 FP32 主权重副本？** BF16 精度低（尾数 7 位），连续累积小更新会**丢精度**。所以 Adam 在 FP32 上更新主权重，再 cast 成 BF16 给前向用。Adam $m, v$ 也必须 FP32（数值范围跨度大）。

## Q4: 算一道题：7B 模型，B=4, L=4096，单卡能装下吗？怎么装？
> 难度 ⭐⭐⭐⭐ ｜ 高频 🔥🔥🔥

设 $\Psi = 7 \times 10^9$，$L_{\text{layers}} = 32$，$H = 4096$。

**Case A：无任何优化**
- 模型状态：$16 \times 7 = 112$ GB
- 激活值：$12 \cdot B \cdot L \cdot H \cdot L_{\text{layers}} \cdot 2 = 12 \times 4 \times 4096 \times 4096 \times 32 \times 2 \approx 50$ GB
- **合计 ~162 GB → 单卡 80 GB 装不下！**

**Case B：开 Gradient Checkpointing**（计算换显存）
- 激活值降为 $O(\sqrt{L_{\text{layers}}})$ 量级 → ~9 GB
- 合计 ~121 GB → 仍装不下

**Case C：B + ZeRO-3（FSDP），8 卡分片**
- 模型状态：$112 / 8 = 14$ GB
- 激活值：~9 GB
- **合计 ~23 GB → 装得下** ✓

**结论**：训 7B 基本都是 **ZeRO-3（FSDP）+ Gradient Checkpointing** 起步。

**追问：激活值公式 $12BLH \cdot L_{\text{layers}}$ 怎么来的？** 单层 Transformer 大约：Attn 的 Q/K/V/scores $\sim 4BLH$ + Attn 输出 $\sim BLH$ + FFN 中间 $\sim 4BLH$，每层合计 $\sim 12BLH$（字节看精度，BF16 再乘 2）。

## Q5: 节点内 NVLink vs 跨节点 InfiniBand 带宽差多少？意味着什么？
> 难度 ⭐⭐ ｜ 高频 🔥🔥

| 互联 | 带宽 |
|---|---|
| NVLink（A100） | ~600 GB/s |
| NVLink（H100） | ~900 GB/s |
| NVSwitch | 节点内 8 卡全互联 |
| InfiniBand HDR | 200 Gb/s ≈ 25 GB/s |
| InfiniBand NDR | 400 Gb/s ≈ 50 GB/s |
| 普通以太网 | 慢 100×+ |

**节点内 NVLink 比跨节点 IB 快 10-30 倍**。

**含义（对并行策略的决定性影响）**：
- **TP**（每层都通信）→ 必须节点内 NVLink，否则 GPU 全在等通信
- **PP**（边界才通信）→ 跨节点 IB 即可
- **DP** → 通信频次低 + 可重叠，任何带宽都行

**追问：NVLink 满载 AllReduce 多快？** A100 节点内 8 卡 AllReduce 100 GB 数据约 200 ms。

## Q6: 梯度累积、梯度检查点、CPU Offload 分别换什么？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥🔥

显存不够时三种"换"显存的手段：

| 工具 | 用什么换显存 | 代价 |
|---|---|---|
| **梯度累积**（Gradient Accumulation） | **时间换 batch** | $k$ 步 micro-batch 累加再更新一次，慢 $k$ 倍 |
| **梯度检查点**（Gradient Checkpointing） | **计算换显存** | 前向只存少数检查点，反向重算激活；显存 $O(L) \to O(\sqrt L)$，计算 +33% |
| **CPU/NVMe Offload** | **速度换显存** | Adam 状态 / 参数搬到 CPU 或 NVMe，PCIe 带宽瓶颈，慢得多 |

**梯度累积代码注意**：
```python
optimizer.zero_grad()
for i in range(accum_steps):
    loss = model(micro_batch).loss / accum_steps   # 必须除以 accum_steps
    loss.backward()                                 # 梯度自动累加
optimizer.step()
```

**追问：FlashAttention 和梯度检查点有什么关系？** FlashAttention 也用了"反向重算"的思想——前向不存 $L \times L$ 的 attention 矩阵，反向重算。本质上是一种针对 attention 的特殊 checkpoint。

## Q7: 通信和计算"重叠"怎么做？为什么能省 20-40% 时间？
> 难度 ⭐⭐⭐ ｜ 高频 🔥🔥

GPU 既能算又能传数据——**两件事可以并行进行**。

**典型机会**：
- **DP 反向**：算完最后几层时，前面几层的梯度可以**同时** AllReduce
- **ZeRO-3 前向**：算第 $i$ 层时，**预取**（AllGather）第 $i+1$ 层的参数
- **PP**：传激活的同时算下一个 microbatch

**PyTorch DDP 的 bucket 机制**：把多个小 tensor 合并成大 tensor 再通信，减少 NCCL 调用次数 + 增大重叠窗口。

**效果**：训练时间能减少 **20-40%**——本来"等通信"的死时间被填上了"算下一步"。

**追问：什么情况下重叠会失效？** ① 通信量太大、计算太少（如小模型 + 高频通信）；② 通信和计算用同一 SM 资源（早期 GPU）；③ 跨节点带宽太差，光通信就比计算长。

## Q8: 显存碎片是什么？长训练为什么会突然 OOM？
> 难度 ⭐⭐⭐ ｜ 高频 🔥

**问题**：PyTorch 频繁 `cudaMalloc` / `cudaFree`，导致显存被切碎。**剩余总量够，但找不到一块连续的大空间**——突然 OOM。

**症状**：训练跑 N 个 step 后，明明任务量没变，突然 OOM。

**应对**：
- `torch.cuda.empty_cache()`：清理缓存中未使用的 block
- 设置环境变量 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`（PyTorch ≥ 2.1）：让 allocator 可扩展，不再依赖固定段
- 控制变长输入：batch 内长度对齐（padding 或 bucket）

**追问：推理服务为什么碎片问题更严重？** 推理 KV Cache 大小因 prompt 长度差异巨大，频繁分配释放——这正是 **vLLM 的 PagedAttention** 设计动机：仿操作系统分页，用固定大小 block 管理 KV Cache。

## Q9: 推理显存怎么算？和训练差多少？
> 难度 ⭐⭐ ｜ 高频 🔥🔥

**推理时没有梯度、没有优化器状态、激活值也只存当前层**：

| 项 | 训练 | 推理 |
|---|---|---|
| 参数（BF16） | $2\Psi$ | $2\Psi$ |
| 梯度 | $2\Psi$ | 无 |
| Adam $m, v$, FP32 副本 | $12\Psi$ | 无 |
| 激活值 | 全层 $\sim 12BLH \cdot L_{\text{layers}}$ | 仅当前层 + KV Cache |

**推理显存 ≈ 参数 + KV Cache + 余量**。

例：7B 模型推理大约 $2 \times 7 + \text{KV} \approx 15-20$ GB（视上下文长度），单张 24 GB 消费卡就能跑。训练同样模型至少要 ~120 GB（无优化）。

**追问：KV Cache 大小怎么算？** $\text{KV} = 2 \times B \times L \times L_{\text{layers}} \times H_{\text{kv}} \times \text{bytes}$，其中 $H_{\text{kv}}$ 是 KV 头维度（GQA 下小于 $H$）。

## Q10: ZeRO-3 比 ZeRO-2 多多少通信？为什么？
> 难度 ⭐⭐⭐ ｜ 高频 🔥

**ZeRO-2**：参数仍完整复制，只切优化器状态 + 梯度。通信 = 1× AllReduce 梯度（实际拆成 ReduceScatter，但总通信量同 AllReduce）。

**ZeRO-3**：参数也切。**前向算每一层时**，必须先 AllGather 把切走的参数拉回来。
- 反向 ReduceScatter 梯度 → 等价 0.5× AllReduce
- 前向 AllGather 参数 → 0.5×
- 反向 AllGather 参数（重算时）或缓存 → 0.5×
- 合计约 **1.5× DP 通信量**

**追问：什么时候宁可用 ZeRO-2 也不用 ZeRO-3？** 当模型 + 优化器状态切完 ZeRO-2 已经装下 + 节点间带宽较差时——ZeRO-2 通信代价小，训练吞吐更高。ZeRO-3 是"装不下时才付的代价"。
