# 并行策略：DP / TP / PP / SP / EP

> 一台 GPU 装不下 LLM、训不动大数据 → 必须用多张 GPU。
> 这一篇把"怎么用多张 GPU 同时训练一个模型"从零讲清楚。

---

## 0. 先建立直觉：为什么需要并行？

假设你要训练一个 70B 模型，**单卡装不下，单卡也算不快**：

| 矛盾 | 大概数字 |
|---|---|
| 模型 + 优化器 + 激活值要占的显存 | ~1.4 TB（详见后文显存估算） |
| 单张 H100 显存 | 80 GB |
| 单卡每秒能算的 token | 几百 |
| 想要的吞吐 | 上万 tokens/s |

→ 必须**把训练任务切给一群 GPU**。

**4 种切法**（后文详细展开）：

| 名字 | 缩写 | 切的是什么 | 一句话直觉 |
|---|---|---|---|
| 数据并行 | **DP** | 切**数据** | 每卡一份完整模型，分头处理不同数据 |
| 张量并行 | **TP** | 切**层内的矩阵** | 一道大乘法题切给多人一起做 |
| 流水线并行 | **PP** | 切**层** | 工厂流水线，前几层 → 后几层 |
| 序列并行 | **SP** | 切**序列长度** | 一句长文本切给多人各看一段 |
| 专家并行 | **EP** | 切 **MoE 专家** | 每张卡负责一部分专家 |

```text
DP 解决"训练快"，TP/PP/EP 解决"装得下"，SP 解决"序列太长"。
```

---

## 1. 数据并行（DP）：最朴素的多卡方案

### 1.1 直觉

类比：**4 个学生同时刷题**——每人**一本完整教材**（模型完整副本），但每人**做不同的题**（不同 batch 数据）。每天放学时大家**对一下答案的平均值**（梯度同步），然后一起更新教材。

### 1.2 流程

```
Step 1: 每张卡都有完整模型 W 和优化器状态
Step 2: 把一个 batch 切成 N 份，每张卡处理一份
Step 3: 每张卡独立做 forward + backward 得到自己的梯度 g_i
Step 4: 把所有卡的梯度做平均（AllReduce）
        → 所有卡都得到完整 batch 的平均梯度
Step 5: 每张卡用同样的梯度更新自己的 W → 各卡 W 仍然一致
```

**AllReduce** 是关键步骤：让所有 GPU 上的梯度求和后再分发回每张卡。

> 详细的集合通信原语见下一篇 [《通信与显存》](./02-通信与显存.md)。

### 1.3 优劣

✅ **优点**：实现简单（PyTorch 一行 `DistributedDataParallel` 搞定），扩展性好。
❌ **缺点**：每张卡都要装完整模型——**模型太大就爆显存**。

**适用**：模型 < 单卡显存（比如 7B 模型在 80GB 卡上还能装下时）。

```text
DP 是"扩 batch"的工具，不是"装大模型"的工具。
```

## 2. ZeRO：把"模型状态"分片到多卡

### 2.1 先看看模型状态有多大

训练一个 7B 模型，每张卡要存的"模型状态"包括：

| 项 | 是什么 | 大小（7B） |
|---|---|---|
| 参数（BF16） | 模型权重 | $2 \times 7B = 14$ GB |
| 梯度（BF16） | 反向算出来的 | 14 GB |
| Adam $m$（FP32） | 一阶动量（梯度的滑动平均） | 28 GB |
| Adam $v$（FP32） | 二阶动量（梯度平方的滑动平均） | 28 GB |
| FP32 主权重 | 高精度参数副本（混合精度训练用） | 28 GB |
| **合计** | | **112 GB** |

**所以**：单卡 80 GB 都装不下 7B 的"训练状态"！

> 公式：模型状态 ≈ $16 \Psi$ 字节（$\Psi$ 是参数量，BF16 + Adam）。

### 2.2 关键洞察：DP 中存了 N 份重复的东西

```
DP 8 卡：
  GPU0: [完整参数] [完整梯度] [完整 Adam m] [完整 Adam v] [完整 FP32 副本]
  GPU1: [完整参数] [完整梯度] [完整 Adam m] [完整 Adam v] [完整 FP32 副本]
  ...
  GPU7: [完整参数] [完整梯度] [完整 Adam m] [完整 Adam v] [完整 FP32 副本]
```

**所有卡都存了一模一样的副本**——浪费 8 倍显存。

### 2.3 ZeRO 的思路：每张卡只存 1/N

ZeRO（Zero Redundancy Optimizer，"零冗余优化器"）由 DeepSpeed 提出。
**思路**：把"重复的状态"切分给 N 张卡，每张卡只存一段，需要时再凑齐。

它有 3 个阶段，**切得越多、显存越省、通信越多**：

| 阶段 | 切什么 | 单卡需存 | 通信代价 |
|---|---|---|---|
| 普通 DP | 啥都不切 | 全部 16 Ψ | 1× AllReduce |
| **ZeRO-1** | 只切优化器状态（Adam $m, v$, FP32 副本） | 4Ψ + 12Ψ/N | 1× |
| **ZeRO-2** | + 梯度也切 | 4Ψ + 14Ψ/N | 1× |
| **ZeRO-3** | + 参数也切 | 16Ψ/N | **1.5×** |

例：8 卡训 7B，ZeRO-3 单卡只需 $112/8 = 14$ GB 模型状态——**装下了**！

### 2.4 一个比喻

ZeRO 就像**云盘**：
- DP = 每人电脑都存一份完整文件（浪费）
- ZeRO-3 = 文件分块存在云盘里，谁要用哪一块就下载哪一块

### 2.5 FSDP：PyTorch 原生 ZeRO

PyTorch 自带的 **FSDP**（Fully Sharded Data Parallel）就是 ZeRO 的官方实现：
- `FULL_SHARD` ≈ ZeRO-3
- `SHARD_GRAD_OP` ≈ ZeRO-2
- `HYBRID_SHARD` ≈ 节点内切（ZeRO-3）+ 节点间复制（DP）

```text
中小集群训 7-70B 模型，FSDP（=ZeRO-3） + DP 是首选方案，简单够用。
```

## 3. 张量并行（TP）：把一层内的矩阵切给多卡

### 3.1 直觉

类比：**4 个学生一起算一道大乘法题**——每人算一部分列，最后拼起来。

DP/ZeRO 是"切数据 + 切状态"，TP 是**切计算本身**——一层中的矩阵乘法被拆给多张卡并行算。

### 3.2 在 FFN 中怎么切

FFN 是 $y = W_2 \cdot \text{GELU}(W_1 x)$，$W_1$ 把 $d \to 4d$，$W_2$ 把 $4d \to d$。

**列并行 $W_1$**（按"输出维度"切）：
```
W_1 切成 [W_1^A | W_1^B]   (横着切，左右两半)
GPU0 持有 W_1^A，GPU1 持有 W_1^B

GPU0: 算出 GELU(W_1^A · x) → 中间结果 a（前一半）
GPU1: 算出 GELU(W_1^B · x) → 中间结果 b（后一半）

[a | b] 拼起来就是完整的 GELU(W_1 · x)
```

**行并行 $W_2$**（按"输入维度"切）：
```
W_2 切成 [W_2^A]
              ↓
         [W_2^B]      (竖着切，上下两段)

GPU0: 用 a 和 W_2^A 算出 W_2^A · a
GPU1: 用 b 和 W_2^B 算出 W_2^B · b

把两边相加（AllReduce）：W_2^A · a + W_2^B · b = W_2 · [a;b]
                              ← 这就是完整 FFN 输出
```

**关键设计**：列并行 + 行并行**配对使用** → 中间结果不需要立刻通信，只在两层之间 AllReduce 一次。

### 3.3 在 Attention 中怎么切

把不同的注意力**头**分给不同的卡：
- GPU0 持有头 1-16，GPU1 持有头 17-32
- 每张卡独立算自己的头
- 输出经一次 AllReduce 合并

### 3.4 通信代价

每个 Transformer block 要做 **2 次 AllReduce**（attention 后 + FFN 后），通信量正比于激活值大小 $B \cdot L \cdot D$。

**通信量大** → TP 必须用**节点内** GPU（NVLink 直连，~600-900 GB/s 带宽）。
跨节点用 InfiniBand 才 ~50 GB/s，TP 立刻成瓶颈。

```text
经验：TP 大小 ≤ 单节点 GPU 数（通常 8）。
```

## 4. 流水线并行（PP）：把不同层放到不同卡

### 4.1 直觉

类比：**汽车流水线**——4 个工人，工人 1 装引擎、工人 2 装车身、工人 3 喷漆、工人 4 装轮子。每个工人只做自己那部分。

把模型按层切：80 层模型，4 张卡每卡 20 层。
- GPU0 算前 20 层 → 把激活传给 GPU1
- GPU1 算 21-40 层 → 传给 GPU2
- ...

### 4.2 朴素 PP 的"气泡"问题

```
朴素 PP（4 卡）：
时刻:   1  2  3  4  5  6  7
GPU0:  F0 -- -- -- B0 -- --     ← 前向算完后只能干等
GPU1:  -- F0 -- -- -- B0 --
GPU2:  -- -- F0 -- -- -- B0
GPU3:  -- -- -- F0 B0 -- --

(F0 = forward batch 0, B0 = backward batch 0, -- = 闲置)
```

每张卡有大量空闲时间（**bubble，气泡**）。如果只跑 1 个 batch，效率只有 1/N。

### 4.3 GPipe：把 batch 切成 microbatch

**思路**：把一个大 batch 切成 $M$ 个小批（microbatch），让流水线**填满**。

```
GPipe（4 卡，4 个 microbatch）：
时刻:    1   2   3   4   5   6   7
GPU0:   F0  F1  F2  F3  --  --  --
GPU1:   --  F0  F1  F2  F3  --  --
GPU2:   --  --  F0  F1  F2  F3  --
GPU3:   --  --  --  F0  F1  F2  F3   ← 然后开始反向
```

**气泡比例**：

$$\frac{P - 1}{M}$$

- $P$ = 流水线段数（卡数）
- $M$ = microbatch 数

例：$P=4, M=16$ → 气泡比例 = 3/16 ≈ 19%（再多 microbatch 就更小）。

### 4.4 1F1B / Interleaved 1F1B：进一步优化

- **1F1B**（One Forward One Backward）：前向反向交错执行，减少**激活值显存**
- **Interleaved 1F1B**（Megatron）：每张卡持有不连续的层 chunk（如 GPU0 持有 1-4 层 + 13-16 层），气泡更小

### 4.5 通信特点

PP **只在 stage 边界**传一次激活值（Point-to-Point，P2P），通信量小。

→ 适合**跨节点**用（InfiniBand 即可）。

```text
TP 通信重 → 节点内
PP 通信轻 → 跨节点
```

## 5. 序列并行（SP）：长上下文必备

### 5.1 为什么需要

训练 128K 上下文时，单层激活值显存爆炸：
- Attention 中间矩阵 $\sim L^2$
- 即使有 FlashAttention，激活值也是 $\sim BLD$ 量级

**SP 思路**：把序列长度 $L$ 切给多卡，每卡只看一段。

### 5.2 三种方案

| 方案 | 思路 |
|---|---|
| **Megatron-SP** | 在 TP 基础上，把 LayerNorm/Dropout 的激活也按序列切 |
| **DeepSpeed-Ulysses** | attention 时按"头"切，其他时按"序列"切，用 All-to-All 转换 |
| **Ring Attention** | 设备间环形传 K/V 块，支持任意长度（详见 [高效注意力篇](../04-训练推理加速篇/03-高效注意力算法.md)） |

```text
长上下文（128K+）训练几乎离不开 SP。
```

## 6. 专家并行（EP）：MoE 模型必备

### 6.1 MoE 的特殊性

MoE 模型每层有 N 个"专家"（小 FFN，如 256 个），每个 token 只激活 K 个（如 8 个）。
- **总参数巨大**（DeepSeek-V3 有 671B）
- **每 token 只算 K 个专家**（37B 激活）

### 6.2 EP 思路

把 N 个专家分到 P 张卡上，每张卡持有 N/P 个专家。

每个 token 经路由器决定去哪 K 个专家 → 通过 **All-to-All** 通信发到对应的卡。

```
路由 + All-to-All:
  GPU0 上的 token → 大部分要去 GPU1 / GPU2 上的专家
  All-to-All：所有卡互相把"自己的 token 发到对应专家所在卡"

每层 2 次 All-to-All：
  ① 把 token 送到对应专家 → 计算
  ② 把结果送回原来的卡
```

**通信代价巨大** → DeepSeek 等公司专门做了 DeepEP 等定制 kernel 优化。

## 7. 真实世界：3D / 4D 并行组合

实际训 LLaMA-3 70B 这种规模的模型，**单一并行不够**，要**多种并行组合用**。

### 7.1 经典 3D 并行

```
DP（外）  ×  PP（中）  ×  TP（内）
扩 batch     跨节点切     节点内切
```

- **TP 在最内层**：通信最重，必须用 NVLink（节点内）
- **PP 在中层**：跨节点切，通信轻（只传激活）
- **DP 在最外层**：跨"3D 副本"复制扩 batch

**总卡数** = TP × PP × DP。

### 7.2 例子：LLaMA-3 70B 训练

假设有 256 张 H100：
```
TP = 8（每个节点 8 张卡内部切层）
PP = 4（每 4 个节点接力算不同层）
DP = 8（共 8 份这样的"PP 流水线"并行训不同数据）
8 × 4 × 8 = 256 卡 ✓
```

### 7.3 4D 并行

加一个维度：
- 长上下文 → 加 SP
- MoE → 加 EP

DeepSeek-V3 训练就是 DP + PP + EP 的组合。

### 7.4 选型指南

| 情况 | 推荐 |
|---|---|
| 模型 < 单卡显存 | DP / FSDP |
| 模型 < 单节点显存 | TP（节点内）+ DP |
| 模型 > 单节点显存 | TP + PP + DP |
| 长上下文 | + SP |
| MoE | + EP |

## 8. 通信开销对比一览

| 并行 | 通信类型 | 频率 | 通信量级 | 适合的硬件 |
|---|---|---|---|---|
| DP | AllReduce 梯度 | 每 step | $O(\Psi)$ | 任何 |
| ZeRO-3 | AllGather 参数 + ReduceScatter 梯度 | 每层每 step | ~1.5× DP | 节点内为佳 |
| **TP** | AllReduce 激活 | **每层 2 次** | $O(BLD)$ | **节点内 NVLink** |
| **PP** | P2P 激活 | 每 stage 边界 | $O(BLD)$，**少** | **跨节点 IB** |
| SP | All-to-All | 每层 | $O(BLD)$ | 节点内 |
| EP | All-to-All | 每层 2 次 | 大 | 节点内 / 高带宽 |

```text
记住一条铁律：
  TP 通信最重 → 用最快的硬件（NVLink）
  PP 通信最轻 → 用稍慢的硬件（IB）
```

## 9. 最简记忆

```text
切数据：DP / ZeRO（DP 复制，ZeRO 分片）
切层内：TP（一道大乘法题给多人）→ 节点内
切层间：PP（流水线）→ 跨节点
切序列：SP（长上下文）
切专家：EP（MoE）

3D 并行 = DP × PP × TP，工业标准

显存换通信顺序：
  DP < ZeRO-1 < ZeRO-2 < ZeRO-3 < +PP < +TP
  (省显存递增，通信代价也递增)
```

## 🎯 高频追问

1. **TP 大小为什么不能跨节点**？跨节点带宽（IB ~50 GB/s）远低于 NVLink（~600-900 GB/s）。TP 每层都要 AllReduce 几 GB 激活，跨节点会让 GPU 大部分时间在等通信。

2. **PP 气泡怎么减少**？① 用 1F1B / Interleaved 1F1B；② 加大 microbatch 数 $M$，让 $(P-1)/M$ 比例下降。

3. **ZeRO-3 vs PP 怎么选**？ZeRO-3 通信多但实现简单（FSDP 一行）；PP 通信少但代码复杂（要切层 + 调度气泡）。中小集群（< 256 卡）用 ZeRO-3 + DP；大集群用 3D 并行。

4. **FSDP 能替代 Megatron 吗**？中等规模可以；超大规模（千卡以上）Megatron 仍更优——它有更精细的 TP+PP 调度。

5. **MoE 的 EP 通信怎么优化**？All-to-All 是瓶颈。DeepEP（DeepSeek 开源）、Flux（NVIDIA）做定制 kernel，能把通信和计算重叠。
