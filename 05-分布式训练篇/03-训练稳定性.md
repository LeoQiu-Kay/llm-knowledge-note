# 训练稳定性

> LLM 训练动辄几十天、上千卡。**一旦训崩了不仅浪费钱，还浪费时间**——
> 这一篇讲清楚训练为什么会崩，以及怎么预防。

---

## 0. 先认识"训练崩了"长什么样

正常训练时，loss 曲线是这样：

```
loss
  |
6 |\
5 | \___
4 |     \___
3 |         \____
2 |              \________
1 |
  +-------------------→ step
```

**异常**有几种典型形态：

```
loss spike（毛刺）         发散（彻底崩）           NaN（一刀切）
  |    /\                   |       _/              |
6 |   /  \___               |     _/                |     ────
5 |__/       \              |   _/                  |  __/
4 |           \             |__/                    | /
3 |____________\____        |                       |/   ← NaN!
  +-----------→             +------→               +---→
```

- **Loss spike**：突然飙升后又恢复（最常见，可挽救）
- **发散**：完全停不下来（炸了，得回滚）
- **NaN**：直接出现 nan/inf（数值溢出，立刻挂掉）

```text
所有这些"训崩"的共同根源：
  数值精度问题 + 梯度过大 + 数据异常 + 调度不当
```

## 1. Loss Spike：训练中的"心电图毛刺"

### 1.1 什么是 Loss Spike？

Loss 突然从 2.5 飙升到 8.0，然后**可能恢复也可能彻底发散**。

类比：跑步时突然踩到香蕉皮——可能稳住继续跑，也可能直接摔出去。

### 1.2 6 个常见原因

| # | 原因 | 通俗解释 |
|---|---|---|
| 1 | **学习率过大** | 步子太大，更新一下就跳到错误区域 |
| 2 | **梯度爆炸** | 反向传播时数值连乘越来越大 |
| 3 | **数据异常** | 某个 batch 编码错误、超长、或全是重复内容 |
| 4 | **数值精度问题** | FP16 表示不了的数值变成 0 或 inf |
| 5 | **优化器状态异常** | Adam 的 $v$ 突然很小，分母趋零 → 步子超大 |
| 6 | **Loss Scaling 不当**（FP16 下） | scale 选错导致下溢或溢出 |

### 1.3 怎么处理？

**当下处理**：
1. **回滚 checkpoint**：从上一个稳定的存档点重启
2. **跳过坏 batch**：找出导致 spike 的那批数据，过滤掉
3. **降低学习率**：暂时把 LR 调小度过敏感期
4. **加严梯度裁剪**：把裁剪阈值 $\tau$ 调小

**长期预防三件套**：

```text
✅ BF16 替代 FP16     避免数值精度问题
✅ 充分 Warmup        前期 loss 稳，避免 v_t 估计不准
✅ 梯度裁剪 τ = 1.0   防止单步更新过大
+ 数据预清洗（过滤超长/异常/重复样本）
```

## 2. BF16 vs FP16：为什么现在大家都用 BF16？

### 2.1 浮点数怎么表示数值？

一个浮点数由 3 部分组成：
- **符号位**：正/负
- **指数位**：决定能表示**多大/多小的数**（动态范围）
- **尾数位**：决定**能表示多少有效位数**（精度）

| 格式 | 总位 | 指数 | 尾数 | 范围 | 精度 |
|---|---|---|---|---|---|
| FP32 | 32 | 8 | 23 | ±$10^{38}$ | 高 |
| **FP16** | 16 | **5** | 10 | **±65504**（小！） | 中 |
| **BF16** | 16 | **8** | 7 | ±$10^{38}$（同 FP32） | 低 |
| FP8 (E4M3) | 8 | 4 | 3 | 极小 | 很低 |

**关键洞察**：
- BF16 把一半的位拿去存"指数"，**牺牲精度换范围**
- FP16 拿去存"尾数"，**精度高但范围小**

### 2.2 为什么 LLM 训练 FP16 会出问题？

LLM 反向传播得到的梯度数值**普遍很小**（$10^{-6}$ 量级）。

**FP16 的最小可表示数 ≈ $6 \times 10^{-5}$**。

**结果**：很多梯度直接**下溢成 0**！
- 梯度 = 0 → 参数不更新
- 训练原地踏步、loss 不下降

**而 BF16 的最小可表示数 ≈ $10^{-38}$**——和 FP32 一样，根本不会下溢。

### 2.3 FP16 的补救方案：Loss Scaling

**思路**：训练前把 loss 乘一个大数 $S$（如 65536），让梯度也跟着放大 $S$ 倍，**搬到 FP16 可表示范围**。更新前再除回去。

```python
# 朴素流程（PyTorch 旧 API 大致）：
loss = compute_loss(model, batch)
scaled_loss = loss * S                  # ← 放大
scaled_loss.backward()                   # 梯度也是 S 倍

for p in params:
    p.grad = p.grad / S                  # ← 还原
optimizer.step()
```

**符号说明**：
- $S$：Loss Scale（典型 65536 = $2^{16}$）

### 2.4 动态 Loss Scaling

固定 $S$ 不智能：太小起不到作用，太大又溢出。所以 PyTorch 用**动态调整**：

```text
开始：S 设很大（比如 65536）
每步：
  if 检测到 inf/nan:
      S /= 2          ← 减半
      跳过这一步
  elif 连续 N 步无 inf:
      S *= 2          ← 加倍
```

像 PID 控制器一样，自适应找到当下能用的最大 $S$。

### 2.5 BF16 不需要这些麻烦

```text
BF16 是当前 LLM 训练的事实标准：
  ✓ 不需要 Loss Scaling（直接训）
  ✓ 配置简单
  ✓ 训练稳定
  
FP16 只在不支持 BF16 的旧硬件上用（如 V100）。
A100、H100、TPU 都原生支持 BF16。
```

## 3. FP8：H100 时代的极致压榨

H100/Blackwell 引入了 **FP8**——理论速度比 BF16 翻倍，显存减半。

### 3.1 两种 FP8 格式

| 格式 | 用途 | 特点 |
|---|---|---|
| **E4M3**（4 位指数 + 3 位尾数） | 前向用 | 精度优先，范围窄 |
| **E5M2**（5 位指数 + 2 位尾数） | 反向用 | 范围优先，精度差 |

### 3.2 难在哪？

1. **范围更小** → 必须做 per-tensor 或 per-block scaling 管理动态范围
2. **outlier 容易撑爆**：少数极大值就让整个 tensor 量化失效
3. **比 BF16 更敏感**：调参经验少、参考案例少

### 3.3 实践

- **NVIDIA Transformer Engine** 库：自动做 FP8 缩放和 cast
- **DeepSeek-V3** 是公开的大规模 FP8 训练成功案例（节省 ~50% 显存）
- 通常 FP8 计算 + BF16 主权重副本

```text
FP8 还在快速演进期，DeepSeek-V3 是当下最详细的成功案例。
非顶级团队建议先用 BF16。
```

## 4. 梯度裁剪：防止"步子过大"的安全带

### 4.1 为什么需要

训练初期或者遇到难样本，梯度可能突然变得很大——直接更新就会让参数跳到糟糕的位置（loss spike）。

**梯度裁剪 = 给梯度设个上限，超过就压回来**。

### 4.2 两种主流方法

**By value（逐元素裁剪）**：

$$g_i \leftarrow \text{clip}(g_i, -c, c)$$

- 每个元素如果超过 $c$ 就被截断到 $\pm c$
- 缺点：会**改变梯度方向**

**By norm（全局 L2 范数）**——主流方法：

$$g \leftarrow g \cdot \min\left(1, \frac{\tau}{\|g\|_2}\right)$$

**符号说明**：
- $\|g\|_2$：所有参数的梯度合起来的 L2 范数（一个标量）
- $\tau$：裁剪阈值（典型 1.0）

**做法**：
- 如果 $\|g\|_2 \leq \tau$：不变
- 如果 $\|g\|_2 > \tau$：整体按比例缩小，让 norm 变成 $\tau$

### 4.3 直观例子

```
梯度 g = [3, 4]，则 ||g|| = √(9+16) = 5
设 τ = 1.0，因为 5 > 1.0：
g ← g × (1.0 / 5) = [0.6, 0.8]
新 ||g|| = √(0.36+0.64) = 1.0 ✓
```

**关键好处**：保持梯度**方向不变**，只压缩"步长"。

### 4.4 经验

```text
✓ 训练初期梯度大，频繁触发裁剪
✓ 稳定后偶发触发
✗ 整个训练都在裁剪 → 学习率太大
```

PyTorch 一行就能用：

```python
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
```

## 5. Warmup：训练初期的"暖身"

### 5.1 为什么必须 Warmup？

回想 Adam：每个参数的更新步长是 $\eta \cdot \hat{m} / \sqrt{\hat{v}}$。

**问题**：训练刚开始，Adam 的 $v_t$ 由**很少的样本**估计，**极不准确**：
- 如果 $v_t$ 偶然估出一个很小的值
- 那 $\sqrt{v_t}$ 就很小
- 步长 $\eta / \sqrt{v_t}$ 就**爆炸式增大**
- 一步直接崩

### 5.2 Warmup 怎么做

**线性 Warmup**：从 0 开始线性增加到 peak LR：

```
LR
  |
peak +--------___
     |   /        \___（cosine decay）
     |  /              \___
     | /                   \___
   0 +/-----------------------→ step
     0  warmup     总步数
        steps
```

**典型设置**：
- Warmup 步数 = 1000-2000 步
- 约占总训练步数的 0.5%-1%

### 5.3 直觉理解

```text
Warmup ≈ 给 Adam 的 v_t 一段时间"预热"，
         让它从初始的不准确状态收敛到稳定估计。
         之后再放大 LR 才安全。
```

## 6. 数据问题导致的不稳

很多 loss spike 不是模型问题，**而是数据问题**。

### 6.1 常见坏数据

| 类型 | 例子 | 后果 |
|---|---|---|
| 超长序列 | 一条数据 200K token | 截断不当 → 信息丢失 |
| Tokenizer 失败 | 编码出 token id = 257000（超出词表） | 嵌入查表越界 |
| 空数据 | tokenize 后是空列表 | loss 异常或 NaN |
| 重复轰炸 | 一段网页代码包含 1000 次 `<br>` | loss 异常低 |
| 域偏移 | 训练 90% 中文突然来一个 batch 全英文 | loss 突然飙高 |

### 6.2 检测方法

- 监控 **loss per sample 的分布**（不只是 batch 平均）
- 设阈值：单 sample loss > 阈值就告警
- 抽样审查导致 spike 的 batch（一旦发现）

### 6.3 预防

- 长度过滤：太短（< 50 字符）或太长（> 200K）一律丢弃
- N-gram 重复检测：3-gram 重复占比超阈值就丢弃
- PII（个人信息）和毒性过滤

## 7. 训练监控：要盯哪些指标？

### 7.1 必须监控

| 指标 | 看什么 |
|---|---|
| **Train loss / Val loss** | 是否在稳定下降 |
| **梯度 norm** $\|g\|_2$ | 是否突然飙升 |
| **学习率** | 调度是否正确（warmup → decay 形状对不对） |
| **吞吐量**（tokens/sec/GPU） | 性能是否退化 |
| **GPU 利用率 / 显存占用** | 是否瓶颈 |
| **梯度 / 权重 norm 比** | 参数是否在被有效更新（太小 → 学不动） |

### 7.2 进阶（debug 用）

- 每层的激活/梯度统计（mean、std、norm）→ 看哪一层爆
- Attention entropy → 是否退化成 hard attention
- 输出多样性（不同 prompt 生成是否雷同）

### 7.3 工具

- **WandB**、**TensorBoard**：通用 logger
- **NeMo / DeepSpeed** 自带 dashboard

## 8. Checkpoint 与重启

### 8.1 一个完整 checkpoint 包括

```text
✓ 模型权重
✓ 优化器状态（Adam m, v, FP32 主权重）
✓ 学习率调度器状态（当前 step 数）
✓ 数据加载器状态（处理到哪个 batch）
✓ 随机种子（保证 dropout 等可复现）
```

**少存一项就可能复现不出来**。

### 8.2 Loss Spike 处理流程

```
检测到 spike (loss > threshold)
   ↓
立刻停止训练
   ↓
回滚到最近的稳定 checkpoint
   ↓
分析：是数据问题、还是 LR 问题？
   ↓
处理：
  数据问题 → 跳过那批 batch
  LR 问题 → 降低 LR、加严梯度裁剪
   ↓
重启训练
```

## 9. 千卡 / 万卡训练的额外挑战

规模一大，挑战完全不同：

| 挑战 | 解释 | 应对 |
|---|---|---|
| **节点故障** | 每天总有几台机器宕机 | 自动检测 + 自动重启 |
| **网络抖动** | IB 偶尔慢一会儿 → step 时长不稳 | 网络监控 + 异常处理 |
| **单点故障** | 一台节点挂 → 整次训练失败 | 弹性训练（PyTorch elastic） |
| **数据加载** | 大数据集预处理 + 分发到几千节点 | 流式加载 + WebDataset |
| **不可复现** | 不同节点随机性叠加 → 难复现 bug | 严格控制种子、记录所有随机源 |

### 工程实践

```text
✓ 健康检查 + auto-restart：节点挂了自动拉起
✓ Async checkpoint：保存不阻塞训练
✓ 定期 checkpoint：每 1000 步存一次
✓ 弹性训练：节点数变化时能自适应
✓ 详细的训练日志：spike 出现后能回查
```

```text
Loss Spike 6 大原因：
  LR 太大 / 梯度爆炸 / 坏数据 / FP16 溢出 / 优化器异常 / Loss Scaling 错

预防三件套：
  BF16 + 充分 Warmup + grad_clip = 1.0

精度选择：
  BF16  → 默认（不需 Loss Scaling）
  FP16  → 只在老硬件（V100）

```

## 🎯 高频追问

1. **BF16 真的完全替代 FP16 了吗**？
   训练几乎是。**推理**仍有 FP16 场景（V100 等老硬件不支持 BF16）。

2. **梯度爆炸 vs Loss Spike 区别**？
   - **梯度爆炸**是**原因**：反向传播时梯度连乘越来越大
   - **Loss Spike**是**结果现象**：loss 突然飙升
   - 两者常同时出现，但 spike 也可能由其他原因导致（坏数据、Adam 异常）

3. **学习率应该多大**？
   - 经验：$\eta_{\max} \approx 1\text{--}5 \times 10^{-4}$
   - LLaMA-3 用 $3 \times 10^{-4}$
   - 可用 LR Finder（小学习率试运行，看 loss 突然上升的拐点）

4. **Pre-Norm 真的解决了不稳定吗**？
   比 Post-Norm 好得多（深层 100+ 几乎无损训练），但**千层级**仍需 DeepNorm 等技术配合。

5. **FP8 训练成功案例**？
   - **DeepSeek-V3** 是最有名的（公开技术报告详细描述）
   - NVIDIA 的 H100 + Transformer Engine 也是基础设施支撑
