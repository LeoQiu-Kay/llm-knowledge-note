# 训练稳定性

> Loss spike、BF16 vs FP16 是大模型训练的常见问题。

---

## Q1: Loss spike 是什么？怎么处理？

**答**：
**Loss spike**：训练过程中 loss 突然飙升（如从 2.5 跳到 8.0），可能恢复，也可能彻底发散。

**常见原因**：
1. **学习率过大**：参数更新跨度大
2. **梯度爆炸**：未裁剪 / 裁剪阈值过大
3. **数据异常**：某批数据有问题（编码错误、异常长度）
4. **数值精度问题**：FP16 下激活溢出
5. **优化器状态错误**：Adam 的 $v$ 太小，分母趋零
6. **混合精度 Loss Scaling 不当**

**处理**：
1. **回滚 checkpoint**：从前一个稳定 checkpoint 重启
2. **跳过坏 batch**：找出导致 spike 的 batch 跳过
3. **降低学习率**：暂时降 LR 度过敏感期
4. **更严格梯度裁剪**：把 clip threshold 调小
5. **切到 BF16**：如果原来用 FP16
6. **检查数据**：删除异常样本

**预防**：
- BF16 替代 FP16
- 充分 warmup
- 梯度裁剪（典型 1.0）
- 数据预清洗

## Q2: BF16 vs FP16 的稳定性差异？

**答**：

**FP16**（IEEE 754 half-precision）：
- 1 符号 + 5 指数 + 10 尾数
- 范围：$\sim 6 \times 10^{-5}$ 到 $65504$
- 精度高，但**范围小** → 容易溢出

**BF16**（Brain Float 16）：
- 1 符号 + **8 指数** + 7 尾数
- 范围：与 FP32 同（$\sim 10^{-38}$ 到 $10^{38}$）
- 精度较低，但**范围大** → 不溢出

**LLM 训练**：
- FP16 需要 Loss Scaling 避免梯度下溢
- BF16 范围足够，**几乎不需要 Loss Scaling**
- BF16 是当前 LLM 训练的事实标准

**硬件要求**：
- BF16：A100 / H100 / TPU 原生支持
- FP16：所有现代 GPU 都支持

---

## Q3: Loss Scaling 是什么？

**答**：
**问题**（FP16 训练）：梯度数值很小（$10^{-6}$ 量级），FP16 表示不了 → 下溢为 0 → 训练停滞。

**解法**：
1. 前向：Loss 乘大数 $S$（如 $S = 65536$），$\text{loss}' = S \cdot \text{loss}$
2. 反向：梯度被 $S$ 倍放大，搬入 FP16 可表示范围
3. 更新前：梯度除以 $S$ 还原

**动态 Loss Scaling**：
- 初始 $S$ 设大
- 如果出现 inf/nan → $S$ 减半
- 连续 N 步无 inf → $S$ 加倍
- 自适应找最大可用 $S$

**BF16 不需要**：BF16 范围与 FP32 相同，梯度直接放在 BF16 中没问题。

---

## Q4: FP8 训练的挑战？

**答**：
**H100 / Blackwell 引入 FP8**：进一步加速（理论 2× over BF16）。

**FP8 两种格式**：
- **E4M3**：1 符号 + 4 指数 + 3 尾数，精度优先，前向用
- **E5M2**：1 符号 + 5 指数 + 2 尾数，范围优先，反向用

**挑战**：
1. **范围小**：需要 per-tensor 或 per-block scaling
2. **outlier**：极个别异常值会撑爆量化范围
3. **训练稳定性**：相比 BF16 更敏感

**实践**：
- NVIDIA Transformer Engine 库支持自动 FP8
- DeepSeek-V3 用 FP8 训练大获成功，节省 ~50% 显存
- FP8 训练 + BF16 主权重副本

## Q5: 梯度裁剪策略？

**答**：
**两种主流**：
1. **By value**：$g \leftarrow \text{clip}(g, -c, c)$，每个元素截断
2. **By norm**：$g \leftarrow g \cdot \min(1, \tau / \|g\|)$，按全局 L2 范数缩放

**LLM 训练**：**by norm**，$\tau = 1.0$ 最常用。

**为什么 by norm 更好**：
- 保持梯度方向，只压缩大小
- by value 会扭曲梯度方向

**PyTorch 实现**：
```python
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
```

**经验**：
- 训练初期梯度大，裁剪频繁
- 稳定后裁剪偶发
- 如果一直在裁剪，说明 LR 可能过大

## Q6: 学习率 Warmup 的作用？

**答**：
**目的**：避免训练初期梯度估计不准导致的不稳定。

**两个层面**：
1. **Adam 的 $v$ 估计**：$v$ 是二阶动量，初期估计不准，分母不稳
2. **预训练 LLM 的早期阶段**：参数远离最优，大学习率容易发散

**Warmup 策略**：
- 从 0 线性升到 peak LR
- 常用 step 数：1%-5% 的总训练步数
- 例：LLaMA-3：2000 步

**Warmup 后**：
- Cosine Decay 最常见
- Linear Decay 简单
- WSD（Warmup-Stable-Decay）：阶段性恒定 LR 后衰减

## Q7: 数据问题导致的训练不稳？

**答**：
**常见问题**：
1. **超长序列**：单条数据超出训练长度，导致截断不当
2. **编码错误**：tokenizer 失败产生异常 token id
3. **空数据**：tokenize 后为空，loss 异常
4. **重复 spam**：海量重复 token（如某网页代码）
5. **域偏移**：不同子数据集分布差异大

**检测**：
- 监控 loss per sample 分布
- 设置 loss 阈值告警
- 抽样审查异常 batch

**预防**：
- 数据清洗 + 去重
- 长度过滤（如丢弃 < 50 字符或 > 200K 字符）
- N-gram 重复过滤

## Q8: 训练监控指标？

**答**：
**必须监控**：
1. **Loss**：训练 loss、验证 loss、loss per token type
2. **梯度范数**：监控梯度爆炸
3. **学习率**：确保调度正确
4. **吞吐量**：tokens/sec/GPU，监控效率
5. **GPU 利用率 / 显存**：发现瓶颈
6. **梯度 / 权重的 norm 比**：监控参数是否在被有效更新

**进阶**：
- 每层激活 / 梯度的统计（均值、std、norm）
- Attention entropy（是否退化到 hard）
- 输出多样性

**工具**：
- WandB、TensorBoard
- NeMo / DeepSpeed 自带 logger

## Q9: 重启训练的常见做法？

**答**：
**Checkpoint 包含**：
- 模型权重
- 优化器状态（Adam 的 m, v, FP32 副本）
- 学习率调度器状态
- 数据加载器状态（处理到哪个 batch）
- 随机种子

**恢复**：
- 从最近 checkpoint 加载
- 优化器状态必须恢复（否则 Adam 又得 warmup）
- 数据 iterator 跳过已处理的 batch

**Loss spike 处理**：
- 回滚到 spike 前的 checkpoint
- 跳过导致 spike 的 batch
- 重启时降低 LR 或加强裁剪

## Q10: 千卡 / 万卡训练的挑战？

**答**：
**额外挑战**：
1. **节点故障**：每天有节点宕机，需要自动检测 + 重启
2. **网络抖动**：通信卡顿导致 step 时长不稳
3. **稳定性**：单点故障导致整次训练失败
4. **数据加载**：大数据集预处理 / 分发
5. **Determinism**：复现结果困难

**工程实践**：
- 健康检查 + auto-restart
- Async checkpoint（不阻塞训练）
- 定期 checkpoint（每 1000 步）
- 弹性训练（PyTorch elastic）
- 监控 + 报警系统

## 🎯 高频追问

1. **BF16 真的完全替代 FP16 了吗**？训练几乎是。推理仍有 FP16 场景（V100 等老硬件无 BF16）。
2. **梯度爆炸 vs Loss spike**？梯度爆炸是参数更新过大，loss spike 是结果现象；两者常同时出现。
3. **学习率应该多大**？LLaMA-3 用 ~3e-4 峰值，是常见量级。可用 LR finder 探测。
4. **Pre-Norm 真的解决了不稳定吗**？相比 Post-Norm 好很多，但深度极大（千层）仍需 DeepNorm 等技术。
5. **FP8 训练的成功案例**？DeepSeek-V3 是最有名的（公开技术报告详细）。
